# aci/CLAUDE.md

Guidance for working in `aci` (`com.yanny.aci`), the shared core library consumed by both `ali:common` and `awi:common`. See the repo-root `CLAUDE.md` for the overall project layout; this file is the single source of truth for everything described below — `ali`/`awi` never reimplement this mechanism, they only register their own domain types against it.

`aci` ships as its own mod (`aci`, `com.yanny.aci`, versioned by `aci_version`) and is a **mandatory** dependency of both ALI and AWI, declared in their `fabric.mod.json` `depends` / `mods.toml` `[[dependencies.*]]` blocks. Its layout mirrors the other two: `aci/common` holds all the platform-agnostic logic, and `aci/fabric` / `aci/forge` / `aci/neoforge` are thin loader wrappers that shadow `common` into a loadable jar (see `aci/fabric/CLAUDE.md`, `aci/forge/CLAUDE.md`, `aci/neoforge/CLAUDE.md`). `aci:common` is not shadowed into the ALI/AWI jars — `ali:common`/`awi:common` compile against it (`implementation project(path: ":aci:common", configuration: "namedElements")`) and the loader modules get it at runtime through `modImplementation project(":aci:<loader>")`. Repo-root `CLAUDE.md`'s "Versioning" section is the rule for what an ACI change costs, since these packages are published API.

## Package map (`aci/common/src/main/java/com/yanny/aci`)

### `api` — generic contracts implemented per-mod

- `ICorePlugin<TCommonRegistry, TClientRegistry, TServerRegistry>` — plugin entry-point contract (`getModId`, `registerCommon/Client/Server`); implemented by `ali.api.IPlugin` and `awi.api.IPlugin`.
- `ICoreCommonRegistry` / `ICoreClientRegistry` / `ICoreServerRegistry` and their `...Utils` counterparts (`ICoreCommonUtils`, `ICoreClientUtils`, `ICoreServerUtils`, `ICoreWidgetUtils`) — side-specific registration/runtime-helper contracts. Backed by the abstract `manager.Core*Registry` classes below, extended by `Ali*Registry`/`Awi*Registry`. All three `...Utils` contracts declare `getModId()` (see "Logging" below).
- `ICoreDataNode<TServerUtils>` — base for network-serializable, tooltip-bearing, chance-comparable data entries (`getTooltip`, `getId`, `encode`, defaulted `getChance`, `Comparable` by descending chance). Every mod-specific node type (`ali.plugin.common.nodes.*`, `awi.plugin.common.nodes.*`) implements this.
- `CoreListNode<TServerUtils,TDataNode,TClientUtils>` — abstract composite `ICoreDataNode` holding a sorted child-node list plus shared network encode/decode logic; base for `ali.api.ListNode`/`awi.api.ListNode` (both of which are nothing but the two constructors). Its `encode` is `final`: it writes the child count + each child's `ResourceLocation` id and payload, then delegates to the subclass's `encodeNode` for the node's own payload. A child whose encode throws is dropped rather than corrupting the stream — the writer index rewinds to that child's start and the leading count is patched afterwards. It deliberately does **not** touch `TooltipContext`: that is set once per top-level entry by `network.NetworkUtils` and must stay ambient across the remaining siblings. It logs through `utils.getModId()` (see "Logging" below).
- `IWidget` — GUI widget contract (`getRect`, `getDirection`, defaulted `render`/`getTooltipLines`, shared `PADDING`) — the single rendering abstraction every recipe-viewer widget wrapper (EMI/JEI/REI, in both mods) adapts to its host viewer's native widget interface. See `ali/common-emi/CLAUDE.md` for how that adaptation works.
- `CoreListWidget<TDataNode,TWidgetUtils,TClientUtils>` — abstract widget that lays out a tree of child `IWidget`s and draws the connecting branch lines; base for `ali.*.ListWidget`/`awi.*.ListWidget`.
- `AbstractScrollWidget` — scrollable viewport + scrollbars on **both** axes (drag/click/wheel handling, scissored content rendering, `isOutsideViewport` culling); base for the `Emi/Jei/ReiScrollWidget` in all six recipe-viewer modules. Subclasses supply `renderWidgets` and `getTexture`, and pass `(contentWidth, contentHeight)` — the real laid-out tree size, which `CoreClientRegistry.createWidgets` already writes back into the root `RelativeRect`, *not* the available width. Design points worth knowing before touching it:
  - The vertical scrollbar reserves a column (`getScrollbarExtraWidth()`, excluded from the content viewport) and is always drawn. The horizontal one is drawn **only when the content actually overflows** and **overlays** the bottom 8px of the content viewport rather than reserving space, because JEI and REI both report a height per *category* (not per display), so there is no per-recipe height to grow. Consequence: a click in the bottom 8px hits the bar, not the content underneath.
  - `drawContents` scissors to the **content viewport**, not to `rect` — the scrollbar column (and the bottom strip when the horizontal bar is present) is outside it, so scrolled slots and items cannot bleed over a bar no matter when the host viewer flushes its item batch. Relying on draw order alone does not work here.
  - `getViewportHeight()` is what the Y scroll math uses, so the strip the horizontal bar sits on is subtracted from the scrollable height: the bottom of the content stays reachable instead of being permanently clipped under the bar. When the horizontal bar is present the vertical one also stops `getScrollbarExtraWidth()` short of the bottom, mirroring the inset the horizontal bar already leaves at the right; the uncovered corner is intentional.
  - The mouse wheel scrolls Y; `Shift`+wheel scrolls X, falling back to Y when there is no horizontal overflow. A `ScrollableTooltip` that is on screen and overflowing takes the wheel first (see `compatibility` below). Both bars also support marker drag and click-to-jump. `onScrollbarClicked` clears both drag origins before setting the one that was hit — without that, an X drag leaves `dragOriginX` set and `onMouseDragged` never reaches the Y branch again.
  - `SCROLLBAR_OFFSET` (9px) is what the viewport is inset by, not `getScrollbarExtraWidth()` (10px) — the latter is only the column the viewer modules add to their category width.
  - `isMouseOverContent` is the gate every viewer's tooltip/slot-hit path must go through, so hovering a bar (or holding a drag that wandered back over the content) does not raise a tooltip for whatever sits underneath. It answers false for the whole duration of a held drag, which is why it consults `MouseHandler.isLeftPressed()` rather than the drag origin alone — no viewer gives us a reliable mouse-release hook to clear that origin on. EMI and JEI consult it directly; REI cannot, because `Widgets.createTooltip` queues from the mouse args handed to `render`, so `ReiScrollWidget` renders with off-screen coords instead.
  - The atlas carries no horizontal sprites. The **track** needs none: its bevel is diagonally symmetric (`#373737` along the top row and left column, `#ffffff` along the bottom and right), so nine-slicing it wide-and-short already looks right. The **marker** is drawn `translate` → `Axis.ZP` 90° → `scale(1, -1, 1)`, i.e. a rotation *plus* a mirror: rotating alone is what makes its lit bevel land on the wrong end, and the mirror alone would leave the sprite's striped middle rows running along the bar instead of across it. That combination is a reflection, so it reverses the winding order of `innerBlit`'s quads and the blit must be bracketed by `RenderSystem.disableCull()`/`enableCull()` — `GuiGraphics` blits are immediate (`BufferUploader.drawWithShader`), so toggling cull around the call is enough.
- `Rect` (record) / `RelativeRect` (mutable, parent-chained) / `WidgetDirection` (enum) — geometry primitives for widget layout.
- `NumberExpr` — the symbolic number model (see "Number model" below): a sealed interface whose nested records are the generic node kinds (`Const`, `Range`, `Var`, `Lookup`, `Fn`, `Cond`, `Weighted`, `Opaque`), with `encode`/`decode` over `FriendlyByteBuf`. Operations and distributions are not node kinds but `NumberFunction`s in the `NumberFunctions` registry. `NumberDistribution` (point masses plus one continuous part, with its algebra) and `NumberInterval` (interval arithmetic) are what a function's `distribution`/`bounds` work on; `NumberText` (translation key + arguments, number, literal, sequence) is what formatting produces and what a `Var` carries as its label arguments, turned into a `Component` by `toComponent(locale)`; `NumberMode` is the result of `mode()`.

**Shared atlas layout.** `CoreListWidget` and `AbstractScrollWidget` both hardcode u/v offsets but take the `ResourceLocation` from an abstract `getTexture()`, so `ali`'s and `awi`'s `textures/gui/gui.png` must keep the shared sprites at identical coordinates: branch trunk at `(0,0)` 2×1 and branch arm at `(2,0)` 18×2 (`CoreListWidget`), scrollbar track at `(2,2)` 16×16 and scrollbar marker at `(18,0)` 12×17 (`AbstractScrollWidget`). Each mod is free to place its own sprites elsewhere in the atlas. This coupling is invisible to the compiler — changing a sprite means editing both atlases.

### `manager` — plugin-manager and registry base classes

- `ClassKeyedMap` / `ManagedRegistry` / `CorePluginManager` — the generic dispatch/discovery machinery; see "Tooltip system" below for the two dispatch tiers, and the repo-root `CLAUDE.md`'s "Adding a new category" recipe for how `ali`/`awi` build on top of these.
- `BaseRegistry` (package-private) — holds the mod id (`getModId()`, the single implementation behind the three `...Utils` declarations) and tracks every `ManagedRegistry` a mod's registry creates, passing the mod id into each, exposing `clearData`/`printRegistrationInfo`/`printRuntimeInfo` (see "Missing-entry fallback and coverage reporting" below). Parent of `CoreCommonRegistry`/`CoreServerRegistry`/`CoreClientRegistry`.
- `CoreCommonRegistry<TConfig>` — implements `ICoreCommonRegistry`+`ICoreCommonUtils`; takes the mod id as its constructor argument, and owns the translation-key dictionary (`HashBiMap<String,Integer>`) and config access. Extended by `AliCommonRegistry`/`AwiCommonRegistry`, which pass their `Utils.MOD_ID`.
- `CoreServerRegistry<TConfig,TCommonUtils,TServerUtils>` — server-side utils base holding the `ServerLevel`, tooltip cache, and `HolderLookup.Provider`. Takes its mod id from the `CoreCommonRegistry` handed to it. Extended by `AliServerRegistry`/`AwiServerRegistry`. It also owns the `IntProvider`/`FloatProvider` → `NumberExpr` converter registries (see "Number model").
- Scan caches: anything cached for the duration of one server scan is emptied through `registerCacheCleaner(Runnable)` (declared on `ICoreServerRegistry`). `clearCaches()` runs every registered cleaner, each guarded on its own, and then clears the tooltip palette; each mod calls it from the `finally` that brackets its scan, so a failed scan releases its data too, and a mod's registry overrides it for its own internal scan state. `clearData()` drops the cleaners along with every other registration — plugins register them again in `registerServer`, which always runs before a scan.
- `CoreClientRegistry<...>` — client-side registry; takes its mod id from the `CoreCommonRegistry` handed to it, owns widget/data-node factory maps, and uses `compatibility.DataReceiver` plus a `ScheduledExecutorService` to reassemble chunked payloads received over the network (see each mod's `network` package). Extended by `AliClientRegistry`/`AwiClientRegistry`.

### `compatibility`

- `DataReceiver` — accumulates indexed byte-array chunks into a `CompletableFuture<byte[]>`, with `forceDone`/`cancelOperation` timeout handling. Used only internally by `manager.CoreClientRegistry`; this is the *client-side reassembly* half of the chunked-sync pattern each mod's `network` package implements independently (see `ali/CLAUDE.md`'s networking section, mirrored by `awi/CLAUDE.md`).

- `ScrollableTooltip` — the tooltip component every ALI/AWI tooltip is handed to a viewer as: one component holding all the `TooltipLine`s, implementing both `TooltipComponent` and `ClientTooltipComponent`, so it goes wherever either type is accepted. It caps its own height to what the screen leaves free and draws only the visible window of lines plus a 1px scrollbar, so no scissoring is involved.
  - Rows differ in height (a text row is one `LINE_HEIGHT`, a chart row several), but every height is a whole number of `LINE_HEIGHT`s and the offset counts in those units. A text row is therefore always fully in or out of the window; a chart can be cut, so its fills are clamped to the visible bands and its label band is drawn only when entirely visible.
  - A chart's height is not known to `TooltipLine`: its panels are laid out here, in the constructor, because it needs the font. Each series is one panel spanning only its own `first … last` columns at the shared column width, and panels fill a row up to the widest text line, then wrap; a chart widens the tooltip only when a single panel is wider than the text. A panel is `PANEL_LINES` high: `BAR_LINES` of bars, then its min/max labels 1px below the axis.
  - The free height depends on the rest of the tooltip (item name, mod name, lines other mods add), which a component cannot see from `getHeight()`. The mods feed it through `setRenderedComponents`: each mod's `MixinGuiGraphics` sets the list at `HEAD` of `GuiGraphics.renderTooltipInternal` and clears it at every `RETURN`. ACI carries no mixins, so this lives in ALI and AWI alike; with both installed it simply runs twice. Outside that window the other components count as zero height.
  - Scroll state is static (offset, the lines last drawn, the time of the last draw), because EMI and REI build a fresh instance every frame. The offset resets when different lines are drawn or nothing was drawn for `ACTIVE_MILLIS`. `onMouseScrolled` consumes the wheel only while a tooltip drawn within that window overflows, and is called from `AbstractScrollWidget.onMouseScrolled` — every viewer's recipe content sits inside a scroll widget, so that one call site covers all of them.
  - Forge's and NeoForge's `ClientTooltipComponent.create` know only registered factories and do not pass a `ClientTooltipComponent` through (NeoForge throws on an unregistered one), so JEI there needs `RegisterClientTooltipComponentFactoriesEvent.register(ScrollableTooltip.class, identity)`. Each mod's Forge and NeoForge module does it (`ForgeClientModBusSubscriber`, `NeoForgeClientModBusSubscriber`); EMI, REI and JEI on Fabric use the instance directly.
  - `LINE_HEIGHT` and `SCREEN_MARGIN` copy vanilla's text line height and tooltip positioner; a tooltip-restyling mod that adds padding makes the tooltip overflow by that padding.

### `configuration`

- `ICoreConfig` — the contract a mod's config root implements: `getConfigVersion`/`setConfigVersion`/`getCurrentVersion`. The version field stays a plain public field on `AliConfig`/`AwiConfig`, so the generated JSON's field order is unchanged. There is no `normalize()` hook: the configs are `Codec`-serialized, and a missing (or `null`) field falls back through the codec's own `orElse`/`orElseGet`.
- `CoreConfigUtils` — guarded by `CoreConfigUtilsTest` (see "Tests" below). `readConfiguration(configDir, modId, fileName, codec, ops, factory)`: creates `<configDir>/<modId>/<fileName>` from defaults when missing, loads it, and rotates it to `.bak` + regenerates when the file's version is older than `getCurrentVersion()`. Every failure path falls back to `factory.get()`, so it never returns null and never throws. The `DynamicOps<JsonElement>` argument is what lets a registry-backed config be read at all — AWI passes plain `JsonOps.INSTANCE`, ALI passes a `HolderLookup.Provider`-backed serialization context, since its `Ingredient` catalysts need the registries. Each mod's own `configuration.ConfigUtils` is only that call.
- `SpawnInfoFilter` — the config block behind both mods' `spawnInfo` option: `entities` (entity ids) plus `whitelist`, with its own `CODEC` embedded in `AliConfig`/`AwiConfig`. It is the `Predicate<EntityType<?>>` handed to `spawn.SpawnInfo`, which drops filtered entities while collecting, so nothing downstream filters again. `isDisabled()` (an empty whitelist) is how a mod skips building `SpawnInfo` at all, and passes `null` on instead. Read on the server only, like the rest of the scan input.
- `TooltipColors` — the config block behind both mods' `tooltipColors` option: five color strings (`text`, `value`, `error`, `branch`, `secondary`) plus the `levels` list, each a vanilla color name or a `#RRGGBB` code, resolved by `resolve(modId)` into a `TooltipStyle` cached in a private field. An unparseable value logs a warning and falls back to that field's default (a bad `levels` entry is skipped, an empty list means the default), so a bad color never breaks rendering. It carries its own `CODEC` and is embedded in `AliConfig`/`AwiConfig`, not something ACI loads for itself — ACI has no config file and no common initializer.

### `network`

- `NetworkUtils` — the *server-side write/compress* half of the chunked-sync pattern, shared by both mods' `AbstractServer`: `writeMapData` (length-prefixed `Map<ResourceLocation, TNode>`, rewinding and re-patching the count when an entry fails), `writeEntryData`/`writeNodeData` (single entry / single node — the latter is what ALI's wandering-trader node uses, since it carries no `ResourceLocation` on the wire), and `compressAndStoreData` (gzip + slice into ≤32KB chunks, handed to a `BiConsumer<Integer, byte[]>` that wraps each chunk in the mod's own packet type). Every method takes a `String modId` first argument, used purely to resolve the logger it writes through (see "Logging" below).

Packet/channel definitions stay entirely mod-specific — the `*Message` records, channel ids and registration live in `ali/common/.../network` + the loader modules, and are duplicated in `awi`.

### `platform`

- `ICorePlatformHelper<T extends ICorePlugin<?,?,?>>` — `getPlugins()` (loader-specific plugin discovery) + `getConfiguration()` (config path). Implemented by `ali.platform.services.IPlatformHelper` and `awi.platform.services.IPlatformHelper`, each with per-loader implementations living outside `common` (see `ali/fabric/CLAUDE.md`, `ali/forge/CLAUDE.md`, `awi/fabric/CLAUDE.md`).

### `number`

`NumberEvaluator` (`bounds()`/`distribution()` dispatch over the node kinds), `BuiltinFunctions` (the `aci:` functions) and `NumberFormatter` — internal machinery behind `api.NumberExpr`, described under "Number model" below.

### `language`

Supporting types for the translation-key model, plus `CoreLang` (the static `TRANSLATION_MAP` aggregator — the wiring itself is described under "Language wiring" below):
- `IMultiKey` — `singular()`/`plural()` accessor contract.
- `ITooltipKey extends IMultiKey` — adds `getTranslation()` plus English fallback accessors; implemented by generated lang enums (`ali.language.Lang`, `awi.language.Lang`).
- `Translation` (record: `sKey, pKey, sEng, pEng`) — the singular/plural key + English-fallback tuple.

### `tooltip`

`TooltipBuilder`, `TooltipNode`, `RawTooltipNode`, `TooltipNodePalette`, `TooltipContext`, `TooltipStyle`, `CacheKey`, `CommonValueTooltip`, `CoreTooltipUtils`, `RegistryNames` — the tree model described in full below. `TooltipLine`, `TooltipNumber`, `NumberOptions`, the package-private `NumberView` and `CommonNumberProviders` belong to the number nodes (see "Number model"). A `TooltipNodePalette` is built for one mod and logs under that mod's id.

## Logging

Loggers come from `CommonLogUtils.getLogger(modId)` (root package, next to `Utils`): it names the logger after the calling class through a `StackWalker` and wraps it in `PrefixLogger`, which prepends `[<modId>]` to every message. Minecraft's log pattern prints the logger name on Forge but not on Fabric, so that prefix is what identifies the writing mod there; it is emitted on every loader. Never prefix a message by hand.

ACI's shared code logs under the mod it works for, not under `aci`, so the mod id has to reach every log site:
- classes owned by one mod's registry tree — `CorePluginManager`, `CoreCommonRegistry`, `CoreClientRegistry`, `ManagedRegistry`, `DataReceiver`, `TooltipNodePalette` — take the mod id as a constructor argument and keep an instance `logger` field;
- static helpers `CoreConfigUtils` and `NetworkUtils` resolve the logger from their `String modId` parameter;
- code reached through a utils instance uses `utils.getModId()` (`CoreListNode.encode`, `TooltipNode.decodeRaw`); `TooltipBuilder.build` has no mod id of its own and reports through `TooltipContext.getPalette()`, which already logs under the mod it was built for.

`getModId()` is declared three times — on `ICoreCommonUtils`, `ICoreServerUtils` and `ICoreClientUtils`. The latter two cannot inherit it from `ICoreCommonUtils<TConfig>`, because a mod's `IServerUtils`/`IClientUtils` already extends that interface with its concrete config type and a second, wildcarded inheritance is a type-argument clash. `BaseRegistry` implements it once for all three.

`ali`/`awi` classes need none of this plumbing: they hold `private static final Logger LOGGER = CommonLogUtils.getLogger(Utils.MOD_ID)`.

## Tooltip system

ALI and AWI both display their information the same way: a tree of `TooltipNode`s built once on the server and rendered into `Component`s on the client. The whole mechanism — tree model, registry-lookup dispatch, language wiring, network caching — lives here in `aci` and is identical for both mods. **This section is the single source of truth for how it works; don't re-derive or restate it in a mod-specific doc.** `ali`/`awi` only ever add their own domain-specific categories and builder methods on top of this — they never reimplement the mechanism itself.

### Tree model

- `TooltipBuilder` (`aci.tooltip`) is the fluent construction API — `value(...)`, `array(...)`, `branch(...)`, `keyOnly(...)`, `error(...)`, etc. — terminated by `.build(key)` to produce an immutable `TooltipNode`. `add(TooltipBuilder|TooltipNode)` silently drops empty children, so composing builders never produces stray empty headers.
- `TooltipBuilder.component(...)` is the last resort: a component travels as its full JSON in every palette node (no key index), and the translation keys inside it are invisible to the unused-lang-key audit. Express a value as a key with `value`s, a `number` or `intervals` instead; `component` is only for a value that already arrives as a `Component`.
- A value string may carry a marker that the client resolves at render time (`TooltipNode.formatValue`): `TooltipBuilder.translate(key)` becomes `Component.translatable(key)`, and `TooltipBuilder.registryEntry(registry, value)` (`<registry id> <entry id>`) becomes the entry's in-game name through the resolver `RegistryNames` holds for that built-in registry, or the bare entry id when there is none. The name is built on the client because some names take arguments (`Item.getName(ItemStack)` of GregTech's `%s Dust`) that a translation key alone loses; both stay plain interned strings on the wire. `CoreTooltipUtils.getBuiltInRegistryTooltip(utils, registry, value, showName)` is how ALI/AWI emit it under their `showInGameNames`. ACI registers the vanilla resolvers (item, block, entity type, mob effect, attribute, potion — named as its potion item); `RegistryNames.register` is a static global for the same reason `NumberFunctions` is — it is reached from the node alone and holds stateless definitions keyed by registry id.
- An entry with no resolver — any registry, synced or datapack-only, since only ids travel — is named through the first translation key the client's language has, out of `<registry>.<ns>.<path>` with `<registry>` the last segment of the registry path (`biome`, `dimension`, `structure`), the whole path dotted (`worldgen.biome`) or raw, each also prefixed by the registry namespace for a modded registry. `TooltipBuilder.registryKey(ResourceKey)` emits it from just the key — `spawn.SpawnInfo` does so for its dimensions, biomes and structures when constructed with `showInGameNames`; `RegistryNames.name(registry, id, fallback)` is the same lookup for client code outside a tooltip (AWI's dimension and biome titles). A tag goes through its own marker, `TooltipBuilder.tagKey(TagKey)` → `RegistryNames.resolveTag`: `tag.<registry>.<ns>.<path>` (the Fabric API / NeoForge / EMI form, the registry prefixed by its namespace only when modded), with a `forge` tag also tried as `c`, then EMI's registry-less `tag.<ns>.<path>`. Every path, registry or entry, is tried with `/` turned into `.` first and raw second — vanilla, tags and most mods dot it, NeoForge's dimension keys do not. No match shows the bare id. `CommonValueTooltip` emits both for every `ResourceKey`/`TagKey` value when `ICoreCommonUtils.showInGameNames()` (default `false`, ALI/AWI return their config's) is on, which is why its `TServerUtils` is also an `ICoreCommonUtils<?>`.
- `TooltipNode` is the immutable tree node actually rendered (`CoreTooltipUtils.toLines(node, indent, showAdvanced, style, numberOptions)`, a list of `TooltipLine`s) or sent over the network. Nodes are deduplicated/interned per registry/client through `TooltipNodePalette.getOrCreate(...)` and referenced by integer id when encoded. This is why every `*Node` class (e.g. `PlacedFeatureNode`, `BlockNode`) stores a `TooltipNode` (or its id) rather than a raw `Component`, and why they all share the same dual-constructor shape: a server constructor that builds the tree, and a client constructor (`IClientUtils utils, FriendlyByteBuf buf`) that reads node ids back out of the palette.
- Which palette a build writes into is **ambient**, held in a `TooltipContext` `ThreadLocal`: `TooltipBuilder.build()` and `TooltipNode.empty()` resolve it through `TooltipContext.getPalette()`. Each mod brackets its whole server-side scan (`AbstractServer.readLootTables` / `readWorldgenInfo`) with `TooltipContext.setPalette(serverRegistry.getTooltipCache())` and a `finally`-clause `clearPalette()`, and each mod's `TooltipTestSuite` binds it once in `@BeforeSuite`. Anything that builds a tooltip outside such a bracket throws `IllegalStateException` naming the fix, rather than writing into another mod's palette. This is why the palette is not reachable from a static singleton: ALI and AWI load one shared copy of `aci`, so a static field on `CorePluginManager` would be one field for both mods and whichever registered last would win.
- Both `TooltipContext` ThreadLocals (the current loot table and the current palette) are therefore shared between ALI and AWI at runtime. That is safe only because the two scans run sequentially on the server thread and each brackets its own region — never leave either one set across a mod boundary.
- On the wire, the full deduplicated `TooltipNodePalette` is sent **upfront**, once per full sync (not lazily/per-request): each mod's `AbstractServer` data-build method calls `serverRegistry.getTooltipCache().encode(serverRegistry, buf)` as the very first thing written into the raw buffer, before any loot/trade/worldgen node tree. Client-side, `TooltipNodePalette.decode` reads that header first and rebuilds `idToNode` before any dependent node reconstruction resolves children by id lookup.

### Tooltip colors

Rendering colors live in the `TooltipStyle` record (`text`, `value`, `error`, `branch`, `secondary` as `Style`s, plus `levels`, the RGB colors of level rows and their chart panels, cycled by `level(index)`) and are applied at render time only — nothing style-related is part of `CacheKey`, of the palette's deduplication, or of the wire format, so color is a purely client-side decision. `TooltipNode.getLines`/`CoreTooltipUtils.toLines` take the style next to the `NumberOptions`; `TooltipStyle.DEFAULT` is gold/aqua/red/dark_gray/gray. `secondary` colors what follows a number (`~`, chart labels).

Each mod resolves its **own** style from its **own** config through `plugin/client/TooltipUtils.getStyle()` and passes it into `CoreTooltipUtils.toLines` at the call site, together with `TooltipUtils.getNumberOptions()`. A static style field on an ACI class would be wrong for the same reason the palette is not a static singleton: ALI and AWI share one loaded copy of `aci`, so whichever mod wrote last would win. The config is read once at `CoreCommonRegistry` construction, so a color change needs a restart.

### Two dispatch tiers

Every mod's `IServerRegistry`/`IServerUtils` (each extends ACI's generic `ICoreServerRegistry<TServerUtils>` / `ICoreServerUtils<SELF>`) exposes tooltip lookup through two distinct mechanisms — don't conflate them:

1. **Generic value dispatch** — `registerValueTooltip(Class<T>, BiFunction<TServerUtils, T, TooltipBuilder>)` / `getValueTooltip(utils, value)`. Backed by `ClassKeyedMap` (`aci.manager`), which walks superclasses/interfaces to find the closest registered supertype, so registering `Collection.class` or `Enum.class` once covers every concrete subtype. `new CommonValueTooltip<TServerUtils, TServerRegistry>().registerAll(registry)` — called once at the top of each mod's `Plugin.registerServer` — pre-registers this tier for common JDK/Minecraft types (`Boolean`, `Enum`, `Collection`, `Optional`, `Holder`, `ResourceLocation`, `NumberExpr` as a number node, ...). Each mod then layers its own domain value types on top (e.g. AWI adds `Block`, `Fluid`, `BlockState`, `Vec3i`; ALI adds its own loot-specific value types).
2. **Domain-specific category dispatch** — one `register<Category>Tooltip(Class<T>, BiFunction)` / `get<Category>Tooltip(utils, entry)` pair per category (AWI: `PlacementModifier`, `HeightProvider`, `BlockPredicate`, `IntProvider`, `RuleTest`, `FeatureConfiguration`; ALI: `LootItemFunction`, `LootItemCondition`, `Ingredient`, ...). Each category is its own `ManagedRegistry<Class<?>, BiFunction<...>>` field on the mod's `<Mod>ServerRegistry` (e.g. `AwiServerRegistry`, `AliServerRegistry`), created via `registerClassKeyed(label, reportMissing, HashMap::new, vanillaRegistry)`. This tier is **exact-class-keyed** (plain `HashMap`, no supertype walking) because every concrete implementation in these categories corresponds 1:1 with an entry in a vanilla `Registry` (`BuiltInRegistries.PLACEMENT_MODIFIER_TYPE`, `..._TYPE`, ...) — there's no polymorphism to resolve.

Both tiers follow the same three-part convention per registered type: a builder method (e.g. `PlacementModifierTooltipUtils.getHeightmapPlacementTooltip`), a `register...` call wiring it to its concrete class in `Plugin.registerServer`, and a shared `Missing...TooltipUtils` fallback for anything not registered.

### Missing-entry fallback and coverage reporting

`get<Category>Tooltip` always resolves through `.get(entry.getClass()).map(...).orElseGet(missingFallback)`. The fallback (`MissingTooltipUtils`) re-serializes the object through its own `Codec` (`RegistryOps` + `JsonOps`) and dumps the raw JSON under an "Auto-detected" key, so an unregistered type still shows *something* useful instead of nothing. Separately, `ManagedRegistry` (constructed with `reportMissing = true`) records every class that missed lookup; `printRuntimeInfo()` (called server-side after data collection, see each mod's `network/AbstractServer`) logs each miss, and `printRegistrationInfo()` (called from `CorePluginManager` at startup) logs `registered/total` counts against the backing vanilla registry — check these logs to find categories/types still missing a builder.

Some types are deliberately registered to return `TooltipBuilder.empty()` (e.g. AWI's `BiomeFilter`, `InSquarePlacement`) rather than left unregistered — do this when a type carries no information useful to the end user. Leaving it unregistered instead falls through to the JSON-dump fallback, which is noisy for something intentionally uninteresting.

### Adding a new category

1. Declare a `ManagedRegistry` field on `<Mod>ServerRegistry` via `registerClassKeyed(...)`, backed by the relevant vanilla `Registry` if one exists.
2. Add `register<Category>Tooltip`/`get<Category>Tooltip` to `I<Mod>ServerRegistry`/`I<Mod>ServerUtils` and implement them on `<Mod>ServerRegistry`.
3. Add a `Missing<Category>TooltipUtils` fallback (copy the codec-dump pattern from an existing one).
4. Write one builder method per concrete type in a `<Category>TooltipUtils` class, and wire each with `registry.register<Category>Tooltip(SomeType.class, ...)` in `Plugin.registerServer`.
5. Add any new leaf/branch `Lang` keys the new builders need (see below).

### Language wiring

Tooltip keys are `IMultiKey`/`ITooltipKey` enum constants (each mod's `language.Lang`, e.g. `Lang.Value`, `Lang.Branch`, one enum per semantic grouping) carrying a singular/plural key plus English fallback text (`Translation` record). `CoreLang.register(translationMap, SomeEnum.class)` — called once per enum, from `<mod>.datagen.LanguageHolder`'s static initializer — merges those into the **caller's** map, which both feeds that mod's datagen-generated `en_us.json` and gets registered into the per-node translation-key index (`Plugin.registerCommon` → `registry.registerTranslationKey`). That index lets `TooltipNode.encode` send a compact varint key index over the network instead of the full string (`FLAG_INDEX_KEY`). Forgetting to route a new `Lang` enum through `CoreLang.register` in `LanguageHolder` means its keys compile and even display server-side, but the client shows raw untranslated keys and lang datagen won't include them.

Each mod owns exactly its own keys: `CoreLang.TRANSLATION_MAP` holds only ACI's own keys (`CoreLang.Utils` → `aci.util.*`, `CoreLang.Spawn` → `aci.spawn.*`, `CoreLang.Numbers` → `aci.number.*`, and `aci.enum.mob_category.*` for the spawn category `SpawnInfo` shows, a modded `MobCategory` without a key falling back to its name), and `aci.datagen.LanguageHolder` copies it for ACI's own lang datagen. Those strings therefore reach the client from ACI's resource pack (`assets/aci/lang/en_us.json`, generated per loader; `zh_cn.json` and `es_ar.json` are hand-written in `aci/common`), not from ALI's or AWI's — a missing ACI jar shows up as raw `aci.*` keys in the tooltip, not as a crash. Never take the map as a shared scratchpad to route a mod's keys through; that is exactly what the `translationMap` parameter exists to prevent.

## Number model

`api.NumberExpr` describes a value (a count, a chance, a height) instead of only bounding it, so the client can show its shape: the range, the most likely value (`~`) and, on request, the formula.

- **Generic nodes, registered functions.** The node kinds are fixed and domain-free; everything that computes — `+ − × ÷`, `clamp`, `round`, `uniform_int`, `binomial`, … — is an `Fn(id, args)` whose meaning comes from the `NumberFunction` registered under that `ResourceLocation` in `NumberFunctions`. ACI registers its `aci:` functions itself (`BuiltinFunctions`, from the registry's static initializer); a mod adds its own through `NumberFunctions.register`, from code that runs on both sides (`registerCommon`), usually built with `NumberFunction.builder(id)`. A second definition under a taken id is logged and ignored (the first one stays), so one mod's mistake cannot abort the rest of its `registerCommon`; re-registering the same instance is a no-op.
- **The registry is a static global on purpose.** `bounds()`/`mode()` take no utils and the client re-evaluates expressions (level rows), so the definition must be reachable from the expression alone. It holds stateless definitions keyed by namespaced ids, so ALI and AWI sharing one copy of ACI cannot collide the way mod-bound state would (see "Tree model" for why that state is never static).
- **Defining a function.** Semantics come one of two ways. A *macro* gives `expand(args)` into other nodes; bounds, distribution and folding are derived from the expansion while formulas keep the function's name — the way to add a distribution that is a composition of existing ones (the vanilla biased/trapezoid families are nested uniforms). A *primitive* gives `evaluate` (constant folding, `bind`), `bounds` over `NumberInterval` and `distribution` over `NumberDistribution`; `distributionOfParameters` needs the distribution only for constant parameters, and random discrete parameters are then mixed by `NumberDistribution.ofParameters`. Anything left undefined degrades: no `evaluate` means no folding, no `bounds` means `?`, no `distribution` means no `~`. Formatting is infix/prefix (`infix`), custom (`format`) or `name(a; b)`, with per-argument units (`SAME`, `PLAIN`, `PERCENT`) deciding whether a percent context carries into an argument.
- **Unknown on the client.** The wire form of `Fn` is only its id and arguments, so an expression decodes even when the client lacks the definition; such a node has unknown bounds, no distribution and renders as `? (id)`, like `Opaque`. `Opaque` stays a separate node for an unconverted *source* type, so its type id can never be mistaken for a function id.
- **Factories simplify.** `NumberExpr.fn` (and the shortcuts `add`, `mul`, `clamp`, `uniformInt`, …) checks arity, folds all-constant arguments through `evaluate`, applies the function's `simplify` (`add`/`mul` flatten, drop `+ 0`/`× 1`, turn `× 0` into `0` and keep a folded constant where the first one stood; `uniform_*` with equal bounds collapse) and folds a macro whose expansion is constant. `transform` (and so `bind`) rebuilds through `fn`. `NumberExpr.cond` flattens a `Cond` whose `otherwise` is another `Cond` into one branch list, outer branches first, so chained conditional functions render one row per condition. Construct nodes through the factories, not the record constructors, or formulas carry `1 ×` and `+ 0`.
- **Variables.** `Var(type, args, min, max)`: `args` are `NumberText` label arguments, `[min; max]` is the domain `bounds()` assumes while the variable is unbound. An enchantment level is `NumberExpr.level(enchantmentId, maxLevel)` — type `aci:level`, `args[0]` the enchantment id, `max` the highest level a row is shown for. A variable whose domain is finite is *stepped*: every integer of its domain except 0 gets a row, and the node's own line shows the variable at 0 when the domain contains 0, its whole range otherwise (see "Rendering"). `aci:level`, luck and ALI's `ali:enchantment_level` (`1 … max`) are stepped, a score (unbounded) is not.
- **Translation keys** are derived from ids: `<namespace>.number.fn.<path>` for a function's name, `<namespace>.number.var.<path>` (formula) and `<path>.desc` (range text) for a variable type, plus `<path>.row` (positive values) and `<path>.row.negative` (negative ones) for the row name of a stepped variable other than `aci:level` (which is named after its enchantment), each taking the absolute value as its first argument before the variable's own — `aci:level` has no `.desc` and no `.row`. ACI's own live in `CoreLang.Numbers`; an extension ships its keys in its own lang files.
- **`bounds()`** is interval arithmetic that tracks open ends (`trunc(U[0; 3))` is `0 … 2`); `NumberInterval.UNKNOWN` (NaN ends) propagates from `Opaque` and unknown functions. A consumer's implicit limit (max stack) is not part of the expression — it is passed to `NumberFormatter.format(..., limit)` and applied to both the range and `~`.
- **`mode()`** comes from the expression's `NumberDistribution`: atoms plus at most one continuous part given by its CDF (`Density`: `cdf` is the part's mass in `(-∞; x]`, `peakDensity` is `NaN` when the peak is unknown). Sums, clamps, affine maps and rounding of such a part stay exact; anything else — an unbound variable, `Range`, `Opaque`, `Cond`, two continuous summands, more than `MAX_ATOMS` (1024) values — yields no distribution and therefore no `~`. Probabilities within a relative `1e-6` count as equal: all-equal (uniform, constant) gives no `~`, a contiguous run of equal maxima gives a band, a non-contiguous one gives none. `NumberMode.probability` is always the probability of one value, never the band's total, so `~` reads the same for a band as for a single value. A continuous peak is shown without a probability; a clamp atom wins over it when its probability exceeds the peak density per unit.
- **Formatting** (`NumberFormatter`) returns `NumberText`, never finished strings, so it is testable without Minecraft and the client decides locale and colors. `format(expr, showFormula, percent)` gives the range text (with the labels of non-level variables, opaque type ids and unknown function ids) or, when `showFormula` and not `isSimple()`, the formula; `mode` is formatted separately. Numbers are rendered through `NumberText.formatNumber` (two decimals at most, client locale, `−` for negatives). `slot(bounds)` is the one plain-string form, for the 50 % slot overlay: `a-b` over integer ends (open ends stepped inward), a single value, or `?` when unknown or unbounded. `slotBounds(expr)` is the `bounds()` a slot overlay reads it from: a throwing function gives `UNKNOWN` (logged) instead of reaching the widget.
- **Number nodes in the tooltip tree.** `TooltipBuilder.number(expr[, percent, limit])`/`percent(expr)` put a `TooltipNumber` (expression, percent flag, optional consumer limit) into a node under `FLAG_NUMBER`. It is part of `CacheKey`, so equal expressions share one palette node, and it travels as the expression itself (`TooltipNumber.encode`) — a wire-format change. Text is made only on the client, in the client's locale (`NumberOptions.client(showCharts)`, which takes `showFormulas` from vanilla advanced tooltips, F3+H; tests use `NumberOptions.DEFAULT`, `Locale.ROOT`).
- **Interval lists.** `TooltipBuilder.intervals(list, values...)` puts plain `NumberInterval`s into a node under `FLAG_INTERVALS` (part of `CacheKey`, sent as the intervals themselves). The client formats each through `NumberFormatter.interval` in its locale and joins them with `, `; that text is the first format argument of the node's key, any `values` follow it. It is for lists of already-known ranges (AWI's base-layout heights), where a `NumberExpr` per entry would be overkill.
- **Rendering** (`NumberView`, cached per node and per `showFormulas`/`showCharts` combination; the locale and colors are applied on every call). The node's own line gets the value — range text, or the formula when `showFormulas` and not `isSimple()` — with every stepped variable whose domain contains 0 bound to 0, followed by `~` in `secondary`. Under it:
  - one row per value `min … max` of every stepped variable, 0 excepted when the domain contains it (the other stepped variables bound to 0 where their domain contains it), preceded by a formula row when `showFormulas`; an `aci:level` row is the enchantment name `enchantment.<ns>.<path>` with `enchantment.level.<n>` (`LVL` on the formula row, joined by `LEVEL_ROW`), any other one the variable's `.row`/`.row.negative` key (its formula key on the formula row, joined by `VAR_ROW`);
  - a top-level `Cond` leaves the node's own value empty and gets one row per branch, every row after the first and the `otherwise` row prefixed by `CoreLang.Numbers.OTHERWISE`, since the first matching branch wins; the branch's condition is the node's **child** at index `Branch.condition`, rendered under that row and skipped among the ordinary children (an out-of-range index is ignored). `TooltipBuilder.add` drops empty children, so a producer counts indices over the conditions it actually added;
  - a top-level `Weighted` keeps the combined range and `~` on its own line (always text) and gets one `value (p %)` row per entry;
  - with `showCharts`, a chart row (`TooltipLine.Chart`) when the value or any level row has a `~`: one panel per series — the base distribution in gray (absent when a stepped variable stays unbound on the node's own line, since that line then has no distribution), every level row in the color its label is drawn in — on shared columns and a shared height scale; a series whose support is a single value or a single column gets no panel and takes no part in the columns or the height scale, and no panel left means no chart. Each panel marks its most likely columns: the `~` value or band, or, when `mode()` has none, every column tied at the maximum unless all are equal; the base draws them light gray, a level at full color and its other columns at 80 %. `Cond` gets none, `Weighted` no level overlay.
- **Failure containment.** A converter that throws, or a type with no converter, yields `Opaque(typeId)` (`manager.NumberConverters.convert`, logged under the mod id); a number that fails to render shows `?` in the error color and is logged once, since the failed view is cached like a good one. Neither reaches the scan or the GUI.
- **Value-provider converters.** `registerIntProvider`/`registerFloatProvider` on `ICoreServerRegistry` and `convertIntProvider`/`convertFloatProvider` on `ICoreServerUtils`, exact-class keyed and reported against `INT_PROVIDER_TYPE`/`FLOAT_PROVIDER_TYPE`. The vanilla ones are `tooltip.CommonNumberProviders`, registered by a mod calling its `registerAll(registry)` in `registerServer`, like `CommonValueTooltip`; nested providers (`ClampedInt`, `WeightedListInt`) recurse through `utils.convert*`, so a modded provider inside a vanilla wrapper still reaches its own converter. Every converter is a `NumberConverter` `(utils, value, conditions) → NumberExpr`: one that yields a `Cond` appends each condition's tooltip to `conditions` and puts its index into the `Branch`, nested conversions get the same list, and the caller that builds the number node attaches the list as the node's children (`TooltipBuilder.number(expr, conditions)`). The list is a parameter, not state on `utils`, so no conversion can lose its conditions by running outside a collector.
- **Access widener.** Those converters read private vanilla fields, so ACI ships `aci.accesswidener` (wired as in ALI, see `aci/fabric/CLAUDE.md`, `aci/forge/CLAUDE.md`, `aci/neoforge/CLAUDE.md`). Loom does not carry an access widener across a `namedElements` project dependency, not even with `transitive-accessible`, so ALI's and AWI's tests run against a Minecraft opened only by their own file: every `aci.accesswidener` member ACI code touches in an ALI or AWI test must be listed in `ali.accesswidener`/`awi.accesswidener` too. Production jars are unaffected.

## Tests

`aci/common/src/test` (`./gradlew :aci:common:test`) holds `CoreTestSuite`, the suite for the mod-agnostic machinery. **Anything shared by both mods belongs here, tested once, instead of being asserted twice in ALI's and AWI's suites.** Unlike those two it needs no resource-pack/language/registry-lookup setup, so keep it that way: test against stand-ins like `TestConfig` (a minimal `ICoreConfig` holding no registry-backed content) rather than pulling in `Items`/`Blocks`. `NodeCodecTest` does call `Bootstrap.bootStrap()` in its own `@BeforeAll`, because `TooltipNode` encoding goes through `ComponentSerialization`, whose static init needs the registries.

`test/utils` also holds the **shared test utilities both mods use** — `TestUtils` (tooltip/`Component` assertions incl. `assertUnorderedTooltip`, `componentToPlainString`, `bindVanillaTags`, `loadDefaultLanguage`) plus the `Test*Node`/`Test*Utils` stand-ins `NodeCodecTest` builds its trees from. ALI and AWI import them from `com.yanny.aci.test.utils.*` rather than keeping copies. `loadDefaultLanguage` takes the mod's `LanguageHolder.TRANSLATION_MAP` as an argument and returns a `LoadedLanguage(language, unusedKeys)` — the second half is the unused-lang-key audit both suites log in their `@AfterSuite`. It layers `CoreLang.TRANSLATION_MAP` in *under* the mod's map, standing in for ACI's resource pack, and deliberately keeps those keys out of `unusedKeys` — otherwise an `aci.util.*` key that one mod happens not to use would read as an unused key of that mod. These are on the mods' test classpath through a test jar: `aci/common/build.gradle` publishes `sourceSets.test.output` under the `testArtifacts` configuration, and each mod declares `testImplementation project(path: ":aci:common", configuration: "testArtifacts")`. Note that these utilities do touch Minecraft — that is fine, they are only *compiled* into `CoreTestSuite`'s module.

Currently: `CoreConfigUtilsTest` covers the whole config lifecycle — create-from-defaults, don't rewrite an existing file, load custom values, missing fields falling back to codec defaults, `.bak` rotation of an outdated file (including replacing an older `.bak`), recreation from an empty or malformed file, and the two give-up paths (`null` config dir, a config dir that cannot be created). ALI's and AWI's own `ConfigTest` keep only what is theirs: the golden `<mod>_common.json` comparison, their default-value behaviour, and their own custom values. `NodeCodecTest` covers the encode/compress/chunk/reassemble/decode round trip of `CoreListNode` + `NetworkUtils` + `DataReceiver`. `NumberExprTest` covers the number model: the worked examples in both formatting modes, `bounds()` edge cases, round-trip encoding, locale formatting, and the extension mechanism — it registers `test:` functions (macros for the height and 26.3 biased/trapezoid families, checked against sampling with the vanilla algorithms, and two primitives), plus an unregistered function and a duplicate registration. `NumberTooltipTest` covers the number nodes: round trip and palette deduplication, level and `LVL` rows, the consumer limit, `Cond`/`Weighted` rows, the chart data, and both failure paths (a throwing converter, a number that fails to render).

### Reference implementations

`aci` defines the mechanism once; `ali/common/.../manager/AliServerRegistry.java` and `awi/common/.../manager/AwiServerRegistry.java` are its two concrete instantiations, and `ali/common/.../plugin/Plugin.java` / `awi/common/.../plugin/Plugin.java` are where every category and value type actually gets wired up (see `ali/CLAUDE.md` and `awi/CLAUDE.md`). When adding tooltip coverage for a new Minecraft type, check the sibling mod's registry/`Plugin.java` for established category-naming and builder-file conventions before inventing new ones.
