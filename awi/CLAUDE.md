# awi/CLAUDE.md

Guidance for working on **AWI** (`AdvancedWorldgenInfo`, `com.yanny.awi`) — the recipe-viewer plugin that displays worldgen information (placed features, placement modifiers, height providers, block predicates, biome surface blocks, ...). See the repo-root `CLAUDE.md` for the multi-mod monorepo layout, and `aci/CLAUDE.md` for the shared tooltip/plugin-manager mechanism this mod instantiates (read that first — this doc assumes it). AWI's architecture mirrors ALI's almost 1:1 at the plugin/registry/network layer — where it does, this doc says so and points at `ali/CLAUDE.md` instead of restating.

## Module layout

- `awi/common` — platform-agnostic mod logic, covered by this file.
- `awi/common-emi`, `awi/common-jei`, `awi/common-rei` — recipe-viewer integrations. See `awi/common-emi/CLAUDE.md`, `awi/common-jei/CLAUDE.md`, `awi/common-rei/CLAUDE.md` (all reference `ali/common-emi/CLAUDE.md` for the shared pattern).
- `awi/fabric` — Fabric loader module. See `awi/fabric/CLAUDE.md`.
- `awi/forge` — Forge loader module (enabled via `forge_enabled`). See `awi/forge/CLAUDE.md`.
- `awi/neoforge` — NeoForge loader module (enabled via `neoforge_enabled`). See `awi/neoforge/CLAUDE.md`.

AWI has no `common-lootjs` equivalent, and its `configuration` package is minimal compared to ALI's: `AwiConfig` (`configVersion`, `logMoreStatistics`, `showInGameNames`) plus `ConfigUtils`, written to `<config>/awi/awi_common.json`. The read/version-rotate/re-create logic is no longer copy-pasted from ALI — both go through `aci.configuration.CoreConfigUtils` and `AwiConfig` implements `aci.configuration.ICoreConfig` (see `aci/CLAUDE.md`); AWI's `ConfigUtils` is just that call with `AwiConfig.CODEC` and plain `JsonOps.INSTANCE`, since nothing in it is registry-backed. There are no loot-category-style filters to configure, since worldgen registries are enumerated exhaustively rather than matched against user-declared categories (contrast with ALI's `ali_config.schema.json`-driven filtering).

## `awi/common` package map (`com.yanny.awi`)

### Root
`Utils.java` — mod-id constant + `modLoc(String)` `ResourceLocation` helper, used for every node ID.

### `api`
Mirrors ALI's `api` package, specialized to worldgen value types: `IPlugin`, `@AwiEntrypoint` — plugin registration entrypoints. `ICommonRegistry`/`ICommonUtils`, `IClientRegistry`/`IClientUtils`/`IWidgetUtils`, `IServerRegistry`/`IServerUtils` — thin extensions of `aci`'s generic `ICoreXxx<...>` interfaces, adding AWI-specific registration methods (see `plugin/Plugin.java` below). `IDataNode` (extends `aci.api.ICoreDataNode<IServerUtils>`), `ListNode` (abstract, extends `aci.api.CoreListNode`) — the recursive server-built/client-synced tree node base, now only the two constructors; the encode itself (child count + per-child id/payload, tolerating per-node encode failures) lives in `CoreListNode` and is shared with ALI — see `aci/CLAUDE.md`. `IBlockNode` (`getBlock()`/`getBlocks()`/`retainBlocks()`/`getChance()`, implemented by `BlockNode` — see the tag pipeline under `plugin/server`). `FeatureHolder` (record: items + conditions tooltip), `ListWidget`.

### `manager`
Mirrors ALI's `manager` package exactly in shape:
- `PluginManager extends CorePluginManager<...>` — singleton, wires `AwiCommonRegistry`/`AwiClientRegistry`/`AwiServerRegistry`, plugins sourced from `Services.getPlatform().getPlugins()`.
- `AwiServerRegistry` — holds ~22 `ManagedRegistry` maps in three groups (all created with `registerClassKeyed`, most backed by the matching `BuiltInRegistries.*_TYPE` so `printRegistrationInfo` can report coverage):
  - **block collectors** (`List<Block>` results): feature config, block-state provider, root placer, tree decorator.
  - **tooltip categories** (`TooltipBuilder` results): feature config, placement modifier, int provider, float provider, rule test, height provider, block predicate, block-state provider, tree decorator, feature size, root placer, foliage placer, trunk placer, structure processor, plus the `ClassKeyedMap`-backed generic "value" tier (`aci/CLAUDE.md`'s tier 1).
  - **placement-summary propagators**: int span, height span, placement (see `plugin/server/summary` below).

  Falls back to `MissingTooltipUtils` when a class has no registered handler (see `aci/CLAUDE.md`'s "Missing-entry fallback" section). When adding a category, this list plus `IServerRegistry`/`IServerUtils` are what need touching — see `aci/CLAUDE.md`'s "Adding a new category".
- `AwiClientRegistry` — client-side counterpart holding decoded `IDataNode`s.

### `plugin/Plugin.java` — the `@AwiEntrypoint`
`registerServer` is one long wiring block; the call counts are the quickest map of where AWI's coverage actually sits: 55 `registerValueTooltip` (generic tier — `IntProvider`, `RuleTest`, `HeightProvider`, `BlockPredicate`, `OreConfiguration.TargetBlockState`, `BlockState`, `Vec3i`, registry-keyed `Block`/`Fluid`/`*Type` lookups, ...), 37 `registerFeatureTooltip` + 37 `registerFeatureBlockCollector` (one pair per `FeatureConfiguration` subclass), 16 `registerPlacementModifierTooltip`, 13 `registerBlockPredicateTooltip`, 11 each `registerStructureProcessorTooltip`/`registerFoliagePlacerTooltip`, 9 `registerTrunkPlacerTooltip`, 9 `registerPlacementPropagator`, 7 each `registerStateProviderBlockCollector`/`registerBlockStateProviderTooltip`, 6 each for tree-decorator tooltips/collectors, rule tests, int providers, height providers, `registerIntSpanPropagator`, `registerHeightSpanPropagator`, 4 `registerFloatProviderTooltip`, 2 `registerFeatureSizeTooltip`, 1 each root-placer tooltip/collector. `registerClient` registers 6 widget + 6 data-node factory pairs; `registerCommon` registers translation keys and calls `new CommonValueTooltip<>().registerAll(registry)`.

**Important**: there are no surface-rule, structure, carver, or noise-settings *registrations* here — those aren't pluggable value types with a 1:1 vanilla registry, so they're not handled through the two-tier dispatch pattern at all. They're handled procedurally by `plugin/common/nodes.NodeUtils` (below), which is why you won't find a `SurfaceRules.RuleSource` category anywhere in `Plugin.java`. Structure *processors* are the near-miss to keep straight: `StructureProcessor` does have a vanilla registry and is registered normally (11 tooltips) — it's whole structures that aren't.

### `plugin/common/nodes` — the AWI data-scan engine
Server-side tree construction; each class doubles as codec (server constructor + `IClientUtils`/`FriendlyByteBuf` decode constructor + `encodeNode`, per `aci/CLAUDE.md`'s dual-constructor convention).

- `LevelStemNode` (entry-level node) — one per dimension; iterates the generator's `possibleBiomes()` and builds a `BiomeNode` per biome. It does **not** scan anything itself: the base blocks are handed to it as a pre-computed `Map<Holder<Biome>, NodeUtils.LayerHolder>` (empty for non-noise generators).
- **`BaseLayoutScanner`** — runs `NodeUtils.getBaseBlocksForBiome` for every (dimension, biome) pair of the world *up front*, on one shared pool, before any node is built. One pool for all dimensions rather than one per dimension, so workers stay busy across dimension boundaries; tasks are ordered by dimension and each worker keeps the `DimensionContext` of the dimension it last worked on (`ContextCache`), which bounds both `RandomState.create` calls and the memory the mock chunks hold. Results are cached per (noise settings, biome) — the scan's outcome depends only on the dimension's `NoiseGeneratorSettings`, the biome and the seed, so dimensions sharing settings scan each biome once. Also collects the `Stats` that `AbstractServer` logs (elapsed time, cache hits, min/max/mean per biome, and how many distinct surface rules the scanned dimensions use — that last one measures how much wider the cache key could be).
- `BiomeNode` → iterates `BiomeGenerationSettings.features()` per `GenerationStep.Decoration` → `GenerationStepNode` → `PlacedFeatureNode` (splits into `ConfiguredFeature`/`FeatureConfiguration` blocks via `utils.collectBlocks`, and `PlacementModifier` tooltips) → `BlockNode` (leaf).
- `BaseTerrainNode` — leaf list of blocks discovered by the surface-rule scanner below.
- **`SurfaceRuleSpecializer`** — rewrites a dimension's `SurfaceRules.RuleSource` into the subset that can fire for one biome; one instance per dimension, since the encode behind it is not free. The scan pins the biome for a whole `getBaseBlocksForBiome` call, yet every `minecraft:biome` condition is a `LazyYCondition` — invalidated on *every cell* — so each dead biome-gated branch costs a set lookup per cell, and a modded overworld carries hundreds of them (measured on Prominence II: 2394 → 146 nodes, 94% of the rule dead for any single biome).

  The rewrite goes through `SurfaceRules.RuleSource.CODEC` (serialize → prune JSON → deserialize) rather than over the object graph, because the node classes are package-private records whose field/method names remap in production while registry ids in the serialized form do not.

  **Unknown node types are descended into but never restructured.** Mods wrap the vanilla rule in their own rule type (Terrablender being the common one) and the branches worth pruning sit *inside* that wrapper — stopping at the first unrecognised node prunes nothing on exactly the packs that need it most. Inside an unknown node a dead branch is therefore replaced *in place* by an empty `minecraft:sequence` (a valid rule that never fires) instead of being removed, so arity and element order survive and it does not matter whether the wrapper indexes its children or pairs them with data of its own. Elements are only truly dropped inside a `minecraft:sequence`, whose semantics are known. An object carrying `"type": "minecraft:condition"` is always a `RuleSource` (that id belongs to the rule registry), so descending cannot misread a condition as one. Any failure — and any dimension whose first biome prunes nothing — falls back to the original rule and switches specialization off for that dimension.

- **`NodeUtils`** — the real worldgen-data-collection engine, and the single most distinctive piece of AWI's architecture: there is no `BuiltInRegistries.PLACED_FEATURE`-style enumeration for surface blocks (features come from a biome's own `BiomeGenerationSettings`, reached only through the per-dimension `LevelStem`→generator→biome path above). Instead, `DimensionContext` builds a mock `SurfaceRules.Context`/`ProtoChunk`/`NoiseChunk`, and `walkColumn` empirically **fires the biome's compiled `SurfaceRules.SurfaceRule` over synthetic canonical columns** (swept surface heights, spiral-sampled XZ, ceiling/overhang probes) to reverse-engineer which blocks the rule places — there is no vanilla API that just answers "what blocks can this biome's surface rule produce," so AWI empirically probes it. Each discovered block gets classified as RELATIVE/ABSOLUTE/LAYERED with water/floor-ceiling constraints.

  The sampling knobs live in `NodeUtils.ScanSettings` (`DEFAULT` is what production uses) so their cost/coverage trade stays measurable — see the test harness below before touching them. Two of them are not plain "more/less sampling" and interact with the classification, which is why changing them alone silently corrupts output:
  - `deepWalkWindow` bounds how far below the assumed surface a normal walk still evaluates, turning the walk's cost from quadratic in world height into linear. Every Y is still reached (the assumed surface sweeps the whole range), but it *censors the depth axis*, so `BlockObservation.classify` treats a block whose depths run into the window as unbounded-depth — without that guard deepslate/bedrock flip from `ABSOLUTE` to "1..window blocks below the surface".
  - `specializeRulePerBiome` recompiles the rule per biome with the branches that cannot fire for it removed (`SurfaceRuleSpecializer`). Semantics-preserving, so the golden file must stay byte-identical when it is toggled — it is a pure cost cut, worth 1.5× on vanilla and 2.8× on a heavily-modded overworld.
  - `extentStableRounds` is a second, weaker stop condition next to `stableRounds`: stop once nothing has *widened* the result (no new block, flag, or wider extent) for that many rounds, even while new interior positions keep turning up. Noise-banded rules (badlands) never stop producing those, so `stableRounds` alone never triggers for them and they always run to `maxRounds`. It must stay the weaker of the two rather than replace `stableRounds` — making the extent metric the only criterion forces every simple biome to sit through the longer window, which measured +60% on a real pack while looking free on vanilla.

  (An earlier abandoned attempt to instead *run* feature placement against mock `Fake*` level/chunk implementations was removed as a dead end — empirically running `Feature.place()` is unreliable because placement reads the surrounding world; see the ASM approach in `plugin/server` below.)

Feature-placed blocks come from two complementary sources, both in `plugin/server`: static config introspection (`FeatureConfigurationCollectorUtils`, covers blocks stored in the `FeatureConfiguration`) and, additively for blocks hardcoded inside `Feature.place()` bytecode (the ones absent from config), `FeatureBytecodeScanner` (below). Both are collected as `Either<Block, TagKey<Block>>` — see "The block-tag pipeline" below.

The two must be paired at **every** level of nesting, which is what `FeatureConfigurationCollectorUtils.collectConfiguredFeatureBlocks` is for — it is the only sanctioned way to descend into a nested `ConfiguredFeature`, and `PlacedFeatureNode` uses it for the top level too. Pairing them only at the top used to lose whole features: warm ocean's coral reaches the world exclusively as three `NoneFeatureConfiguration` features nested inside `warm_ocean_vegetation`'s `SimpleRandomFeatureConfiguration`, so the config side contributed nothing and the scanner only ever saw the outer `simple_random_selector`. Every nested descent (`RandomFeatureConfiguration`, `RandomBooleanFeatureConfiguration`, `RandomPatchConfiguration`, `RootSystemConfiguration`, `VegetationPatchConfiguration`, and the generic `getFeatures()` walk) now routes through it.

### `plugin/server`
Pure `IServerUtils`-based utility classes registered by `Plugin.java`, following the same one-static-method-per-Mojang-subtype convention as ALI — one class per category in `AwiServerRegistry`: `TooltipUtils`, `ValueTooltipUtils`, `RegistriesTooltipUtils` (registry-keyed name/id lookups via `CoreTooltipUtils.getBuiltInRegistryTooltip`), `FeatureConfigurationTooltipUtils`/`FeatureConfigurationCollectorUtils`, `PlacementModifierTooltipUtils`, `IntProviderTooltipUtils`, `FloatProviderTooltipUtils`, `HeightProviderTooltipUtils`, `BlockPredicateTooltipUtils`, `RuleTestTooltipUtils`, `BlockStateProviderTooltipUtils`/`BlockStateProviderCollectorUtils`, `TreeDecoratorTooltipUtils`/`TreeDecoratorCollectorUtils`, `RootPlacerTooltipUtils`/`RootPlacerCollectorUtils`, `FoliagePlacerTooltipUtils`, `TrunkPlacerTooltipUtils`, `FeatureSizeTooltipUtils`, `StructureProcessorTooltipUtils`, `PlacedFeatureUtils`, `MissingTooltipUtils` (fallback).

#### `plugin/server/summary` — the placement summary
The second distinctive piece of AWI (after `NodeUtils`): instead of only dumping each `PlacementModifier`'s own tooltip, this derives the three numbers a player actually wants per placed feature — **how many per chunk, with what chance, in which vertical band** — without running worldgen. `PlacementSummaryUtils.summarize` walks a feature's modifier list, asks the `placementPropagators` registry for each modifier's `PlacementContribution` (each modifier fills at most one of count/chance/height; first count wins, chances multiply), and merges them into a `PlacementSummary(CountSpan, chancePercent, HeightSpan)` that `appendSummary` writes as top-level un-headed tooltip lines. `CountSpan`/`HeightSpan` carry both a `RangeValue` and a `Kind` (distribution shape: `CONSTANT`, `UNIFORM`, `BIASED_TO_BOTTOM`, `TRAPEZOID`, `CLAMPED_NORMAL`, `WEIGHTED`, `RELATIVE_TO_HEIGHTMAP`, ...), plus `HeightSpan.bestBand` (the highest-probability Y interval, collapsing to the mode for peaked distributions) and `CountSpan.details` (the modifier's own tooltip, shown when the range is unknown — e.g. `NoiseBasedCountPlacement`). `ColumnContext(minY, height)` reimplements `VerticalAnchor.resolveY` without a world, so the whole path is world-free and unit-testable (`PlacementSummaryTest`). Adding a modded count/chance/height modifier means registering a `PlacementPropagator` (and, if it wraps a provider, an int/height span propagator) — not touching this orchestration.

`FeatureBytecodeScanner` is the exception to the "read the config" rule: a **static ASM data-flow analysis of `Feature.place()` bytecode** that recovers blocks hardcoded in a feature's placement logic (absent from its `FeatureConfiguration` — e.g. iceberg ice, monster-room spawner/chest, dripstone, kelp). It tracks only `BlockState`/`Block` values that flow into a placement sink (`LevelWriter#setBlock`/`Feature#setBlock`), so a block that is merely read or checked is not reported — but that is not the same as "no false positives", see the section below. It is deliberately **mapping-agnostic** — nothing is matched by method/field/class name (those remap in production); sinks and value types are identified via `Class` assignability and concrete blocks by reflectively reading the referenced static field. ASM (`org.ow2.asm`) is already on the classpath transitively via loom/fabric-loader. `PlacedFeatureNode` calls it additively alongside `utils.collectBlocks`. PoC-level: no inter-procedural receiver binding, limited tag-lookup resolution (documented in the class Javadoc).

A block reached through a `TagKey<Block>` is reported as the **tag**, not as its members: `ScanResult` carries `blocks` and `tags` side by side, and the walk never resolves a tag into its members (a tag bound to a parameter or to a lambda parameter travels as the tag — that propagation is what keeps the coral features working, since their block reaches the sink as a lambda parameter). Nothing on the server expands it; see the tag pipeline below.

The backwards walk from a sink crosses seven hops, each added because a real vanilla feature needed it — without them only a block written inline in the `setBlock` argument is ever seen. **Local variables** back to their stores (`throughLocal`; `SourceInterpreter` treats a load as its own producer, so `BlockState state = ...; setBlock(pos, state, 2)` otherwise resolves to nothing — this is why seagrass/kelp were missing). **Method parameters** back to their call sites (`bindArguments` records what each call passes per parameter, `addParameterCandidates` materializes it only when that parameter actually reaches a sink, so a block merely handed to a predicate is never collected). **`CHECKCAST` plus the receiver and block-carrying arguments** of the producing call — this is what reaches a `TagKey` through an `Optional` chain (`BLOCK.getTag(BlockTags.CORAL_BLOCKS)`, the coral features). **Lambda/method-reference bodies** via the `INVOKEDYNAMIC` bootstrap handle (`UnderwaterMagmaFeature`'s `forEach` is why magma was missing).

A lambda's **own parameters** are bound two independent ways, because vanilla hands lambdas around in two shapes:
- From the **receiver** of the call the lambda is handed to (`bindLambdaParameters`) — `getTag(BlockTags.CORALS)...ifPresent(block -> setBlock(pos, block.defaultBlockState(), 2))` places a value that has no producer in the enclosing method at all.
- From the **callee's own use of the lambda** (`recordFunctionalArguments` records which lambda a call site put in which parameter; `bindFunctionalCandidates` binds it when the callee invokes that parameter). This is dripstone: `DripstoneUtils.growPointedDripstone` hands `state -> level.setBlock(pos, state, 2)` to the *static* `buildBaseToTipColumn`, so the receiver hop returns immediately (`INVOKESTATIC`) and the value only exists inside the callee's `consumer.accept(...)`. The binding is **positional** and deliberately **not** filtered by `carriesBlocks` on the call's own argument types — a functional interface's descriptor is erased, so `Consumer#accept` declares `Object`; the lambda body's parameter type is what decides.

**Return values** of called helpers are resolved from their `ARETURN`s (`resolveReturnValue`/`returnedCandidates`, memoized per method). `DripstoneUtils.createPointedDripstone(direction, thickness)` is the shape that needs it: a static factory whose entire input is enum values, so neither the receiver nor the argument hop sees anything and `pointed_dripstone` is invisible without reading the callee.

Calls whose owner is a `BlockGetter` are **excluded** from that hop, and the exclusion is load-bearing rather than an optimization: a feature that writes back a state it read (`setBlock(pos, level.getBlockState(other), 2)`) would otherwise report the sentinels a reader answers with out of bounds — `ProtoChunk#getBlockState` returns `VOID_AIR`, which is how `fossil` and `end_gateway` first picked up `void_air`.

**`final` instance fields** are resolved from the `PUTFIELD`s in their owner's constructors (`addInstanceFieldValue`). `GETFIELD` has no value to read reflectively — `scan` is handed a `Class`, never an instance — so `DesertWellFeature`, which caches sand/sandstone/sandstone-slab/water in fields, reached its sinks carrying nothing. Restricted to `final` fields on purpose: anything reassignable makes the constructor's value a guess. Modded features cache blocks in fields far more often than vanilla does (vanilla's only case is `DesertWellFeature`).

Method lookup **walks the hierarchy both ways**. Up, because `place()` is often declared on an abstract base (`CoralFeature`, `AbstractHugeMushroomFeature`) — without it those features analyzed zero methods and silently returned nothing. Down, because that base then calls back into an abstract method the subclass implements (`CoralFeature#place` → abstract `placeFeature`); stopping at the abstract declaration cost coral every block below it (21 vs 5 per feature). The downward dispatch deliberately targets only the class being scanned, since that is the receiver of a feature's self-call.

An abstract call that is *not* such a self-call is dispatched to the classes of **registered blocks** implementing it (`queueImplementors`). Sculk is the case: a patch spreads through `SculkSpreader`, which calls `SculkBehaviour#attemptSpreadVein` on whatever block it found in the world, so no static receiver type leads to the placing code. The block registry is the only implementor index available, and `MAX_IMPLEMENTORS` is what keeps it from blowing up — a method declared on a wide base type (`BlockBehaviour`) resolves to hundreds of classes and is dropped rather than dispatched. This is the **one place the scanner reads a registry**; the `Either<Block, TagKey<Block>>` output still never expands a tag. Implementors that are not registered blocks (an inner class, an anonymous `SculkBehaviour.DEFAULT`) stay out of reach — which is exactly why `sculk_patch` reports the sculk and sensors it grows but **not** `sculk_vein`: veins go through `MultifaceSpreader.SpreadConfig#getStateForPlacement`, implemented by inner classes only. Reaching those needs a classpath-wide implementor index, which is a different mechanism with real blow-up risk, not an extension of this one.

`MAX_METHODS` is sized against all of that: a runaway guard at ~2× vanilla's widest feature (`fossil`, 427 methods), not a tuning knob — lowering it silently drops blocks rather than failing.

#### Config-conditional blocks

The scan is keyed by `Feature` *class*, so it cannot know which `FeatureConfiguration` it is being asked about and reports every branch. A block whose every placement is reached only through a test on the configuration therefore shows up for configurations that never place it — `LakeFeature`'s `ICE` is only placed when `configuration.fluid()` yields water (`LakeFeature:59` + `:132`), and 1.20.1 ships a single lake, `lake_lava`, so it is wrong for every vanilla lake.

`ScanResult.configConditionalBlocks` is that subset, computed by `configGuardedInstructions`: control dependence per conditional jump (what is reachable from one successor but not the other only runs when that branch was taken), plus interprocedural propagation of how each method was reached. `collectConfiguredFeatureBlocks` drops it unless `AwiConfig.showConfigConditionalBlocks` says otherwise. Dropping it there, not in the widget, also keeps those blocks out of the reverse index — a block that is not shown is not searchable either.

**A config-derived condition is deliberately not enough** (`isConfigSelectiveTest`), and this is the part to understand before touching it. `l < configuration.tries()` and `for (Spike spike : configuration.spikes())` are config-derived too, yet always run — and a feature's whole body typically sits inside one, so counting them marked 8 of 61 features, including `underwater_magma`'s own magma and `end_spike`'s obsidian. Only an **identity test** on a config-derived block, state or fluid (`is(Block)`, `is(TagKey)`) is counted, which is the shape that actually selects. With that narrowing the flagged set across all 61 vanilla features is exactly `lake` → `ice`.

Two things this cannot see, both by construction:
- **A guard encoded as a number.** `HugeFungusFeature` places weeping vines only for crimson, but the test travels to one of its two call sites as a *probability*: `placeHatBlock(..., bl2 ? 0.1F : 0.0F)` then `if (randomSource.nextFloat() < h)` (`:137`–`:141` → `:163`). Proving `h == 0.0F` makes the comparison unsatisfiable is value reasoning, not identity-test detection — no widening of this mechanism reaches it. Warped fungus still reports vines it never grows.
- **A guard whose shape is unrecognized**, which falls back to reporting the block unconditionally. That is the safe direction: the mechanism only ever hides what it positively proved conditional.

How a method was reached is recorded monotonically and never retracted, so a method analyzed before its caller's guard is known would record itself unguarded forever. `doScan` therefore walks twice — the first walk only learns the interprocedural facts, the second attributes with cleared reach flags. It costs 2× the analyses and changes nothing on vanilla data; it is there so that on a modpack it is not call order that decides whether a false positive gets caught.

#### The other false positive: a block placed by a library the feature calls into

`fossil` reports `barrier`, which comes out of `StructureTemplate#placeInWorld`, not out of `FossilFeature` — and the blocks a fossil really places sit in NBT structures no static analysis can reach. This is a different cause from the config-conditional kind above; don't treat them as one problem. World *reads* are already excluded (the `BlockGetter` rule above); template placement is not, because there is no equally crisp type to exclude it by. In the display it does not matter: `PlacedFeatureNode` never shows `BARRIER`, `AIR`, `CAVE_AIR` or `VOID_AIR` at all.

`reachableInstructions` prunes branches gated on a `static final boolean` that reflectively reads `false`, before any sink is looked at. On 1.20.1 this changes nothing — `SharedConstants.DEBUG_*` are compile-time constants here, so javac already stripped the branches behind them — but it is a correctness requirement from 1.21.10 on, where they are initialized from `debugFlag(...)` and the debug code becomes real bytecode (`LargeDripstoneFeature`'s diamond block, gold block, creeper head, glass). It lives on this branch so the scanner stays identical across branches. The dead half also has to be dropped in `resolve`, not only in the instruction loop: the analyzer merges both arms of `DEBUG ? GLASS : DRIPSTONE_BLOCK` into one stack value at the sink. Only `IFEQ`/`IFNE` directly on a `GETSTATIC` is folded, so live code can never be pruned.

`shouldRecurse`'s `rootPkg` clause (which degrades to `net/minecraft/` for vanilla features) looks like a redundant catch-all next to its two explicit package prefixes, but it is the opposite: under Fabric's production intermediary mappings every Minecraft class is flat `net/minecraft/class_NNNN`, so those prefixes match nothing and only `rootPkg` keeps the walk going. Narrowing it is a ~70% cheaper walk in dev with no blocks lost, and a scan reduced to `place()` alone on a Fabric jar — invisible to tests, which run against named mappings.

The scanner's output is guarded by `FeatureBytecodeScanTest` (golden file `feature_bytecode_scan.json`), which also records per-feature `MAX_METHODS` consumption. Widening the walk must only *add* blocks and must leave `methodLimitReached` false everywhere. Tags are recorded as tag keys, so the file needs no bound tags to be meaningful.

### The block-tag pipeline

A block tag stays a tag from the scanner all the way to the slot, and is only resolved into members on the client. That is what lets one slot be named after the tag instead of spraying N slots (vanilla's three coral features: 3 tags instead of 21 blocks), and it is what makes the display survive a datapack reload — the decode that resolves the tag re-runs whenever tags are synced (`MixinClientPlayNetworkHandler` → `reloadData`).

The type carried end to end is `Either<Block, TagKey<Block>>`, deliberately the same shape ALI uses for `ItemNode`/`IItemNode`/`IWidgetUtils` (`Either<ItemStack, TagKey<? extends ItemLike>>`) — this is one pattern across both mods, not two.

- **Server, feature-configuration family only.** `IServerUtils.collectBlocks(FeatureConfiguration)` and `IServerRegistry.registerFeatureBlockCollector` hand back `List<Either<Block, TagKey<Block>>>`, because the tag is produced deep inside the nesting (`collectConfiguredFeatureBlocks` calls the scanner, and warm ocean's coral is three features down) and a `List<Block>` return type would drop it on the way out. The other three collector families (`BlockStateProvider`, `RootPlacer`, `TreeDecorator`) stay `List<Block>`: nothing in them can express a tag, so they are lifted with `Either.left` at the call sites in `FeatureConfigurationCollectorUtils` instead of being widened for nobody.
- **Node.** `BlockNode` holds the `Either`, encodes it via `FriendlyByteBuf.writeEither`, and resolves the members once at decode into a mutable list in registry order (stable, so a cycling slot does not jitter between reloads). A tag node's tooltip is the shared `Lang.Value.TAG`, so all three viewers show the tag name without any viewer-specific code.
- **Index and prune must stay in agreement** (`compatibility/GenericUtils`): `collectBlocks` contributes a tag's *members* to the reverse index, so clicking `tube_coral_block` still finds warm ocean; `pruneHiddenBlocks` calls `retainBlocks` to drop the members the viewer hides and drops the whole node once none are left. Both go through `IBlockNode` rather than the concrete `BlockNode`, so a third-party block node participates too (it previously did not — `collectBlocks` tested the concrete class).
- **Viewers.** Each builds one slot per node from `IBlockNode.getBlocks()` and cycles it: EMI `EmiIngredient.of(List<EmiStack>)`, JEI several `addItemLike`/`addFluidStack` calls on one slot, REI `Slot.entries(...)`. `EmiIngredient.of(TagKey)` does support block tags (EMI's `EmiTags.getRawValues` special-cases the block registry) but is deliberately **not** used: it would resolve the tag itself and so bypass `pruneHiddenBlocks`, and it would render item-less members as blank frames.
- **Mixed-render tags are the known gap.** A member with no item form but a model of its own (`tall_seagrass`, `kelp_plant`) is no viewer ingredient at all — see `rendersAsFluid`/`rendersAsBlockModel` below. Such members contribute nothing to a cycling slot; only a tag made up *entirely* of them falls back to a rendered 3D model of its first member. They stay in the reverse index either way. Vanilla's coral tags are all item-ful, so this only bites on modded tags.

### `plugin/client` / `plugin/client/widget`
GUI-side rendering: `ClientUtils`, `WidgetUtils` (dispatch to per-node-id widget), widgets `LevelStemWidget`, `BiomeWidget`, `GenerationStepWidget`, `PlacedFeatureWidget`, `BlockWidget`, `BaseTerrainWidget`, `TextureWidget`.

### `compatibility`
`GenericUtils` (gunzip + decode the reassembled network buffer client-side into `Map<ResourceLocation, LevelStemNode>` — the recipe-viewer-integration glue analogous to ALI's `compatibility/common`, consumed by `awi/common-emi`/`common-jei`/`common-rei`).

`GenericUtils` also owns `rendersAsFluid`/`rendersAsBlockModel`, the shared rule for how a `Block` becomes a viewer ingredient — item, else fluid, else 3D model. It lives here because all three viewer modules need the same answer and previously each carried its own copy, all three with the same bug: the fluid was tested first, so every block waterlogged in its default state (all 30 coral/coral-fan variants, seagrass, kelp, sea pickle, conduit) rendered as plain water. The fluid must stay the *last* resort, gated on `RenderShape.INVISIBLE` — an item-less block that still has a model (`tall_seagrass`, `kelp_plant`) belongs in the 3D-model branch, not the fluid one.

### `datagen`
Only `LanguageHolder` — registers `Lang.*` enum classes into `aci.CoreLang.TRANSLATION_MAP` (see `aci/CLAUDE.md`'s "Language wiring"). Unlike ALI, AWI's `datagen` generates no config: the whole user-config surface is the two-field `AwiConfig` described under Module layout above.

### `mixin`
Single `MixinClientPlayNetworkHandler` — injects into `handleUpdateTags` (tail) to trigger `clientRegistry.reloadData()` on resource reload (same role as ALI's mixin of the same name).

### `platform` / `platform/services`
`Services` (`ServiceLoader`-based platform accessor) + `IPlatformHelper extends ICorePlatformHelper<IPlugin>` — a smaller interface than ALI's (only `getPlugins`/`getConfiguration`, no loot-pool/spawn-egg/loot-table-parsing methods since AWI has no loot domain). Per-loader implementations live in `awi/fabric`, `awi/forge` and `awi/neoforge` (see `awi/fabric/CLAUDE.md`, `awi/forge/CLAUDE.md`, `awi/neoforge/CLAUDE.md`).

## Data-scan entry point

`network.AbstractServer.readWorldgenInfo(ServerLevel level)` is where AWI's whole scan starts: gets `AwiServerRegistry`, runs `BaseLayoutScanner.scan` over the `Registries.LEVEL_STEM` registry (the parallel base-block phase, ~70% of the total time), then iterates the same registry and builds one `LevelStemNode` per dimension from the scanned layouts into a `Map<ResourceLocation, IDataNode>`, drops empty/optimized-away nodes (`ListNode.optimizeList`), encodes the whole tree plus the server's `TooltipCache` into a `FriendlyByteBuf` (palette-first — see `aci/CLAUDE.md`'s tree-model section; the node write itself is `NetworkUtils.writeMapData`), gzips it, and slices it into `WorldgenDataChunkMessage` chunks cached in memory for later per-player sync.

It runs **on the server thread**, at server start and on datapack reload (see the root `CLAUDE.md` — only the *transfer* is on demand), and it blocks that thread for the whole duration.

## Base-layout scan test harness

The surface-rule scan is empirical, so it is guarded by a golden file rather than by unit assertions. Both tests build the world from vanilla data without a server: `VanillaRegistries.createLookup()` supplies the datapack registries, the vanilla `WorldPreset` supplies real `LevelStem`s, and `RegistryAccess.ImmutableRegistryAccess` wraps copies of just BIOME + NOISE (the only two registries the scan asks for). Shared setup lives in `test/utils/BaseLayoutTestUtils`.

- **`BaseLayoutTest`** — scans every vanilla biome of every vanilla dimension over **three fixed seeds** and compares against `src/test/resources/base_layout.json`. Three seeds because coverage is genuinely seed-dependent (nether `soul_sand`, frozen-peaks `ice` are only hit for some seeds, badlands band positions differ per seed); a single seed would let a sampling reduction pass here while losing blocks in other worlds. Runs as part of the normal test task (~8s). Regenerate after an intentional change with `-Dawi.baselayout.regenerate=true`.
- **`BaseLayoutSweepTest`** — cost/coverage sweep over candidate `ScanSettings`; asserts nothing, reports. Skipped unless `-Dawi.baselayout.sweep=true`. It diffs **atomic coverage** — `(block, storage, position, water, placement)` with `ANY` expanded into both halves — not just the set of block ids, because a narrowed range or a lost flag is a regression too: this is what caught `maxCeilingThickness=4` silently losing ceiling depths while still reporting every block.

Both properties are forwarded to the test JVM from `awi/common/build.gradle`.

## Networking

Mirrors `ali/CLAUDE.md`'s networking pattern exactly — same `AbstractServer`/`AbstractClient` template-method shape, same chunked-gzip-payload-with-palette-first-in-buffer design. The buffer-writing and compression half is genuinely code-shared through `aci.network.NetworkUtils`; the packets, channels and the `AbstractServer`/`AbstractClient` templates themselves are still copy-pasted per mod. The only differences are the payload/entry-point names:

| ALI | AWI |
|---|---|
| `AbstractServer.readLootTables(LootDataManager)` | `AbstractServer.readWorldgenInfo(ServerLevel)` |
| `LootDataChunkMessage(int, byte[])` | `WorldgenDataChunkMessage(int, byte[])` |
| `RequestLootDataMessage()` | `RequestWorldgenDataMessage()` |
| `syncLootTables` server method name | also named `syncLootTables` — **not renamed for AWI**, a naming leftover from copy-pasting ALI's sync logic (`onLootDataChunk`/`startLootData` client-side callbacks are similarly still loot-named). Don't be confused by "loot" naming showing up in AWI's worldgen sync path — it's cosmetic, not a sign the code is misplaced. |

Actual packet/channel registration lives in the loader modules (`awi/fabric`, `awi/forge`, `awi/neoforge`), same division of responsibility as ALI.
