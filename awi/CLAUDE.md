# awi/CLAUDE.md

Guidance for working on **AWI** (`AdvancedWorldgenInfo`, `com.yanny.awi`) — the recipe-viewer plugin that displays worldgen information (placed features, placement modifiers, height providers, block predicates, biome surface blocks, ...). See the repo-root `CLAUDE.md` for the multi-mod monorepo layout, and `aci/CLAUDE.md` for the shared tooltip/plugin-manager mechanism this mod instantiates (read that first — this doc assumes it). AWI's architecture mirrors ALI's almost 1:1 at the plugin/registry/network layer — where it does, this doc says so and points at `ali/CLAUDE.md` instead of restating.

## Module layout

- `awi/common` — platform-agnostic mod logic, covered by this file.
- `awi/common-emi`, `awi/common-jei`, `awi/common-rei` — recipe-viewer integrations. See `awi/common-emi/CLAUDE.md`, `awi/common-jei/CLAUDE.md`, `awi/common-rei/CLAUDE.md` (all reference `ali/common-emi/CLAUDE.md` for the shared pattern). `awi/common-emi` and `awi/common-rei` are **not built on this branch** (`emi_enabled`/`rei_enabled=false`); JEI is the only viewer.
- `awi/fabric` — Fabric loader module. See `awi/fabric/CLAUDE.md`.
- `awi/neoforge` — NeoForge loader module (enabled via `neoforge_enabled`). See `awi/neoforge/CLAUDE.md`.
- `awi/forge` — Forge loader module; **excluded from the build on this branch** (`forge_enabled=false`) and unported. See `awi/forge/CLAUDE.md`.

AWI has no `common-lootjs` equivalent, and its `configuration` package is minimal compared to ALI's: `AwiConfig` (`configVersion`, `tooltipColors`, `logMoreStatistics`, `showInGameNames`, `showConfigConditionalBlocks`, `dimensions`, `dimensionIcons`) plus `ConfigUtils` and `DimensionFilter`, written to `<config>/awi/awi_common.json` and documented by the repo-root `awi_config.schema.json`. `tooltipColors` is the shared `aci.configuration.TooltipColors` block, read on the client alone (see `aci/CLAUDE.md`); `dimensionIcons` (dimension id → item id) is client-only too, resolved by `GenericUtils.getCategoryIcon` for all three viewers' category icons; everything else is read while the data is built. The read/version-rotate/re-create logic is shared with ALI: both go through `aci.configuration.CoreConfigUtils` and `AwiConfig` implements `aci.configuration.ICoreConfig` (see `aci/CLAUDE.md`); AWI's `ConfigUtils` is just that call with `AwiConfig.CODEC` and plain `JsonOps.INSTANCE`, since nothing in it is registry-backed. There are no loot-category-style filters to configure, since worldgen registries are enumerated exhaustively rather than matched against user-declared categories (contrast with ALI's `ali_config.schema.json`-driven filtering). The one filter is `dimensions`, a single list read by `DimensionFilter`: ids and `#tags`, `!` hides, any entry without `!` makes it a whitelist. Like ALI's hidden categories it applies on both sides — the server skips a hidden dimension before `BaseLayoutScanner` and `LevelStemNode` touch it, so it costs no scan time, and `GenericUtils.decompressWorldgenData` drops it again with the client's own config. `LEVEL_STEM` is not a synced registry, so the client cannot resolve tags: there a `!#tag` entry is ignored and a `#tag` entry lets every received dimension through, since the server already applied it.

## `awi/common` package map (`com.yanny.awi`)

### Root
`Utils.java` — mod-id constant + `modLoc(String)` `Identifier` helper, used for every node ID.

### `api`
Mirrors ALI's `api` package, specialized to worldgen value types: `IPlugin`, `@AwiEntrypoint` — plugin registration entrypoints. `ICommonRegistry`/`ICommonUtils`, `IClientRegistry`/`IClientUtils`/`IWidgetUtils`, `IServerRegistry`/`IServerUtils` — thin extensions of `aci`'s generic `ICoreXxx<...>` interfaces, adding AWI-specific registration methods (see `plugin/Plugin.java` below). Every category is keyed by exact `Class` except **features**, which are keyed by their `MapCodec` (see the feature model below). `IDataNode` (extends `aci.api.ICoreDataNode<IServerUtils>`), `ListNode` (abstract, extends `aci.api.CoreListNode`) — the recursive server-built/client-synced tree node base, only the two constructors; the encode itself (child count + per-child id/payload, tolerating per-node encode failures) lives in `CoreListNode` and is shared with ALI — see `aci/CLAUDE.md`. `IBlockNode` (`getBlock()`/`getBlocks()`/`retainBlocks()`/`getChance()`, implemented by `BlockNode` — see the tag pipeline under `plugin/server`). `FeatureHolder` (record: items + conditions tooltip), `ListWidget`.

### `manager`
Mirrors ALI's `manager` package exactly in shape:
- `PluginManager extends CorePluginManager<...>` — singleton, wires `AwiCommonRegistry`/`AwiClientRegistry`/`AwiServerRegistry`, plugins sourced from `Services.getPlatform().getPlugins()`.
- `AwiServerRegistry` — holds ~22 `ManagedRegistry` maps in three groups (most backed by the matching `BuiltInRegistries.*_TYPE` so `printRegistrationInfo` can report coverage):
  - **block collectors** (`List<Block>` results): feature, block-state provider, root placer, tree decorator.
  - **tooltip categories** (`TooltipBuilder` results): feature, placement modifier, int provider, float provider, rule test, height provider, block predicate, block-state provider, tree decorator, feature size, root placer, foliage placer, trunk placer, structure processor, plus the `ClassKeyedMap`-backed generic "value" tier (`aci/CLAUDE.md`'s tier 1).
  - **placement-summary propagators**: int span, height span, placement (see `plugin/server/summary` below).

  Plus the **surface rule handlers** (see `SurfaceRuleSpecializer` below), keyed by rule-type `Identifier` and reported against `MATERIAL_RULE_TYPE`.

  All of them are created with `registerClassKeyed` except the two **feature** registries, which use the generic `register(...)` keyed on `MapCodec<? extends Feature>` and named through `BuiltInRegistries.FEATURE_TYPE.getKey(codec)` — a feature has no dedicated type object to key on, and its class is not what the registry holds — and the surface rule handlers.

  Falls back to `MissingTooltipUtils` when a class has no registered handler (see `aci/CLAUDE.md`'s "Missing-entry fallback" section). When adding a category, this list plus `IServerRegistry`/`IServerUtils` are what need touching — see `aci/CLAUDE.md`'s "Adding a new category".
- `AwiClientRegistry` — client-side counterpart holding decoded `IDataNode`s.

### `plugin/Plugin.java` — the `@AwiEntrypoint`
`registerServer` is one long wiring block; the call counts are the quickest map of where AWI's coverage actually sits: 51 `registerValueTooltip` (generic tier — `IntProvider`, `RuleTest`, `HeightProvider`, `BlockPredicate`, `Feature`, `BlockReplacement`, `BlockState`, `Vec3i`, registry-keyed `Block`/`Fluid`/`*Type` lookups, ...), 58 `registerFeatureTooltip` + 58 `registerFeatureBlockCollector` (one pair per entry of `BuiltInRegistries.FEATURE_TYPE`), 15 `registerPlacementModifierTooltip`, 13 `registerBlockPredicateTooltip`, 11 each `registerStructureProcessorTooltip`/`registerFoliagePlacerTooltip`, 9 `registerTrunkPlacerTooltip`, 9 `registerPlacementPropagator`, 8 each `registerStateProviderBlockCollector`/`registerBlockStateProviderTooltip`, 10 each for tree-decorator tooltips/collectors, 6 each rule tests, int providers, height providers, `registerIntSpanPropagator`, `registerHeightSpanPropagator`, 4 `registerFloatProviderTooltip`, 2 `registerFeatureSizeTooltip`, 1 each root-placer tooltip/collector. `registerClient` registers 6 widget + 6 data-node factory pairs; `registerCommon` registers translation keys and calls `new CommonValueTooltip<>().registerAll(registry)`. It also wires the three placement-summary propagator registries (int span / height span / placement) — see `plugin/server/summary` below.

**Important**: there are no material-rule, structure, carver, or noise-settings *tooltip or collector registrations* here — those aren't pluggable value types with a 1:1 vanilla registry, so they're not handled through the two-tier dispatch pattern at all. They're handled procedurally by `plugin/common/nodes.NodeUtils` (below), which is why you won't find a `MaterialRule` category anywhere in `Plugin.java`. The one material-rule hook is `registerSurfaceRuleHandler`, which takes a single rule type out of that procedure (`BandlandsLayout`, `OreVeinLayout` — see `SurfaceRuleSpecializer` below). Structure *processors* are the near-miss to keep straight: `StructureProcessor` does have a vanilla registry and is registered normally (11 tooltips) — it's whole structures that aren't.

### `plugin/common/nodes` — the AWI data-scan engine
Server-side tree construction; each class doubles as codec (server constructor + `IClientUtils`/`FriendlyByteBuf` decode constructor + `encodeNode`, per `aci/CLAUDE.md`'s dual-constructor convention).

- `LevelStemNode` (entry-level node) — one per dimension; iterates the generator's `possibleBiomes()` and builds a `BiomeNode` per biome. It does **not** scan anything itself: the base blocks are handed to it as a pre-computed `Map<Holder<Biome>, NodeUtils.LayerHolder>` (empty for non-noise generators).
- **`BaseLayoutScanner`** — runs `NodeUtils.getBaseBlocksForBiome` for every (dimension, biome) pair of the world *up front*, on one shared pool, before any node is built. One pool for all dimensions rather than one per dimension, so workers stay busy across dimension boundaries; tasks are ordered by dimension and each worker keeps the `DimensionContext` of the dimension it last worked on (`ContextCache`), which bounds both `RandomState.create` calls and the memory the material-rule contexts hold. Results are cached per (noise settings, biome) — the scan's outcome depends only on the dimension's `NoiseGeneratorSettings`, the biome and the seed, so dimensions sharing settings scan each biome once. Also collects the `Stats` that `AbstractServer` logs (elapsed time, cache hits, min/max/mean per biome, and how many distinct material rules the scanned dimensions use — that last one measures how much wider the cache key could be).
- `BiomeNode` → iterates `BiomeGenerationSettings.features()` per `GenerationStep.Decoration` → `GenerationStepNode` → `PlacedFeatureNode` (splits into the `Feature`'s blocks via `utils.collectBlocks`, and `PlacementModifier` tooltips) → `BlockNode` (leaf).
- `BaseTerrainNode` — leaf list of blocks discovered by the material-rule scanner below. From 26.3 that includes ore-vein blocks: veins are an `ore_vein` material rule rather than a separate generator switch, so the dimension's rule really does place them; `OreVeinLayout` reports them (see below).
- **`SurfaceRuleSpecializer`** — rewrites a dimension's `MaterialRule` into the subset that can fire for one biome (the class keeps AWI's older "surface rule" wording for what 26.3 renamed to a material rule; the vocabulary is AWI's own, the type is Mojang's); one instance per dimension, since the encode behind it is not free. The scan pins the biome for a whole `getBaseBlocksForBiome` call, yet every `minecraft:biome` condition compiles to a `LazyYCondition` — invalidated on *every cell* — so each dead biome-gated branch costs a set lookup per cell, and a modded overworld carries hundreds of them (measured on Prominence II: 2394 → 146 nodes, 94% of the rule dead for any single biome).

  The rewrite goes through `MaterialRule.CODEC` (serialize → prune JSON → deserialize) rather than over the object graph, because the node classes are records whose field/method names remap in production while registry ids in the serialized form do not. It must be `CODEC` and not `DIRECT_CODEC`: a rule or condition held in the `worldgen/material_rule`/`worldgen/material_condition` registry is a `HolderHolder`, whose own `codec()` throws, and only the holder codec encodes it — as its bare id.

  **A reference is resolved, pruned and inlined only when pruning changed it.** Vanilla splits the overworld rule into many referenced pieces, so a branch worth pruning routinely sits behind an id; stopping at the id prunes nothing. References are followed only in positions known to hold a rule (the root, a `minecraft:sequence` element, a `then_run`) or a condition (`if_true`) — a bare string anywhere else is a block/noise id, not a rule. An untouched reference stays a reference, which keeps the rule from being expanded for nothing. Node count is therefore **not** the cost metric any more: inlining a 1-node reference makes the serialized form grow while the compiled rule still shrinks, which is why the statistics log says `references inlined` instead of a negative percentage there.

  **Unknown node types are descended into but never restructured.** Mods wrap the vanilla rule in their own rule type (Terrablender being the common one) and the branches worth pruning sit *inside* that wrapper — stopping at the first unrecognised node prunes nothing on exactly the packs that need it most. Inside an unknown node a dead branch is therefore replaced *in place* by an empty `minecraft:sequence` (a valid rule that never fires) instead of being removed, so arity and element order survive and it does not matter whether the wrapper indexes its children or pairs them with data of its own. Elements are only truly dropped inside a `minecraft:sequence`, whose semantics are known. An object carrying `"type": "minecraft:condition"` is always a `MaterialRule` (that id belongs to the rule registry), so descending cannot misread a condition as one. Any failure — and any dimension whose first biome prunes nothing — falls back to the original rule and switches specialization off for that dimension.

  **Surface rule handlers — ghosts, markers and coins.** Some rule types are not a plain function of the position, and sampling catches only fragments of them. `IServerRegistry.registerSurfaceRuleHandler(ruleTypeId, Context -> ISurfaceRuleHandler)` takes one rule type out of the measurement; `NodeUtils.DimensionContext` binds the factories once per dimension with an `ISurfaceRuleHandler.Context` (the dimension's `RandomState` plus the codec lookup, through which a handler decodes a definition that references registry entries), and a factory that returns `null` or throws leaves the rule measured. Before any pruning, the constructor rewrites the encoded rule once per dimension:
  - Every node of a handled type becomes a **ghost**: `minecraft:light` with its own `LEVEL`, so at most 16 distinct definitions per dimension, identical definitions sharing one. The walk records ghosts apart from real blocks (`LayerHolder.recordGhost`), and `expandGhosts` hands each handler the Ys, water and placement where its ghost landed. A rule that places `minecraft:light` itself disables ghosts for that dimension.
  - A handler whose `alwaysPlaces()` is `false` — its rule passes the positions it does not fill on to the next rule — gets a **marker** instead: the ghost behind a `y_above` that is never true. A ghost there wins every position it is reached at and starves every rule after it, and gating it with a coin fails both ways: a 50% coin halves the samples of the later rules, and a coin thin enough not to matter is hit too rarely to observe. The marker never fires; whether it survives `specialize(biome)` decides whether the rule applies to the biome (`markers(biome)`), and `expandMarkers` gives the handler the dimension's whole height with `ANY` water and placement, so the handler has to find its Ys itself.
  - Every `noise_threshold` and `hole` condition becomes a **coin**: a `vertical_gradient` between ±2000, true for about half of all positions. Never a constant true — an always-open gate shadows its sequence siblings and every `not(gate)` branch. Every anchor AWI writes has to stay inside the codec's absolute-Y range (about ±2032): outside it the whole rewrite fails and the dimension is scanned unchanged, silently without ghosts and coins.
  - The rewrite follows references like pruning does, in the same positions (a `sequence` element, `then_run`, `if_true`, `invert`), and inlines one only when it changed. Vanilla keeps both handled types behind ids — `bandlands` inside `minecraft:overworld/surface`, the veins as bare `minecraft:overworld/*_ore_vein` elements of the overworld sequence — so a rewrite that stops at a reference replaces nothing.

  The handlers AWI registers itself:
  - `BandlandsLayout` (`minecraft:bandlands`) — expands the observed Ys into the clay-band palette (`MaterialSystem.clayBands`, via the access widener): the most common colour as the `ABSOLUTE` filler, every other one `LAYERED`, with the band shift measured from the clay-band offset noise.
  - `OreVeinLayout` (`minecraft:ore_vein`, 26.3) — a marker handler. It decodes the `OreVeinRule` through the context's lookup and keeps every Y at which the vein's `density` is positive somewhere on a fixed X/Z grid (±2048, step 64) — positive density is what vanilla needs before it places anything — and reports ore, raw ore (when `raw_ore_chance > 0`) and filler as `ABSOLUTE` over those Ys. Its result is cached per definition and window, since `expand` runs once per biome.

- **`NodeUtils`** — the real worldgen-data-collection engine, and the single most distinctive piece of AWI's architecture: there is no `BuiltInRegistries.PLACED_FEATURE`-style enumeration for surface blocks (features come from a biome's own `BiomeGenerationSettings`, reached only through the per-dimension `LevelStem`→generator→biome path above). Instead, `DimensionContext` builds a `MaterialRuleContext` by hand and `walkColumn` empirically **fires the biome's compiled `RuleEvaluator` over synthetic canonical columns** (swept surface heights, spiral-sampled XZ, ceiling/overhang probes) to reverse-engineer which blocks the rule places — there is no vanilla API that just answers "what blocks can this biome's material rule produce," so AWI empirically probes it.

  The context needs no chunk and no `NoiseChunk`: its inputs are a 1×1×1 `DensityVolume` plus `randomState.samplersWithContext(SamplerContext.EMPTY_UNCACHED)`, which is why `DimensionContext` takes neither a `RegistryAccess` nor a `PalettedContainerFactory`. `walkColumn` pins `minSurfaceLevel` itself (with `lastMinSurfaceLevelUpdate = lastUpdateXZ`) so `above_preliminary_surface` resolves against the assumed surface instead of sampling the preliminary-surface function, and passes **zero surface gradients** to `updateXZ` — flat canonical terrain, so `steep` never fires, exactly as the empty mock heightmap behaved before. Each discovered block gets classified as RELATIVE/ABSOLUTE/LAYERED with water/floor-ceiling constraints.

  The sampling knobs live in `NodeUtils.ScanSettings` (`DEFAULT` is what production uses) so their cost/coverage trade stays measurable — see the test harness below before touching them. Two of them are not plain "more/less sampling" and interact with the classification, which is why changing them alone silently corrupts output:
  - `deepWalkWindow` bounds how far below the assumed surface a normal walk still evaluates, turning the walk's cost from quadratic in world height into linear. Every Y is still reached (the assumed surface sweeps the whole range), but it *censors the depth axis*, so `BlockObservation.classify` treats a block whose depths run into the window as unbounded-depth — without that guard deepslate/bedrock flip from `ABSOLUTE` to "1..window blocks below the surface".
  - `specializeRulePerBiome` recompiles the rule per biome with the branches that cannot fire for it removed (`SurfaceRuleSpecializer`). Semantics-preserving, so the golden file must stay byte-identical when it is toggled — it is a pure cost cut, worth 1.5× on vanilla and 2.8× on a heavily-modded overworld.
  - `extentStableRounds` is a second, weaker stop condition next to `stableRounds`: stop once nothing has *widened* the result (no new block, flag, or wider extent) for that many rounds, even while new interior positions keep turning up. Noise-banded rules (badlands) never stop producing those, so `stableRounds` alone never triggers for them and they always run to `maxRounds`. It must stay the weaker of the two rather than replace `stableRounds` — making the extent metric the only criterion forces every simple biome to sit through the longer window, which measured +60% on a real pack while looking free on vanilla.

  Feature-placed blocks are **not** obtained by running `Feature.place()` against mock level/chunk implementations — placement reads the surrounding world, so the result is unreliable; the static ASM approach in `plugin/server` below is what covers that side instead.

Feature-placed blocks come from two complementary sources, both in `plugin/server`: static introspection of the feature's own fields (`FeatureCollectorUtils`) and, additively for blocks hardcoded inside `Feature.place()` bytecode (the ones absent from those fields), `FeatureBytecodeScanner` (below). Both are collected as `Either<Block, TagKey<Block>>` — see "The block-tag pipeline" below.

The two must be paired at **every** level of nesting, which is what `FeatureCollectorUtils.collectFeatureBlocks` is for — it is the only sanctioned way to descend into a nested feature, and `PlacedFeatureNode` uses it for the top level too. Pairing them only at the top loses whole features: warm ocean's coral reaches the world exclusively as features nested inside `warm_ocean_vegetation`'s `simple_random_selector`, so the outer feature contributes nothing of its own and the scanner sees only the selector.

A nested feature is a **`Holder<PlacedFeature>`**, so every descent unwraps `placed.value().feature().value()` — `collectPlacedFeature` does that, guarded by `isBound()` on both hops. Two routes reach it: the six selectors (`overlay`, `random_boolean_selector`, `random_selector`, `sequence`, `simple_random_selector`, `weighted_random_selector`) override `Feature.getSubFeatures()` and are covered generically by `collectSubFeatures`; `coral_claw`, `coral_tree`, `root_system`, `vegetation_patch`, `waterlogged_vegetation_patch` and `single_block_pillar` nest a placed feature **without** overriding it and need the explicit descent in their own collector. `getSubFeatures()` is already transitive, so a deep tree is visited more than once — `PlacedFeatureNode` dedups through a `LinkedHashSet`, which is what makes that harmless.

**Every** registered feature type needs a collector, even one that contributes no blocks of its own: an unregistered feature yields an empty list, and the sub-feature walk lives *inside* the collector, so a missing registration silently severs the whole nested subtree. Those cases register `FeatureCollectorUtils::collectSubFeatures` directly.

### `plugin/server`
From 26.3 every field that held a `BlockStateProvider` holds a `Holder<BlockStateProvider>` (an inline value or a reference into `worldgen/block_state_provider`), and `BlockStateProvider`/`PlacementModifier` lost `type()` in favour of `codec()`. AWI's API is unchanged: a tooltip passes the `Holder` straight to `getValueTooltip` (ACI's `CommonValueTooltip` renders `holder.value()`), and a **collector** unwraps through the single shared `BlockStateProviderCollectorUtils.collectHolder`, which is guarded by `isBound()` and is the only place that unwrapping happens.

Pure `IServerUtils`-based utility classes registered by `Plugin.java`, following the same one-static-method-per-Mojang-subtype convention as ALI — one class per category in `AwiServerRegistry`: `TooltipUtils`, `ValueTooltipUtils`, `RegistriesTooltipUtils` (registry-keyed name/id lookups via `CoreTooltipUtils.getBuiltInRegistryTooltip`), `FeatureTooltipUtils`/`FeatureCollectorUtils`, `PlacementModifierTooltipUtils`, `IntProviderTooltipUtils`, `FloatProviderTooltipUtils`, `HeightProviderTooltipUtils`, `BlockPredicateTooltipUtils`, `RuleTestTooltipUtils`, `BlockStateProviderTooltipUtils`/`BlockStateProviderCollectorUtils`, `TreeDecoratorTooltipUtils`/`TreeDecoratorCollectorUtils`, `RootPlacerTooltipUtils`/`RootPlacerCollectorUtils`, `FoliagePlacerTooltipUtils`, `TrunkPlacerTooltipUtils`, `FeatureSizeTooltipUtils`, `StructureProcessorTooltipUtils`, `PlacedFeatureUtils`, `MissingTooltipUtils` (fallback).

#### `plugin/server/summary` — the placement summary
The second distinctive piece of AWI (after `NodeUtils`): instead of only dumping each `PlacementModifier`'s own tooltip, this derives the three numbers a player actually wants per placed feature — **how many per chunk, with what chance, in which vertical band** — without running worldgen. `PlacementSummaryUtils.summarize` walks a feature's modifier list, asks the `placementPropagators` registry for each modifier's `PlacementContribution` (each modifier fills at most one of count/chance/height; first count wins, chances multiply), and merges them into a `PlacementSummary(CountSpan, chancePercent, HeightSpan)` that `appendSummary` writes as top-level un-headed tooltip lines. `CountSpan`/`HeightSpan` carry both a `RangeValue` and a `Kind` (distribution shape: `CONSTANT`, `UNIFORM`, `BIASED_TO_BOTTOM`, `TRAPEZOID`, `CLAMPED_NORMAL`, `WEIGHTED`, `RELATIVE_TO_HEIGHTMAP`, ...), plus `HeightSpan.bestBand` (the highest-probability Y interval, collapsing to the mode for peaked distributions) and `CountSpan.details` (the modifier's own tooltip, shown when the range is unknown — e.g. `NoiseBasedCountPlacement`). `ColumnContext(minY, height)` reimplements `VerticalAnchor.resolveY` without a world, so the whole path is world-free and unit-testable (`PlacementSummaryTest`). Adding a modded count/chance/height modifier means registering a `PlacementPropagator` (and, if it wraps a provider, an int/height span propagator) — not touching this orchestration.

`FeatureBytecodeScanner` is the exception to the "read the config" rule: a **static ASM data-flow analysis of `Feature.place()` bytecode** that recovers blocks hardcoded in a feature's placement logic (absent from its own fields — e.g. iceberg ice, monster-room spawner/chest, dripstone). The entry point it resolves reflectively is `Feature#place(WorldGenLevel, ChunkGenerator, RandomSource, BlockPos)`; there is no `FeaturePlaceContext` any more, so config values arrive as `GETFIELD this.<component>` on the feature record itself. It tracks only `BlockState`/`Block` values that flow into a placement sink (`LevelWriter#setBlock`/`Feature#setBlock`), so a block that is merely read or checked is not reported — but that is not the same as "no false positives", see the section below. It is deliberately **mapping-agnostic** — nothing is matched by method/field/class name (those remap in production); sinks and value types are identified via `Class` assignability and concrete blocks by reflectively reading the referenced static field. ASM (`org.ow2.asm`) is already on the classpath transitively via loom/fabric-loader. `PlacedFeatureNode` calls it additively alongside `utils.collectBlocks`. PoC-level: no inter-procedural receiver binding, limited tag-lookup resolution (documented in the class Javadoc).

A block reached through a `TagKey<Block>` is reported as the **tag**, not as its members: `ScanResult` carries `blocks` and `tags` side by side, and the walk never resolves a tag into its members (a tag bound to a parameter or to a lambda parameter travels as the tag — that propagation is what keeps the coral features working, since their block reaches the sink as a lambda parameter). Nothing on the server expands it; see the tag pipeline below.

The backwards walk from a sink crosses seven hops, each needed by a real vanilla feature — without them only a block written inline in the `setBlock` argument is ever seen. **Local variables** back to their stores (`throughLocal`; `SourceInterpreter` treats a load as its own producer, so `BlockState state = ...; setBlock(pos, state, 2)` otherwise resolves to nothing — seagrass/kelp depend on this hop). **Method parameters** back to their call sites (`bindArguments` records what each call passes per parameter, `addParameterCandidates` materializes it only when that parameter actually reaches a sink, so a block merely handed to a predicate is never collected). **`CHECKCAST` plus the receiver and block-carrying arguments** of the producing call — this is what reaches a `TagKey` through an `Optional` chain (`BLOCK.getTag(BlockTags.CORAL_BLOCKS)`, the coral features). **Lambda/method-reference bodies** via the `INVOKEDYNAMIC` bootstrap handle (`UnderwaterMagmaFeature`'s `forEach` reaches its magma only through this hop).

A lambda's **own parameters** are bound two independent ways, because vanilla hands lambdas around in two shapes:
- From the **receiver** of the call the lambda is handed to (`bindLambdaParameters`) — `getTag(BlockTags.CORALS)...ifPresent(block -> setBlock(pos, block.defaultBlockState(), 2))` places a value that has no producer in the enclosing method at all.
- From the **callee's own use of the lambda** (`recordFunctionalArguments` records which lambda a call site put in which parameter; `bindFunctionalCandidates` binds it when the callee invokes that parameter). This is dripstone: `DripstoneUtils.growPointedDripstone` hands `state -> level.setBlock(pos, state, 2)` to the *static* `buildBaseToTipColumn`, so the receiver hop returns immediately (`INVOKESTATIC`) and the value only exists inside the callee's `consumer.accept(...)`. The binding is **positional** and deliberately **not** filtered by `carriesBlocks` on the call's own argument types — a functional interface's descriptor is erased, so `Consumer#accept` declares `Object`; the lambda body's parameter type is what decides.

**Return values** of called helpers are resolved from their `ARETURN`s (`resolveReturnValue`/`returnedCandidates`, memoized per method). `DripstoneUtils.createPointedDripstone(direction, thickness)` is the shape that needs it: a static factory whose entire input is enum values, so neither the receiver nor the argument hop sees anything and `pointed_dripstone` is invisible without reading the callee.

Calls whose owner is a `BlockGetter` are **excluded** from that hop, and the exclusion is load-bearing rather than an optimization: a feature that writes back a state it read (`setBlock(pos, level.getBlockState(other), 2)`) would otherwise report the sentinels a reader answers with out of bounds — `ProtoChunk#getBlockState` returns `VOID_AIR`, which `fossil` and `end_gateway` would then report as a placed block.

**`final` instance fields** are resolved from the `PUTFIELD`s in their owner's constructors (`addInstanceFieldValue`). `GETFIELD` has no value to read reflectively — `scan` is handed a `Class`, never an instance — so without this hop a feature that caches its blocks in fields reaches its sinks carrying nothing. Restricted to `final` fields on purpose: anything reassignable makes the constructor's value a guess. It is there for modded features: vanilla's one case was `DesertWellFeature`, which 26.3 removed, and a feature record's own components are classified as *config-derived* rather than as constants (see "Config-conditional blocks" below).

Method lookup **walks the hierarchy both ways**. Up, because `place()` is often declared on a shared base rather than on the feature itself — without it those features analyze zero methods and silently return nothing. Down, because that base then calls back into an abstract method the subclass implements; stopping at the abstract declaration loses everything below it. The downward dispatch deliberately targets only the class being scanned, since that is the receiver of a feature's self-call.

**Known gap: the upward walk follows `superName` only, never interfaces** (`declaration`). That was complete while shared bases were abstract classes. From 26.3 they are interfaces with a `default place(...)` — `AbstractHugeMushroomFeature` is the vanilla case — so `huge_brown_mushroom`/`huge_red_mushroom` now analyze **0 methods**. Nothing is lost on vanilla data (both already found 0 blocks; their cap and stem come from the config side), but a modded feature that inherits `place()` from an interface is invisible to the scanner, and since `Feature` itself is an interface now that is the shape mods will reach for.

An abstract call that is *not* such a self-call is dispatched to the classes of **registered blocks** implementing it (`queueImplementors`). Sculk is the case: a patch spreads through `SculkSpreader`, which calls `SculkBehaviour#attemptSpreadVein` on whatever block it found in the world, so no static receiver type leads to the placing code. The block registry is the only implementor index available, and `MAX_IMPLEMENTORS` is what keeps it from blowing up — a method declared on a wide base type (`BlockBehaviour`) resolves to hundreds of classes and is dropped rather than dispatched. This is the **one place the scanner reads a registry**; the `Either<Block, TagKey<Block>>` output still never expands a tag. Implementors that are not registered blocks (an inner class, an anonymous `SculkBehaviour.DEFAULT`) stay out of reach — which is exactly why `sculk_patch` reports the sculk and sensors it grows but **not** `sculk_vein`: veins go through `MultifaceSpreader.SpreadConfig#getStateForPlacement`, implemented by inner classes only. Reaching those needs a classpath-wide implementor index, which is a different mechanism with real blow-up risk, not an extension of this one.

`MAX_METHODS` is sized against all of that: a runaway guard at ~2× vanilla's widest feature (`fossil`, 448 methods), not a tuning knob — lowering it silently drops blocks rather than failing.

#### Config-conditional blocks

The scan is keyed by `Feature` *class*, so it cannot know which instance of that feature it is being asked about and reports every branch. A block whose every placement is reached only through a test on one of the feature's own fields therefore shows up for instances that never place it — `LakeFeature`'s `ICE` is only placed when its `fluid` yields water, so it is right for the water lake inside `sulfur_pool` and wrong for `lake_lava`.

`ScanResult.configConditionalBlocks` is that subset, computed by `configGuardedInstructions`: control dependence per conditional jump (what is reachable from one successor but not the other only runs when that branch was taken), plus interprocedural propagation of how each method was reached. `collectFeatureBlocks` drops it unless `AwiConfig.showConfigConditionalBlocks` says otherwise. Dropping it there, not in the widget, also keeps those blocks out of the reverse index — a block that is not shown is not searchable either.

**A config-derived condition is deliberately not enough** (`isConfigSelectiveTest`), and this is the part to understand before touching it. `l < this.tries()` and `for (EndSpike spike : this.spikes())` are config-derived too, yet always run — and a feature's whole body typically sits inside one, so counting them marked a large share of features, including `underwater_magma`'s own magma and `end_spike`'s obsidian. Only an **identity test** on a config-derived block, state or fluid (`is(Block)`, `is(TagKey)`) is counted, which is the shape that actually selects. With that narrowing the flagged set across all 58 vanilla features is exactly `lake` → `ice` and `simple_block` → `air`, `pale_moss_carpet`.

  What counts as *config-derived* is `isFeatureType`: reading a field of a `Feature`, calling a method on one (a record accessor), or receiving one as a declared parameter or return value. Since the configuration now lives in the feature record itself, a record component read as `GETFIELD this.<component>` is config-derived — **not** a constant, even though `addInstanceFieldValue` resolves `final` instance fields from constructors for the non-config case.

Two things this cannot see, both by construction:
- **A guard encoded as a number.** `HugeFungusFeature` places weeping vines only for crimson, but the test travels to one of its two call sites as a *probability*: `placeHatBlock(..., bl2 ? 0.1F : 0.0F)` then `if (randomSource.nextFloat() < h)` (`:137`–`:141` → `:163`). Proving `h == 0.0F` makes the comparison unsatisfiable is value reasoning, not identity-test detection — no widening of this mechanism reaches it. Warped fungus still reports vines it never grows.
- **A guard whose shape is unrecognized**, which falls back to reporting the block unconditionally. That is the safe direction: the mechanism only ever hides what it positively proved conditional.

How a method was reached is recorded monotonically and never retracted, so a method analyzed before its caller's guard is known would record itself unguarded forever. `doScan` therefore walks twice — the first walk only learns the interprocedural facts, the second attributes with cleared reach flags. It costs 2× the analyses and changes nothing on vanilla data; it is there so that on a modpack it is not call order that decides whether a false positive gets caught.

#### The other false positive: a block placed by a library the feature calls into

`fossil` reports `barrier`, which comes out of `StructureTemplate#placeInWorld`, not out of `FossilFeature` — and the blocks a fossil really places sit in NBT structures no static analysis can reach. This is a different cause from the config-conditional kind above; don't treat them as one problem. World *reads* are already excluded (the `BlockGetter` rule above); template placement is not, because there is no equally crisp type to exclude it by. In the display it does not matter: `PlacedFeatureNode` never shows `BARRIER`, `AIR`, `CAVE_AIR` or `VOID_AIR` at all.

`reachableInstructions` prunes branches gated on a `static final boolean` that reflectively reads `false`, before any sink is looked at. On 1.20.1 this changes nothing — `SharedConstants.DEBUG_*` are compile-time constants here, so javac already stripped the branches behind them — but it is a correctness requirement from 1.21.10 on, where they are initialized from `debugFlag(...)` and the debug code becomes real bytecode (`LargeDripstoneFeature`'s diamond block, gold block, creeper head, glass). It lives on this branch so the scanner stays identical across branches. The dead half also has to be dropped in `resolve`, not only in the instruction loop: the analyzer merges both arms of `DEBUG ? GLASS : DRIPSTONE_BLOCK` into one stack value at the sink. Only `IFEQ`/`IFNE` directly on a `GETSTATIC` is folded, so live code can never be pruned.

`shouldRecurse`'s `rootPkg` clause (which degrades to `net/minecraft/` for vanilla features) looks like a redundant catch-all next to its two explicit package prefixes, but it is the opposite: under Fabric's production intermediary mappings every Minecraft class is flat `net/minecraft/class_NNNN`, so those prefixes match nothing and only `rootPkg` keeps the walk going. Narrowing it is a ~70% cheaper walk in dev with no blocks lost, and a scan reduced to `place()` alone on a Fabric jar — invisible to tests, which run against named mappings.

The scanner's output is guarded by `FeatureBytecodeScanTest` (golden file `feature_bytecode_scan.json`), which also records per-feature `MAX_METHODS` consumption. Widening the walk must only *add* blocks and must leave `methodLimitReached` false everywhere. Tags are recorded as tag keys, so the file needs no bound tags to be meaningful.

### `plugin/server/summary` — the placement summary

The three lines at the top of a `PlacedFeatureNode`'s tooltip — attempts per chunk, chance, height — are *derived*, not read off the placement-modifier tooltips: `PlacementSummaryUtils.appendSummary` walks the feature's `List<PlacementModifier>` once, at node build time, and appends the result as un-headed lines so it sits above the (advanced-tooltip-only) `Configured Feature` / `Placement` branches.

Dispatch is three exact-class registries on `AwiServerRegistry`, all fed from `Plugin.registerServer` and all open to plugins through `IServerRegistry`: `registerPlacementPropagator` (per `PlacementModifier` → `PlacementContribution`, the main extension point), and `registerIntSpanPropagator` / `registerHeightSpanPropagator` (per `IntProvider`/`HeightProvider` → `CountSpan`/`HeightSpan`) for the sub-providers a modifier hands its count or height to. A `PlacementContribution` fills **at most one** of the three axes; a filter/scan/spread modifier returns `EMPTY`. `PlacementPropagator`/`HeightSpanPropagator` are named interfaces rather than `BiFunction` only because they take the `ColumnContext` as a third argument.

Merging mirrors vanilla's own semantics and is order-sensitive: the **first** count and the **first** height win (a later modifier of the same axis does not override), while chances **compound** (`p1 × p2`, over percent values, hence the extra `× 0.01`). Changing that to "last wins" or "narrowest wins" would not match how the modifier list is actually applied during generation.

Fallbacks when nothing is registered: `getIntSpan` degrades to `CountSpan.unknown(min..max)` read off the vanilla `IntProvider` accessors, `getHeightSpan` to `HeightSpan.unknown()`, `getPlacementContribution` to `PlacementContribution.EMPTY`. `placementPropagators` is deliberately the one registry created with `reportMissing = false` — most modifiers legitimately contribute to no axis, so a missing-entry report there would be noise rather than a to-do list.

Unknown is a first-class outcome, not a failure. `CountOnEveryLayerPlacement`, `NoiseBasedCountPlacement` and `NoiseThresholdCountPlacement` depend on the surrounding world, so they report `Kind.UNKNOWN` with `markUnknown()` (`RangeValue(false, true)` — keeps the numeric fields but flags them uncertain) plus `unknownDetails`, the modifier's *own* tooltip nested under the `Unknown` line so the reader sees which noise parameters produced it. Inventing a range for them would be worse than saying nothing.

`Kind` is a label only — it never affects a computed number, it just tells the reader how the value is spread. `PlacementSummaryUtils.showsKind` suppresses it for `CONSTANT` (obvious from a single value) and for `UNKNOWN`/`RELATIVE_TO_HEIGHTMAP` (no shape to report).

`HeightSpan.bestBand` has a locked contract: a **flat** distribution reports its exact flat interval (uniform → the whole range, trapezoid with a plateau → the plateau), a **peaked** one collapses to the single mode Y (triangular trapezoid → the centre, biased-to-bottom → the minimum). It is printed only when it actually narrows the range, otherwise the range alone is shown. `WeightedListHeight` takes the union of its branches as the range but the best band of its **heaviest** branch — a union of bands would describe no distribution at all.

Recursive providers (`ClampedInt`, `WeightedListInt`, `WeightedListHeight`) must recurse through `utils.getIntSpan`/`utils.getHeightSpan` rather than call the sibling static directly, otherwise a modded provider nested inside a vanilla wrapper never reaches its own propagator.

`ColumnContext` (`minY` + `height`) exists so a `VerticalAnchor` can be resolved without a world — it mirrors `VerticalAnchor.resolveY(WorldGenerationContext)`. It is created once per dimension in `LevelStemNode` from the generator's `getMinY`/`getGenDepth` and threaded down through `BiomeNode`/`GenerationStepNode` into every `PlacedFeatureNode`, which is why it is a constructor argument everywhere instead of something the summary looks up. A height that is relative to terrain has no absolute Y at all: those report `HeightSpan.relativeTo(heightmap)` and print the heightmap name instead of a range.

### The block-tag pipeline

A block tag stays a tag from the scanner all the way to the slot, and is only resolved into members on the client. That is what lets one slot be named after the tag instead of spraying N slots (vanilla's three coral features: 3 tags instead of 21 blocks), and it is what makes the display survive a datapack reload — the decode that resolves the tag re-runs whenever tags are synced (`MixinClientPlayNetworkHandler` → `reloadData`).

The type carried end to end is `Either<Block, TagKey<Block>>`, deliberately the same shape ALI uses for `ItemNode`/`IItemNode`/`IWidgetUtils` (`Either<ItemStack, TagKey<? extends ItemLike>>`) — this is one pattern across both mods, not two.

- **Server, feature family only.** `IServerUtils.collectBlocks(Feature)` and `IServerRegistry.registerFeatureBlockCollector` hand back `List<Either<Block, TagKey<Block>>>`, because the tag is produced deep inside the nesting (`collectFeatureBlocks` calls the scanner, and warm ocean's coral is several features down) and a `List<Block>` return type would drop it on the way out. The other three collector families (`BlockStateProvider`, `RootPlacer`, `TreeDecorator`) stay `List<Block>`: nothing in them can express a tag, so they are lifted with `Either.left` at the call sites in `FeatureCollectorUtils` instead of being widened for nobody.
- **Node.** `BlockNode` holds the `Either`, encodes it via `FriendlyByteBuf.writeEither`, and resolves the members once at decode into a mutable list in registry order (stable, so a cycling slot does not jitter between reloads). A tag node's tooltip is the shared `Lang.Value.TAG`, so all three viewers show the tag name without any viewer-specific code.
- **Index and prune must stay in agreement** (`compatibility/GenericUtils`): `collectBlocks` contributes a tag's *members* to the reverse index, so clicking `tube_coral_block` still finds warm ocean; `pruneHiddenBlocks` calls `retainBlocks` to drop the members the viewer hides and drops the whole node once none are left. Both must go through `IBlockNode` rather than the concrete `BlockNode`, so a third-party block node participates too.
- **Viewers.** Each builds one slot per node from `IBlockNode.getBlocks()` and cycles it: EMI `EmiIngredient.of(List<EmiStack>)`, JEI several `addItemLike`/`addFluidStack` calls on one slot, REI `Slot.entries(...)`. `EmiIngredient.of(TagKey)` does support block tags (EMI's `EmiTags.getRawValues` special-cases the block registry) but is deliberately **not** used: it would resolve the tag itself and so bypass `pruneHiddenBlocks`, and it would render item-less members as blank frames.
- **Mixed-render tags are the known gap.** A member with no item form but a model of its own (`tall_seagrass`, `kelp_plant`) is no viewer ingredient at all — see `rendersAsFluid`/`rendersAsBlockModel` below. Such members contribute nothing to a cycling slot; only a tag made up *entirely* of them falls back to a rendered 3D model of its first member. They stay in the reverse index either way. Vanilla's coral tags are all item-ful, so this only bites on modded tags.

### `plugin/client` / `plugin/client/widget`
GUI-side rendering: `ClientUtils`, `WidgetUtils` (dispatch to per-node-id widget), widgets `LevelStemWidget`, `BiomeWidget`, `GenerationStepWidget`, `PlacedFeatureWidget`, `BlockWidget`, `BaseTerrainWidget`, `TextureWidget`.

### `compatibility`
`GenericUtils` (gunzip + decode the reassembled network buffer client-side into `Map<Identifier, LevelStemNode>` — the recipe-viewer-integration glue analogous to ALI's `compatibility/common`, consumed by `awi/common-emi`/`common-jei`/`common-rei`).

`GenericUtils` also owns `rendersAsFluid`/`rendersAsBlockModel`, the shared rule for how a `Block` becomes a viewer ingredient — item, else fluid, else 3D model. It lives here because all three viewer modules need the same answer — don't let a viewer module carry its own copy. Order is load-bearing: testing the fluid first renders every block waterlogged in its default state (all 30 coral/coral-fan variants, seagrass, kelp, sea pickle, conduit) as plain water, so the fluid must stay the *last* resort, gated on `RenderShape.INVISIBLE` — an item-less block that still has a model (`tall_seagrass`, `kelp_plant`) belongs in the 3D-model branch, not the fluid one.

### `datagen`
Only `LanguageHolder` — registers `Lang.*` enum classes into `aci.CoreLang.TRANSLATION_MAP` (see `aci/CLAUDE.md`'s "Language wiring"). Unlike ALI, AWI's `datagen` generates no config: the whole user-config surface is the two-field `AwiConfig` described under Module layout above.

### `mixin`
Single `MixinClientPlayNetworkHandler` — injects into `handleUpdateTags` (tail) to trigger `clientRegistry.reloadData()` on resource reload (same role as ALI's mixin of the same name).

### `platform` / `platform/services`
`Services` (`ServiceLoader`-based platform accessor) + `IPlatformHelper extends ICorePlatformHelper<IPlugin>` — an **empty** marker extension: it adds nothing to `aci`'s `getPlugins`/`getConfiguration`, since AWI has no loot domain (ALI's adds `getSpawnEggItem`). Per-loader implementations live in `awi/fabric` and `awi/neoforge` (see `awi/fabric/CLAUDE.md`, `awi/neoforge/CLAUDE.md`; `awi/forge`'s is unported).

## Data-scan entry point

`network.AbstractServer.readWorldgenInfo(ServerLevel level)` is where AWI's whole scan starts: gets `AwiServerRegistry`, runs `BaseLayoutScanner.scan` over the `Registries.LEVEL_STEM` registry (the parallel base-block phase, ~70% of the total time), then iterates the same registry and builds one `LevelStemNode` per dimension from the scanned layouts into a `Map<Identifier, IDataNode>`, drops empty/optimized-away nodes (`ListNode.optimizeList`), encodes the whole tree plus the server's `TooltipCache` into a `FriendlyByteBuf` (palette-first — see `aci/CLAUDE.md`'s tree-model section; the node write itself is `NetworkUtils.writeMapData`), gzips it, and slices it into `WorldgenDataChunkMessage` chunks cached in memory for later per-player sync. Its `finally` runs ACI's `clearCaches` and then `clearData`, so the scan's state is released even when it fails: `Plugin.registerServer` registers `FeatureBytecodeScanner.clearCaches` (the ASM `ClassNode` graph of every visited class) and `SurfaceRuleSpecializer.clearLoggedRules` (the once-per-rule statistics log) as cache cleaners.

It runs **on the server thread**, once at server start (see the root `CLAUDE.md` — only the *transfer* is on demand), and it blocks that thread for the whole duration. It is deliberately **not** re-run on datapack reload: worldgen registries are loaded with the world and a reload never touches them, block tags travel as `TagKey`s resolved on the client (see the tag pipeline above), and `AwiConfig` is read once at mod start. The chunks built at start stay valid, and a client that clears its data on tag sync simply requests them again.

## Test harness

`awi/common`'s test task declares `includeEngines 'junit-platform-suite'`, so **`TooltipTestSuite` is the only runnable entry point** — a `--tests` filter naming an individual class fails with `No tests found`, and a class missing from its `@SelectClasses` cannot be run at all. Every opt-in switch below therefore goes through the suite (see the repo-root `CLAUDE.md` for the exact commands). The three switches are forwarded to the test JVM from `awi/common/build.gradle`.

The base-layout scan is empirical, so it is guarded by a golden file rather than by unit assertions. Both base-layout tests build the world from vanilla data without a server: `VanillaRegistries.createWorldLookup()` supplies the worldgen registries (including `MATERIAL_RULE`/`MATERIAL_CONDITION`, which the specializer's codec round trip resolves references against), the vanilla `WorldPreset` supplies real `LevelStem`s, and `RegistryAccess.ImmutableRegistryAccess` wraps a copy of NOISE alone — the only registry the scan itself asks for, now that the material-rule context needs no chunk. Shared setup lives in `test/utils/BaseLayoutTestUtils`.

- **`BaseLayoutTest`** — scans every vanilla biome of every vanilla dimension over **three fixed seeds** and compares against `src/test/resources/base_layout.json`. Three seeds because coverage is genuinely seed-dependent (nether `soul_sand`, frozen-peaks `ice` are only hit for some seeds, badlands band positions differ per seed); a single seed would let a sampling reduction pass here while losing blocks in other worlds. Regenerate after an intentional change with `-Dawi.baselayout.regenerate=true`. Its second test compares the specialized and unspecialized paths against each other, which is the only guard on `SurfaceRuleSpecializer` — the golden file cannot catch a specializer that silently stops specializing, because that produces the same file. The specializer tests (pruning, ghosts, coins) count nodes on a fully inlined encoding, since vanilla keeps most of the rule behind references; `testSameBlocksInEverySeed` checks the golden file itself, so a block that depends on the seed — which is what a sampled rule that should have a handler looks like — fails it.
- **`SurfaceRuleHandlerTest`** / **`BaseLayoutBandsTest`** — the handler plumbing (a factory returning `null` or throwing, an `expand` that throws) and the badlands bands against the palette.
- **`BaseLayoutSweepTest`** — cost/coverage sweep over candidate `ScanSettings`; asserts nothing, reports. Skipped unless `-Dawi.baselayout.sweep=true`. It diffs **atomic coverage** — `(block, storage, position, water, placement)` with `ANY` expanded into both halves — not just the set of block ids, because a narrowed range or a lost flag is a regression too — a setting can keep reporting every block while silently losing depths or flags.
- **`FeatureBytecodeScanTest`** — golden file `src/test/resources/feature_bytecode_scan.json`, regenerated with `-Dawi.featurescan.regenerate=true`. Widening the walk must only *add* blocks and must leave `methodLimitReached` false everywhere.
- **`test/utils/FeatureInstances`** — one constructed instance per entry of `BuiltInRegistries.FEATURE_TYPE`, shared by `FeatureTooltipTest` and `FeatureBytecodeScanTest`. It exists because the `worldgen/feature` data registry instantiates only 47 of the 58 types, so driving either test off vanilla data alone would silently skip `sculk_patch`, `coral_claw`/`coral_tree`, `template`, `speleothem` and seven others. `FeatureTooltipTest` asserts the map covers the type registry exactly and that each entry's key names the type its instance really is, so a feature type added by Mojang fails loudly instead of dropping out.

## Networking

Mirrors `ali/CLAUDE.md`'s networking pattern exactly — same `AbstractServer`/`AbstractClient` template-method shape, same chunked-gzip-payload-with-palette-first-in-buffer design. The buffer-writing and compression half is genuinely code-shared through `aci.network.NetworkUtils`; the packets, channels and the `AbstractServer`/`AbstractClient` templates themselves are still copy-pasted per mod. The only differences are the payload/entry-point names:

| ALI | AWI |
|---|---|
| `AbstractServer.readLootTables(ReloadableServerRegistries.Holder)` | `AbstractServer.readWorldgenInfo(ServerLevel)` |
| `LootDataChunkMessage(int, byte[])` | `WorldgenDataChunkMessage(int, byte[])` |
| `RequestLootDataMessage()` | `RequestWorldgenDataMessage()` |
| `syncLootTables` server method name | also named `syncLootTables` — **not renamed for AWI**, a naming leftover from copy-pasting ALI's sync logic (`onLootDataChunk`/`startLootData` client-side callbacks are similarly still loot-named). Don't be confused by "loot" naming showing up in AWI's worldgen sync path — it's cosmetic, not a sign the code is misplaced. |

Actual packet/channel registration lives in the loader modules (`awi/fabric`, `awi/neoforge`, plus the unbuilt `awi/forge`), same division of responsibility as ALI.
