# ali/CLAUDE.md

Guidance for working on **ALI** (`AdvancedLootInfo`, `com.yanny.ali`) — the recipe-viewer plugin that displays loot table and villager trade information. See the repo-root `CLAUDE.md` for the multi-mod monorepo layout, and `aci/CLAUDE.md` for the shared tooltip/plugin-manager mechanism this mod instantiates (read that first — this doc assumes it).

## Module layout

- `ali/common` — platform-agnostic mod logic, covered by this file.
- `ali/common-emi`, `ali/common-jei`, `ali/common-rei` — recipe-viewer integrations. See `ali/common-emi/CLAUDE.md` (canonical pattern doc), `ali/common-jei/CLAUDE.md`, `ali/common-rei/CLAUDE.md`.
- `ali/common-lootjs` — optional LootJS compatibility module. See `ali/common-lootjs/CLAUDE.md`.
- `ali/fabric`, `ali/forge` — per-loader entry points. See `ali/fabric/CLAUDE.md`, `ali/forge/CLAUDE.md`.

## `ali/common` package map (`com.yanny.ali`)

### `api`
Public contract layer implemented/consumed by plugins: `IPlugin` (entrypoint: `getModId`, `registerCommon/Client/Server`), `@AliEntrypoint` (ServiceLoader discovery marker), `ICommonRegistry`/`IClientRegistry`/`IServerRegistry` (registration surfaces extending `aci`'s generics), `ICommonUtils`/`IClientUtils`/`IServerUtils` (runtime helper contexts), `IDataNode`/`IItemNode`/`ITradeNode`/`ListNode` (tree node contracts, encode/decode over `FriendlyByteBuf`), `ListWidget` (client widget contract), `ILootModifier`/`IOperation` (the hand-built loot modifier abstraction behind `registerLootModifiers` and LootJS; GLM-derived modifiers are `plugin/glm`'s `IPageLootModifier` instead, see below).

### `manager`
Wires ALI's registries into `aci`'s generic `CorePluginManager` machinery.
- `PluginManager extends CorePluginManager<...>` — singleton; sources plugins from `Services.getPlatform().getPlugins()` and constructs `AliCommonRegistry`/`AliClientRegistry`/`AliServerRegistry`.
- `AliCommonRegistry` — holds `AliConfig` (via `ConfigUtils.readConfiguration()`) and an entity-variant registry (e.g. sheep colors).
- `AliClientRegistry` — client-side widget/data-node factories.
- `AliServerRegistry` — the workhorse: entry/condition/function tooltip builders, value tooltips, chance/count/itemstack modifiers, function/condition/ingredient unwrappers, item listings, and the loot-table/trade parsing entry points `parseTable`/`parseTrade`, plus the tooltip cache.
  - Function and condition unwrappers flatten a wrapper into the functions/conditions it applies. `applyChanceModifier`/`applyCountModifier`/`applyItemStackModifier` and `NodeUtils.hasPredicates` work on the leaves `unwrapFunction`/`unwrapCondition` return, so a modifier nested in a wrapper still counts; tooltips keep the wrapper. An unwrapper returns `null` wherever flattening would not be exact — `any_of`, `inverted`, a reference carrying its own conditions — and references are resolved against the server's `LootDataManager`, where they may form cycles. An unwrapper that throws leaves its value as one leaf, and an item stack modifier that throws is skipped (both logged). A registered entry factory, entry/function/condition/ingredient/value tooltip or item listing that throws gets what an unregistered one gets — the missing node or tooltip, for a listing the `getOffer` fallback first — logged once per class per scan, so one broken renderer never takes its loot table or trader down. The other hooks are cut down to the smallest part they produce, logged once per hook class per scan (`Failed to run <hook> <class>`): an ingredient unwrapper or a page or entity sub-predicate resolver that throws has no opinion, a loot modifier getter contributes no modifiers, a trade override or item-listing supplier leaves its trader with no levels (an override that throws has claimed the trader, so ALI's default levels would show trades it replaces), a level-info function gives that level an opaque offer count, and an `OfTrades` level whose function throws is left out. The same holds for operations: an `IOperation` predicate or factory that throws inside `NodeUtils.processOperations` leaves that item as it was, as if the operation did not apply there, logged once per operation class (the class that built the lambda) per scan. A removed item takes away only the list nodes it leaves without content; leaves that are not items (`EmptyNode`, `DynamicNode`, `MissingNode`, `GlobalLootModifierNode`) stay, and a list holding nothing but `EmptyNode`s counts as empty.
- `FakeLootDataManager` — a `SimpleJsonResourceReloadListener` on the `fake_loot` datapack folder; merges "fake" loot pools declared by other mods' compat shims into real tables at read time (see `datagen.FakeLootProvider` below).

### `plugin/Plugin.java` — the `@AliEntrypoint`
This is where every category and value type from `aci`'s two dispatch tiers actually gets instantiated for ALI. At a survey level:
- `registerCommon` — registers all translation keys from `LanguageHolder.TRANSLATION_MAP`; registers entity variants (`EntityUtils::getSheepVariants`).
- `registerClient` — registers a widget + data-node factory pair for every node ID: loot side (`LootTableNode/EntityLootTableNode/LootPoolNode/ItemNode/EmptyNode/ReferenceNode/DynamicNode/AlternativesNode/SequenceNode/GroupNode/ModifiedNode/GlobalLootModifierNode/MissingNode`) and trade side (`TradeNode/TradeLevelNode/TradeGroupNode/SubTradesNode/ItemsToItemsNode`; `TradeGroupNode` renders through `SubTradesWidget`).
- `registerServer` — the bulk of the file: ACI's `CommonNumberProviders` plus the loot number-provider→`NumberExpr` converters (`ConstantValue, UniformGenerator, BinomialDistributionGenerator, ScoreboardValue`, see "Numbers" below), entry→node builders, 8 entry tooltips (`EntryTooltipUtils`), ~18 condition tooltips and ~24 function tooltips (`ConditionTooltipUtils`/`FunctionTooltipUtils`), an ingredient tooltip, ~35 value tooltips (vanilla-registry values via `RegistriesTooltipUtils`, e.g. `Block/Item/EntityType/Enchantment/Attribute`; structural predicate/misc values via `ValueTooltipUtils`, e.g. `EntityPredicate/ItemPredicate/NumberProvider/MinMaxBounds`), chance/count/item-stack modifier appliers, unwrappers for the vanilla wrappers (`all_of`, predicate/item-modifier references and the composites a JSON-array predicate or item modifier file loads as), the three vanilla global-loot-modifier page resolvers, and villager-trade `IItemListing` registrations covering all 10 `VillagerTrades.*` inner classes (most via generic `TradeUtils`; `EmeraldsForVillagerTypeItem` gets a dedicated node).

Check this file (and `awi/common/.../plugin/Plugin.java` for naming conventions) before adding a new category — see `aci/CLAUDE.md`'s "Adding a new category" recipe.

### `plugin/server` — ALI data-scan tooltip builders
Builds the `TooltipBuilder`/`TooltipNode` tree from vanilla loot-table entries/conditions/functions/ingredients, driven by the registrations above. Key classes: `TooltipUtils` (chance/count/itemstack modifier application and the vanilla unwrappers — the central helper), `EntryTooltipUtils`, `ConditionTooltipUtils`, `FunctionTooltipUtils`, `IngredientTooltipUtils`, `ValueTooltipUtils`, `RegistriesTooltipUtils`, `GenericTooltipUtils`, `MissingTooltipUtils` (fallback), `LootConditionTypes`/`LootFunctionTypes` (registry-type lookup helpers), `LootCount` (a count expression plus the condition tooltips its `Cond` branches point at). Convention: one `getXTooltip`/`collectX`/`applyX`/`unwrapX` static method per vanilla class, registered by exact `.class` in `Plugin.registerServer`.

### `plugin/server/bytecode` — trades worked out from bytecode
`BytecodeInterpreter` covers code nobody wrote a renderer for: `getItemListing` turns an unregistered `ItemListing` into an `ItemsToItemsNode`, `getItemStack` (for shims) turns a `Supplier<ItemStack>` into its possible stacks and their count. `Interpreter` runs the method's bytecode over symbolic values. Fields and statics are read by reflection; every `RandomSource`/`java.util.Random` draw becomes a `NumberExpr` (`nextInt(n)` is `uniform_int(0, n-1)`, a constant added to a range is folded into it, and a number whose bounds are one value is that constant — `Math.min(0, k)` of a non-negative `k` is `0`); a `List.get` or array load at a uniform index becomes a choice of those elements, tied to the draw of that index — loads from several lists at one index stay paired — and every value computed from that choice stays tied to its draw, so a call taking several of them is evaluated once per element, never over every combination; constructing anything other than an `ItemStack` or `MerchantOffer` from a choice or from a uniform integer draw builds one object per value; `ItemStack` and `MerchantOffer` construction and `setCount`/`grow`/`shrink`/`copy` are modelled, and a stack handed to a call that needs a random or unknown value, or a call on a stack that returns one, keeps its item and is marked `Random properties` when the call returns nothing or a stack, which is marked as well, since a call like `setHoverName` changes the stack and returns it (any other result aborts). JDK code runs for real only from a whitelist of pure and read-only methods, or on a stream, which is single-use and so belongs to whoever consumes it, and a pure static method of that whitelist given unknown values and otherwise only numbers, strings or `null` (`String.valueOf(trader.getOffers().size())`) returns an unknown value instead, and so do `String.valueOf` of a random number and a string concatenation with a random or unknown value; Minecraft and mod methods are interpreted, and run for real only when interpreting them fails with every argument concrete — code `getOffer(null, null)` would run anyway. A call is resolved as the JVM selects it: the class and its superclasses first, a JDK class among them ending the search, then a default method of a non-JDK interface. The bytecode comes from the class file, not from what the JVM runs, so a method a mixin changed is never interpreted (`MixinChanges`): one carrying `@MixinMerged` (an overwrite), one an injector annotation's `method` selector or `target` `@Desc` of a mixin applied to its class names (remapped through that mixin config's refmap the way Mixin does), and every method of a class one of whose applied mixins has a selector naming none of its methods — an injector that remaps names by itself, like Fabrication's `@FabInject`. The applied mixins are the ones the class's `@MixinMerged` members name, and a class whose methods cannot be read reflectively (a signature naming a class missing on this side) counts as changed entirely when a mixin configuration targets it; `Mixins.getMixinsForClass` answers only for a mixin's own class, not for its target. Nothing the interpreter did not create is ever written: an `ItemStack` read from a field and then changed gets a shadow copy, any other such write aborts. An object the run created that a change with a random or unknown value cannot be carried out on (a failing call, an array store, a JDK collection taking an unknown element) is uncertain instead: the change is skipped, reading it (an array element, a read-only JDK method) aborts, a call passing it is skipped and leaves its receiver uncertain, and a stack it reaches — passed into a stack call, or an object a stack call returned, like the stack's tag — is marked `Random properties`. A static field the run writes reads back what was written; the real field is never written. Inside a call spread over the elements of a choice, an object that existed before the call is not written either, since every element's run would change the same object (`list.remove(pick)`). A null check, reference comparison or `switch` on a choice is decided outright only when all its elements agree, and a branch only when its operands are concrete or their bounds decide it; otherwise it is a random decision (below), after which the choice, and every choice tied to its draw, keeps only the elements on the side taken. A bit operation on a random value aborts its path. The trader and everything reached from it are unknown values carrying their static type; arithmetic on them stays unknown. Only the server generates offers, so the trader's `Level` is a `ServerLevel` (`instanceof` holds, `isClientSide` is `false`), and its `registryAccess()` is the server's, since registries do not depend on where the trader stands. A Minecraft or mod method that fails on a random or unknown argument, all others concrete, returns an unknown value whose origin is that call (nothing for `void`), unless it returns an `ItemStack`, `MerchantOffer(s)` or a random source; objects of the run it was handed become uncertain. Such a call taking more than one decision is remembered, and when a run then exceeds 8 decisions — or a budget is exceeded inside such a call — the heaviest one becomes opaque: from then on it returns that unknown value without running, and the exploration of the listing or trader starts over (at most 8 times), so a mod method checking every structure of a tag against the world (`mapValid`) is one decision. An unknown value remembers where it came from (`Origin`: receiver, member and arguments, rooted at the trader), and two with the same origin are taken to be the same value. A branch on an unknown or random value (null check, comparison, `instanceof` the type does not decide, a `switch`) is a `Decision` explored both ways — a `switch` once per case key the value can reach, plus the default unless those keys cover its whole range: `getItemListing` re-runs `getOffer` once per path, replaying the decisions taken so far (at most 8 per run, an equality that does not hold not counted, since a chain of them — a lookup in a map of many keys — adds paths one at a time rather than doubling them; 128 runs; a failed run loses only its path — so does one returning something other than nothing or an offer with a stack in every slot — and a listing with a failed path or cut short by the limit shows the offers of the others with `Unable to auto-detect some variants of this trade` added to its condition); a decision with the same test as an earlier one in the run is answered from it, and once an unknown value equals one concrete value it equals no other. A lookup in a concrete `Map` (`get`, `getOrDefault`, `containsKey`, any implementation including fastutil's `get(int)`) by an unknown key is one equality decision per key plus the missing-key case, the keys tried in the order of their text, since a key's hash may be its identity and an exploration cut short by the path limit has to come out the same on every start. A decision is an equality with a concrete value (`==`, `equals`, a map key), a test with one concrete argument (`holder.is(tag)`), a found structure (the null check of `findNearestMapStructure`), a random one (a random value, or a choice whose elements disagree; each is its own decision, never answered from an earlier one, since two draws are independent), or unknown (numbers, `instanceof`, two unknowns). A draw is one call on the random source, recognised by its expression object, which survives being stored, unboxed, widened or shifted by a constant; a branch or `switch` comparing it with a constant narrows the values (an integer draw) or the interval (a float draw) it can still take, so a later comparison of the same draw is decided outright when what is left decides it and otherwise gets the probability conditioned on the earlier ones — `x = nextInt(3); if (x == 0) … else if (x == 1) …` is 1/3 and 1/3, and the path `x != 0, x == 0` does not exist. Paths returning no offer drop out, paths returning the same offer merge, and each offer gets the condition of its paths (`PathCondition`: negations implied by an equality dropped, paths differing in one decision merged, a part common to all paths factored out). A condition value is labelled by its registry — the last segment of the registry's path naming a `Lang.Value` key (`dimension`, `biome`, `villager_type`, `structure`), `Value` otherwise — a random decision shows as `Random chance` whichever way it went, and an unknown one as `Unknown additional predicate`, in the tooltip error color like every other note that something was not worked out. One offer gets its condition added to the listing's; several become a `ConditionalTradesNode` (a `SubTradesNode` carrying the listing's condition) of trades carrying their own. `getTradeLevels` interprets a trader's own `getOffers` when its mod overrides it, `updateTrades` otherwise, with the trader as an unknown value of its entity class: a call on it runs the trader's method when a mod declares it — not Minecraft, Mojang or a loader (`net.minecraft`, `com.mojang`, `net.minecraftforge`, `net.neoforged`, `net.fabricmc`), whose interfaces add default methods to vanilla classes — and stays unknown otherwise, its `RandomSource` field is a random source, and — unless its mod overrides `getOffers` — its `getOffers()` and the field `AbstractVillager.offers` (identified by declaring class, since a mod's own field may share the name) are one symbolic `MerchantOffers`; so is `new` of `MerchantOffers` or of a subclass that does not override `add`. Any other field of the trader the run writes reads back what was written, and a `MerchantOffers` field it has not written is `null`, as on a trader that has never been asked for its offers. When no path of that run offers anything and exactly one other method of the trader declared outside `net.minecraft` writes `AbstractVillager.offers` — a mod filling its offers on interaction (`mobInteract`) — that method is interpreted instead, with unknown arguments, and its trades are what it writes there. `clear` empties the symbolic offers, and sorting, reversing or shuffling them changes nothing, since a level shows no order; `addAll` of a collection whose contents are known adds each of its elements as one trade, and `removeIf` drops the trades its predicate holds for and keeps picks of listings only for `Objects::isNull`, since a listing that offers nothing shows nothing. `Objects.isNull` and `nonNull` are null checks like any other. Vanilla `addOffersFromItemListings(offers, listings, n)` adds a group of `n` picks from those listings. A selection without replacement is a group too, in each of the three shapes mods copy from vanilla versions: `remove(random.nextInt(size()))` — or `remove(element)` of an element drawn from the whole remaining list — from a list the run owns, a set the run fills with `random.nextInt(n)` until it holds `count` indices (then iterated), and `Collections.shuffle` of an owned list followed by `subList(0, k)` — `k` may be random, and then it is the group's count, without a cap at the pool's size, which no draw can exceed anyway. `getOffer` on an element drawn that way, on distinct listings drawn at a uniform index (`listings[random.nextInt(listings.length)]`, as in vanilla's wandering trader), or on a listing read from an array, is a pick of its pool; `add` of picks of one pool counts them into one group (listings read one by one from one array join into a group of exactly those listings), `add` of any other offer is one trade, and the same trade added several times in one path is one trade offered that many times (`TradeGroupNode.repeated`); the same listings added twice in one path give up. Elements of a list of offers drawn without replacement are a group of those offers, counted like picks of listings. A collection the run created that receives an offer, a pick or such an element becomes symbolic offers itself, so every further call on it acts on them, and `addAll` of it adds its trades and groups to the trader's offers. Paths with no trades drop out. A run that fails — an unsupported construct, more than 8 decisions — loses only its own path, and reaching 128 paths stops the exploration; the trader's result is then incomplete. A failed path whose decisions name its level (a held equality with an integer) marks that level, any other failure marks every level, and so does a level that cannot be put together (groups of different chances, the same listings twice in one path, something added that is not an offer with a stack in every slot, which is left out); a marked level shows what was worked out plus a `MissingNode` saying `Unable to auto-detect some custom trades` (a level no path completed shows only that). `getTradeLevels` returns the levels together with that flag (`ComputedTrades`). A random decision whose probability is known — a uniform draw compared with a constant, `random.nextDouble() > includeChance`, a test of a choice drawn at a uniform index (the share of its elements that pass) — weighs its path by that probability, and a group's chance is the summed weight of the paths holding it; every group of a level has to share one chance, which becomes the level's `TradeLevelInfo` chance. A group of the same listings or offers on paths that differ only in random decisions is one group, whose number of offers is the distribution of its counts over those paths (`NumberExpr.Weighted`). Apart from those, a held equality with an integer is a lookup of the level by a value of the trader (`TRADES.get(getTradeLevel())`) and that integer is the path's level (level 1 without one, two give up); every other decision — on what the trader holds, the world, a random value of unknown probability — becomes the `PathCondition` of the groups of that path, merged over the paths holding a group as for listings, and is shown on each of its trades, which makes the level an `OfTrades` one. The probability rides on the decision for listings too, where it changes nothing shown. A group whose listings (an array or a list) came out of a concrete map under an integer key (`TRADES.get(2)`) takes that key as its level, under an enum key its ordinal plus one, as vanilla's wandering trader and the shims built on such maps show them, everything else the level of its path. A level holding one group is an `OfListings` level; several groups or single trades are one `OfTrades` level with a `TradeGroupNode` per group (a group's listings identified by `TradeUtils.listingKey`, so equal listings a mod builds anew on every path are one group whose condition is merged over those paths), except a group whose count is at least the number of its listings, which takes them all and adds them as plain trades. Vanilla's explorer-map API is modelled the way `ItemStack` is: `findNearestMapStructure` yields a position known only by its target, `MapItem.create` a `filled_map`, `renderBiomePreviewMap` nothing, and `addTargetDecoration` puts the target and the decoration into the slot's tooltip, as the renderer of vanilla's `TreasureMapForEmeralds` shows them. The runtime names of the Minecraft methods and fields it models come from `RuntimeNames`, which reads the calls and field reads its own never-called helpers make — loom remaps those, so no mappings are involved; when one cannot be read, auto-detection is off and the server log names the missing ones. The JDK offers no way from a lambda to its target method, so `LambdaResolver` takes the `invokedynamic` sites of the defining class whose interface and captured types match; when several remain, it first looks the lambda up where the defining class's `<clinit>` stored it — a static field of that class assigned it directly, the n-th `add(Object)` to a static `List` of it, or index n of an array then stored into one, read with ASM's `SourceInterpreter` up to the first jump; a list passed to a call or called with anything else in that part is not trusted, nor one whose size at resolution differs from the number of those `add`s — and takes the site whose instance the field, list or array holds (by identity). Otherwise it runs the lambda with `StubRandom` as its random argument (every draw returns its lowest value, then in a second round its second-lowest; the first round runs even when one candidate is left), leaving out every candidate that reads a static `Random`/`RandomSource`, since nothing outside the run is ever changed to make such a field deterministic, twice per round to reject nondeterministic code, and keeps the candidates whose interpretation in the same stub mode returns the same result (compared by `TradeUtils.valueKey`, also between the two real runs) — one, or several whose instructions are identical (operands compared, labels by position, no exception handlers), which differ only in name and so give the same trade. That run only picks the method; nothing it returns is shown. Every run gets a `StubRandom` of its own, which throws after 1000 draws, since mod code looping until a draw comes out differently (a rejection loop, `while (nextInt(50) <= level)` over enchantments compatible with themselves) never ends against a stub returning one value; that run then fails. A real run that throws — the draw limit, a `null` trader — names its target instead: the outermost stack frame of the defining class whose method is a candidate is the method the lambda called (only the proxy's own frame is hidden; two candidates sharing that method's name leave it unresolved), and that candidate is taken without comparing results. Under `logMoreStatistics` the scan logs how many listings were worked out and, once per class and reason, why one was given up or shown only in part (`Computed only some variants of trade item listing`); `-Dali.debug.trades=true` also logs every offer worked out, one line each, for diffing two runs.

### Numbers

Counts, chances, trade prices and every loot number provider are ACI `NumberExpr`s rendered as number nodes (see `aci/CLAUDE.md`'s "Number model"); nothing in ALI formats a range by hand.

- **Two conversions per provider.** Vanilla's `NumberProvider.getInt` is not a rounded `getFloat` for every type — `UniformGenerator.getInt` draws a uniform integer between the rounded bounds — so `registerNumberProvider` takes a float converter and optionally an int one, and `IServerUtils` offers `convertNumber` (float) and `convertIntNumber` (int; `round(float)` when no int converter is registered, like vanilla's default). Both take the conditions list of ACI's `NumberConverter` contract; a tooltip shows a provider through `TooltipUtils.getNumberTooltip`/`getIntNumberTooltip`, which attach it. A consumer calls the variant vanilla calls: `set_count`, `limit_count`/`IntRange`, pool `rolls`, `enchant_with_levels`, `set_enchantments`, `set_stew_effect` and `value_check` use int; `looting_enchant`, `bonus_rolls`, `set_damage` and `set_attributes` use float.
- **Modifiers transform an expression.** `registerCountModifier`/`registerChanceModifier` take a `NumberModifier` `(utils, T, NumberExpr, conditions) → NumberExpr`; `NodeUtils.getCount` starts from `1` and `NodeUtils.getChance` from the entry's weighted chance (a fraction, rendered as a percent), both returning a `LootCount` whose conditions `getCountTooltip`/`getChanceTooltip` attach. An enchantment level is `TooltipUtils.level(enchantment)`, so level rows come from binding it, not from precomputed tables. A modifier that throws turns the value into `Opaque(<function/condition type>)` (logged), never the whole loot table.
- **Conditional functions.** `AliServerRegistry.applyCountModifier` wraps a modifier whose function carries predicates: only `random_chance` predicates give `Weighted(p · modified, (1 − p) · original)`, anything else gives a `Cond` whose branch points at a condition tooltip collected into the `LootCount` and added as a child of the count node. Build the count through `NodeUtils.getCount` and render it with `TooltipUtils.getCountTooltip`, or the branch indices point at nothing.
- **Entry weights.** `registerEntryWeight` (`NumberConverter`) and `registerEntryChildren` are `ClassKeyedMap`-backed, so a registration covers subclasses — a modded `LootPoolSingletonContainer` gets its weight without registering anything. Vanilla: a singleton weighs `max(0, weight + floor(quality · luck))` (`TooltipUtils.luckBased`, `luck` ∈ −1…4, a stepped ACI variable, so a chance or roll count depending on it shows luck 0 plus a `Bad Luck` row and one `Luck n` row per positive value), a composite the sum of its children, `alternatives` the weight of its first unconditioned child (none → `0`) with a `Cond` branch per conditioned child before it, and its children get the pool sum with that weight replaced by their own; an unregistered entry weighs `0`. A pool sums its entries' weights into a conditions list started from its parent chance's conditions, and that list goes read-only to every entry factory (`EntryFactory.create(..., chance, sumWeight, chanceConditions, ...)`) as the index space of both `chance` and `sumWeight`; an entry copies it before adding its own. A node's `float` chance (sorting only) is that expression at luck 0 (`NodeUtils.toFloat`). `getEntryChildren` is what `AbstractServer` walks to collect referenced tables.
- **Clamping.** `set_count` clamps at 0 inside its own transformation, because vanilla clamps on every application and later functions (looting) add on top of the clamped value. The upper bound — the item's max stack, the largest one in a tag — is a consumer limit, never part of the expression: `NodeUtils.getCountLimit` feeds the count tooltip, and the viewers' slot text comes from `plugin/client/TooltipUtils.getSlotCount`.

### `plugin/common` (+ `nodes`, `trades`) — shared client/server tree model
`plugin/common/nodes`: one `IDataNode` implementation per node kind (`LootTableNode, EntityLootTableNode, LootPoolNode, ItemNode, AlternativesNode, SequenceNode, GroupNode, EmptyNode, DynamicNode, ReferenceNode, ModifiedNode, GlobalLootModifierNode, MissingNode`, plus `CompositeNode` base). Convention: each declares `public static final ResourceLocation ID = Utils.modLoc("<snake_case_name>")`, the shared key between its data-node factory and widget factory registered in `Plugin.registerClient`. `plugin/common/trades`: villager-trade equivalents (`TradeNode, TradeLevelNode, TradeGroupNode, SubTradesNode, ItemsToItemsNode, EmeraldsForVillagerTypeItemNode`), plus `TradeUtils` (`getNode` for most `VillagerTrades.ItemListing` subclasses; the slot builders `getSlotNode` for a loot pool entry or for a list of option nodes — joined under a `GroupNode` — `getItemSlotNode` for a list of stacks sharing one count, and `getEmptySlotNode`).

A trader's levels are `api.TradeLevel`s: `OfListings` (an `ItemListing[]`, what `registerTrades` produces) or `OfTrades` (prebuilt trade nodes). `registerTradeOverride` replaces a registered trader's levels at scan time — the overrides are asked in registration order, the first non-`null` answer wins, so a mod that swaps a trader's trades for its own data (VillagerConfig) needs no plugin ordering. Listings equal by `TradeUtils.listingKey` (the `TradeUtils.valueKey` of the listing, which keys any value the same way) — same class and field values, recursing into a mod's own objects that do not define `equals` (records included) and into arrays, collections and maps element by element (sets and maps in any order), `ItemStack`s by item, count and tag, other Minecraft, Mojang, JDK and enum objects by `equals`, and by identity whatever lies deeper than four levels, is met again inside itself or cannot be read, so building a key never fails — are shown once per level or group (`distinctListings`), since mods append the same listings to `VillagerTrades` more than once (Bumblezone on every world load); the selection count still counts them all, as the trader picks from the whole array. A level's children are trades or `TradeGroupNode`s, each picking its own number of trades; the level's selection count is capped at the trades below it, counting into groups. `TradeGroupNode.repeated(times, trade)` is one trade offered `times` times at once, with no cap at its single child, and counts `times` towards the level's cap; the flag is server-side only, since the cap is computed before encoding. An `ItemsToItemsNode` slot is any node subtree — an `ItemNode` for a fixed stack, the node an entry factory builds for a loot pool entry otherwise — and its `IItemNode` leaves are the slot's options (`getSlotOptions`), cycled by the viewers on one clock, so two slots whose items vary together list their options in the same order and number. `NodeUtils`/`EntityUtils`/`ReflectionUtils` are top-level helpers (entry→node dispatch, sheep-variant entity spawning, reading a lambda's captured instances out of its synthetic fields).

An item listing with no registered handler is first worked out from its bytecode (`plugin/server/bytecode`) and falls back to `getOffer(null, null)` only when no path of it gives an offer; that one roll is shown with `Unable to auto-detect this trade, shows one random offer` in the error color added to its condition. Besides the interpreter's identification run, these are the only ways ALI or a plugin reads a listing's offer: nothing passes a real `RandomSource`, since one roll is a sample of a random trade, not the trade. A listing that needs its trader or random source throws there and renders as a `MissingNode`.

`TraderDetector` finds every entity type implementing `Merchant` that no `registerTrades` names and whose page no `tradeCategories` entry hides, so a hidden one is neither created nor interpreted; `AbstractServer.readLootTables` runs it before the trades are parsed, works each one's levels out with `BytecodeInterpreter.getTradeLevels` (see `plugin/server/bytecode`) and shows those under `<namespace>:entity/<path>` of the entity's id like registered trades — a registered trader keeps the bare id, and a profession may share its name with an entity (`wan_ancient_beasts:paleontologist`) — and also the traders whose trades it could work out only in part or not at all: their page carries what was worked out, a level missing some says so, and a trader left without any level — its interpretation throwing or `RuntimeNames` unable to read its helpers included, logged with the cause — gets a single `MissingNode` saying `Unable to auto-detect custom trades` (`AliServerRegistry.parseTrade`). The log names the partial ones with `Computed only some trades of trading entity <id> (<class>)` and those without any level with `Unregistered trading entity <id> (<class>)`; one whose code runs without a decision and offers nothing has no trades to show and is not warned about. It needs no instance for nearly every type: the type's factory is a lambda, the class defining that lambda declares the static field holding the type, and the entity class is the first `Entity` subclass among that field's generic type arguments (`EntityType<X>`, `RegistryObject<EntityType<X>>`, a mod's `MobReg<X>`). The field holds the `EntityType` itself or a registry wrapper reaching it through instance fields within three levels, which are read and never called; a field reaching more than one type is ignored. A type no field claims — registered without a static field, or with a factory that is not a lambda — is created through `createEntities` instead, and their count is logged under `logMoreStatistics`.

`EntityLootTableResolver` maps a loot table id back to the entity types that can drop it — the inverse of asking every entity type what it drops, and the reason the loot scan constructs no sample entities (one entity per registered type with goals/attributes/brains is by far the most expensive thing the scan could do). It runs on the server only: the owning entity type is written into `EntityLootTableNode` and the viewer registration reads it from there, so the client resolves nothing and builds no entity for it. It needs no instance because `EntityType.getDefaultLootTable()` is derived from the registry key and `Mob#getLootTable` is `final`, delegating to `getDefaultLootTable`; the only types that can drop something else are those overriding it, and vanilla's sole case (`Sheep`) puts its per-color tables one path segment below the type's own table, so trimming trailing segments off an unmatched `entities/` table finds the owner **without any variant registration**. A table that still resolves to nothing falls back to building the entities of *that table's namespace only* (`scanNamespace`), so the cost tracks the number of unusual mods, not the registry size — vanilla data never triggers it.

The config's `entityLootTables` (entity type id → loot table ids) is seeded before anything derived and therefore wins over it — that is the escape hatch for a mod whose loot table id follows no convention at all, and it works for tables outside `entities/` too.

Consequences worth knowing before touching it: `registerEntityVariants` is only needed for *rendering* a variant (an unregistered variant entry falls back to any instance of its type, see `EntityStorage`), a table under `entities/` is attributed to its type even when that type is not a `Mob`, and on the loot side the only place needing instances is global loot modifiers — the `ILootModifier<Entity>` predicate and the entity sub-predicate resolvers that read samples — which `AbstractServer` therefore reaches through the lazy, memoised `LootPage#samples` built from `EntityLootTableResolver#getEntities`, never touched when no GLMs are installed. A variant table is matched against the sample instances that report exactly that table (`Mob#getLootTable` is `final`, so an instance always answers for itself), which keeps a modifier bound to one variant off its siblings; when no instance claims the table — a mapping that came from `entityLootTables` or from `fake_loot` — the whole sample of the type is used instead.

Since the attribution travels with the node, `disabledEntities` and `entityLootTables` take effect on the server alone. `entityCategories` still apply on both sides: the server decides what is scanned and sent, the client picks the viewer category for an entry and drops it when the matching category is hidden (`addRecipe` in each viewer module).

### `plugin/glm` — Global Loot Modifier compatibility
Forge/NeoForge GLM datapack modifiers layer: `IGlobalLootModifierPlugin` (extra `IPlugin` extension GLM-integrating mods implement, `registerGlobalLootModifier`), `IGlobalLootModifierWrapper` (loader-agnostic view over one GLM), `LootPage`/`Match`/`Verdict`/`ParamState` (the page model), `IPageLootModifier` (one GLM, judged per page: `test` returns a `PageMatch` — the match plus the conditions that page leaves unexplained — and `getOperations(page, match)` builds the operations from it), `GlobalLootModifierUtils` (turns a GLM's conditions plus its operations into an `IPageLootModifier`, with `getMissingGlobalLootModifier` as the fallback for modifier classes no plugin adapts; its modifiers report `isAutoDetected`, and such a modifier alone never keeps a block page that `hideDefaultBlockLoot` would hide).

A **page** is one entry of the scan: `LootPage(tableId, paramSet, blocks, entityTypes, samples)`, built by `AbstractServer` for every block, entity and gameplay page. `paramSet` is the set vanilla rolls that page with — `BLOCK` for block pages, `ENTITY` for entity pages, the table's own type for gameplay pages, and `ALL_PARAMS` for a table declaring none, which makes the page *generic*. `samples` is a lazy, memoised list of sample entities. Every page carries a table id, so a table-id condition is meaningful on block and entity pages too.

A modifier is evaluated **against each page** in three-valued logic. `Match.NO` means it can never pass there, `Match.YES` that the page selects it, `Match.UNKNOWN` that nothing decides it statically; `Verdict` pairs the match with `explained`, true when the page fully accounts for the condition. A modifier is **bound** on a page when no term answers `NO` and at least one answers `YES`. A modifier that is bound on no page at all falls back to today's unbounded rule: it is attached where nothing rules it out, gated by `showUnboundedGlobalLootModifiers`.

`IServerUtils.testPage` decides one term — a condition, or the modifier object itself — in this order: the `IPageResolver` registered for its exact class through `IServerRegistry.registerPageResolver`, where `null` means "no opinion" and falls through; `AllOfCondition`/`AnyOfCondition`/`InvertedLootItemCondition`, descended in Kleene logic (a composite counts as explained only when every term is an explained `YES`, and inverting anything short of an explained `YES` yields `UNKNOWN`); otherwise the probe. The built-in resolvers live in `plugin/Plugin` (`LootItemBlockStatePropertyCondition`, `LootItemEntityPropertyCondition`, `DamageSourceCondition`).

The **probe** (`LootContextProbe`) runs the condition's own `test` against a `LootContext` built for the page. Its parameter map answers `hasParam` from `ParamState` — `DISALLOWED` is `false`, `REQUIRED` is `true`, `OPTIONAL` and `GENERIC` trap — returns `null` for a disallowed parameter's value and traps on every other read; the `RandomSource` traps on every call and the level is `null`. Returning without trapping is a definitive verdict (`YES` explained, or `NO`); a trap or any other `Throwable` is `UNKNOWN`. The trap is a preallocated `Error` subclass, so a mod's `catch (Exception)` cannot swallow it. This is what decides the loaders' loot-table-id conditions, once an `ILootContextPreparer` registered through `registerLootContextPreparer` has written the page's id into the carrier the condition reads — `ForgePlugin` on Forge, ALICompat's `portinglib` compat on Fabric. The modifier object is never probed, because `doApply` has side effects in real mods; it is decided by page resolvers only.

Entity sub-predicates (`type_specific`) are opt-in through `registerEntitySubPredicateResolver`: samples are bare `EntityType.create` instances carrying no spawn-time or runtime state, so only a resolver that declares the predicate a function of the entity class may read them. Anything unregistered is `UNKNOWN`.

`AbstractServer.readLootTables` collects every page first, evaluates all modifiers against all pages, and only then builds the nodes — the bound-elsewhere rule needs the whole picture before any page is rendered. Candidate items for a page come from parsing its table (plus any `fake_loot` pools for it) with no modifiers applied; a bound modifier survives when one of those items matches one of its operations **or** the page yields no candidates at all, while an unbounded one needs a real item match. The operations are asked for per page with the `PageMatch` the evaluation produced, so the conditions that page explains are left out without deciding them again — a table-id condition disappears on the table it names while an entity predicate carrying more than its type stays visible. A modifier's terms are tested until the first `NO`, and the term that answered `NO` moves to the front of that modifier's order, since consecutive pages of one kind are usually ruled out by the same term; the result does not depend on the order. Nothing on this path is timed per call: `System.nanoTime` on a machine whose clocksource is `hpet` costs about a microsecond, more than a resolver or probe call itself.

A page parses its table without operations at most once (`AbstractServer.PageTable`), for the candidate items and, when no modifier attaches, as the page's node; its `fake_loot` pools are parsed once as well. Everything kept for the scan — the loot table map used for references, the `fake_loot` tables and the tooltip palette — is released in the `finally` of `readLootTables` — the `fake_loot` tables directly, the rest through ACI's `clearCaches` (see `aci/CLAUDE.md`), and a plugin's own scan cache belongs in `registerCacheCleaner`. Hand-built `ILootModifier`s (`registerLootModifiers`, LootJS) keep their own `IType` path. Modifiers that end up on no page are counted into the log.

## Networking (canonical pattern — `awi/CLAUDE.md` mirrors this)

`ali/common/.../network` implements ALI's data-sync protocol — on-demand in its *transfer* only, the data itself is built eagerly at server start (see the root `CLAUDE.md` and step 3 below); packet registration/codec wiring itself lives in the loader modules (`ali/fabric/CLAUDE.md`, `ali/forge/CLAUDE.md`), this package holds the shared logic and abstract template.

**Packets**: `StartMessage(int totalMessages)`, `DoneMessage()` (empty marker), `LootDataChunkMessage(int index, byte[] data)` (chunk payload), `RequestLootDataMessage()` (empty client→server request marker).

**Flow**:
1. Client-side, `compatibility.common.GenericUtils.register(...)` — called while the recipe viewer builds its own data (viewer plugin registration at client/world load, **not** when a loot category is opened) — checks `PluginManager.getInstance().clientRegistry.getCurrentDataFuture()`; if not yet resolved, it calls `AbstractClient.INSTANCE.sendLootDataToPlayer(new RequestLootDataMessage())` and blocks up to 30s per attempt, 3 attempts.
2. Server-side, the loader's `Server` class receives the request (wired via the loader module's own `NetworkUtils.registerCommon` — unrelated to `aci.network.NetworkUtils`, same name, different class) and calls `AbstractServer.syncLootTables(player)`.
3. `AbstractServer.readLootTables(LootDataManager)` (called at world-load/reload time, not per-request) parses all block/entity/gameplay loot tables and trades into `IDataNode`s, writes the tooltip palette header (see `aci/CLAUDE.md`'s tree-model section) followed by the node data into a `FriendlyByteBuf` (both write steps go through `aci.network.NetworkUtils`, see `aci/CLAUDE.md`), gzips it, and slices it into ≤32KB chunks, cached in memory.
4. `syncLootTables` sends `StartMessage(chunks.size())`, then each `LootDataChunkMessage(index, data)`, then `DoneMessage()`.
5. `AbstractClient.onStart`/`onLootDataChunk`/`onDone` forward into `PluginManager.getInstance().clientRegistry` (`startReceivingData`, `addChunkData`, `doneReceivingData`), which reassembles the chunks (`aci.compatibility.DataReceiver`, used inside `CoreClientRegistry`) and completes `getCurrentDataFuture()` with the compressed bytes. The viewer's `GenericUtils.processData` then decompresses and decodes them through `network.LootDataReader`, which references no client-only class, so the same decode runs on a dedicated server.

The two top-level maps are written differently: trades go through `aci.network.NetworkUtils.writeMapData`, while loot tables go through `AbstractServer.writeLootData`, which writes each entry's node ID next to its table id. A top-level node is otherwise not self-describing — `CoreListNode.encode` writes IDs for children only — so without it `LootDataReader` could not tell an `EntityLootTableNode` from a plain `LootTableNode`.

### The item pipeline: nothing item-shaped is sent

The payload carries the node tree and nothing else — the flat item lists a recipe viewer needs (a recipe's outputs, a trade's costs and results, the reverse ingredient index) are derived **client-side** from that same tree, by `compatibility/common/GenericUtils.collectItems`/`collectTradeItems`. This is the same arrangement as AWI's block-tag pipeline (`awi/CLAUDE.md`), for the same two reasons: the lists cannot drift from what is rendered, and a tag is resolved against the *client's* current registry, so it re-resolves on every datapack/tag reload instead of being frozen at scan time.

- `IItemNode.getItem()` is what the slot stands for (`Either<ItemStack, TagKey<? extends ItemLike>>`), `getItems()` the stacks it resolves to (tag members expanded, empty stacks dropped, list mutable), `retainItems(Predicate)` drops the members the viewer hides. Resolution goes through `NodeUtils.resolveItems`, used by both sides.
- `GenericUtils.pruneHiddenItems`/`pruneHiddenTrades` must run before anything asks for the lists — pruning narrows `getItems()` in place, which is what keeps tree, outputs and index in agreement. A node standing for an empty stack is kept: it is the placeholder second input of a single-input trade, and `requiresAllChildren` would drop the whole trade with it.
- In loot tables an empty stack is never an item: `NodeUtils.replaceEmptyItems`, run by `removeEmptyLootTable` after all operations, turns every `IItemNode` standing for one into an `EmptyNode` with the same chance and tooltip. Trades are not passed through it.
- **Inputs vs outputs live on `ITradeNode`, not on the leaf.** A leaf is one stack and cannot know which side of a trade it sat on; `ItemsToItemsNode` adds its children cost-first and encodes how many of the leading ones are costs, so the split survives the wire without relying on child count. The order survives because the node is `isOrdered()`, so `CoreListNode`'s decode does not sort its children by chance.
- The server still walks the tree (`AbstractServer.collectItems`) for two things only: telling an empty loot table from a real one in `removeEmptyLootTable`, and collecting a page's candidate items to match global loot modifiers against (see `plugin/glm`). Neither list is sent.
- There is **no item collector registration at all**, on either side: a table's items come from walking its parsed nodes and a trade's two sides from `ITradeNode`, so nothing in the API answers "what items does this entry/function/`ItemListing` produce". `registerItemListing` (the node factory) is the only trade-side registration.

`AbstractServer`/`AbstractClient` are template-method base classes: they hold all the shared logic above and declare `protected abstract send*` methods that each loader's `Server`/`Client` subclass implements over its native networking API (Fabric's `ServerPlayNetworking`/`ClientPlayNetworking`, Forge's `SimpleChannel`).

## Gametests

The integration test is one server-side GameTest per loader, in a `gametest` source set of `ali/fabric` and `ali/forge` that never reaches the release jar. It boots a headless dedicated server with the real loader, vanilla data and a test datapack, waits for the startup scan, reassembles `AbstractServer.getChunks()`, decodes them through `LootDataReader` with the client registry (`registerClientEvent` on the dedicated server) and renders every loot table and trade page to text, which it compares against the golden files in `ali/<loader>/src/gametest/golden/`. What the run produced is written to `ali/<loader>/build/gametest/golden/`, so `diff -r` between the two shows a failure line by line. `runGametest` deletes the run's `config` directory first, so every run scans with the default configuration, and carries a 10-minute Gradle timeout.

- **Layout.** The logic is `ali/common/src/gametest/java/.../LootDataGolden` (variants, reload) over `LootDataCapture` (decode and render every page — what ALICompat's gametest reuses, so it stays free of KubeJS) and the shared datapack is `ali/common/src/gametest/resources/data/ali_gametest/`; `ali:common` has no gametest source set of its own, both loaders compile these directories into theirs, together with ACI's shared `GoldenFiles`/`GoldenRenderer` (see `aci/CLAUDE.md`'s tests section). Each loader adds only a wrapper carrying the `@GameTest` annotation, plus its own fixtures (see `ali/fabric/CLAUDE.md`, `ali/forge/CLAUDE.md`).
- **Views.** Every page is rendered twice: `normal`, and `advanced` with advanced tooltips and number formulas both on, as F3+H switches them together on the client. Charts are written out as their data, items with their NBT and the count their slot shows (`TooltipUtils.getSlotCount`).
- **Variants.** `default` holds every page. A variant changes one configuration field, reloads the datapacks and stores only the pages that differ from `default`, plus `removed.txt` listing the ones that disappeared; a variant that changes nothing fails. Reloading is required because a scan releases the `fake_loot` tables when it ends, so a second scan without a reload would run without them. After the variants a reload with the defaults has to reproduce the startup output. A loader adds its own variants through the wrapper.
- **Golden files are per loader.** Forge patches vanilla data (shears conditions become `can_tool_perform_action`, suspicious stew carries `forge:effect_id`), so the two sets differ even on vanilla pages.
- **Regenerating.** `-Pali_golden_regenerate=true` rewrites the golden files of every variant. A missing golden directory fails rather than regenerating.
- **LootJS.** LootJS, KubeJS, Rhino and Architectury API are on the gametest run's classpath only (`modGametestRuntimeOnly`, from the same list as each loader's `modCompileOnly` pins). `runGametest` copies `ali/common/src/gametest/kubejs/` into the run directory, whose `server_scripts/lootjs.js` modifies the `ali_gametest:lootjs/*` tables and a few vanilla pages. Every case is its own `LootJS.modifiers` call: KubeJS runs the callbacks in one loop, so a script error in one drops every callback after it. The loader wrapper hands `LootDataGolden.run` the KubeJS server-script errors, which fail the test, so `ali/common`'s gametest code references no KubeJS class.
- **Datapack fixtures.** Each table is named after the case it covers. A table referenced by another one and declaring no `type` is a sub-table and gets no page of its own (`AliServerRegistry.isSubTable`), so a case that lives in referenced tables needs an unreferenced table that reaches them (`references/cycle_entry`).
