# ali/CLAUDE.md

Guidance for working on **ALI** (`AdvancedLootInfo`, `com.yanny.ali`) — the recipe-viewer plugin that displays loot table and villager trade information. See the repo-root `CLAUDE.md` for the multi-mod monorepo layout, and `aci/CLAUDE.md` for the shared tooltip/plugin-manager mechanism this mod instantiates (read that first — this doc assumes it).

## Module layout

- `ali/common` — platform-agnostic mod logic, covered by this file.
- `ali/common-emi`, `ali/common-jei`, `ali/common-rei` — recipe-viewer integrations. See `ali/common-emi/CLAUDE.md` (canonical pattern doc), `ali/common-jei/CLAUDE.md`, `ali/common-rei/CLAUDE.md`.
- `ali/common-lootjs` — optional LootJS compatibility module. See `ali/common-lootjs/CLAUDE.md`.
- `ali/fabric`, `ali/forge` — per-loader entry points. See `ali/fabric/CLAUDE.md`, `ali/forge/CLAUDE.md`.

## `ali/common` package map (`com.yanny.ali`)

### `api`
Public contract layer implemented/consumed by plugins: `IPlugin` (entrypoint: `getModId`, `registerCommon/Client/Server`), `@AliEntrypoint` (ServiceLoader discovery marker), `ICommonRegistry`/`IClientRegistry`/`IServerRegistry` (registration surfaces extending `aci`'s generics), `ICommonUtils`/`IClientUtils`/`IServerUtils` (runtime helper contexts), `IDataNode`/`IItemNode`/`ITradeNode`/`ListNode` (tree node contracts, encode/decode over `FriendlyByteBuf`), `ListWidget` (client widget contract), `ILootModifier`/`IOperation` (the hand-built loot modifier abstraction behind `registerLootModifiers` and LootJS; GLM-derived modifiers are `plugin/glm`'s `IPageLootModifier` instead, see below).

### `manager`
Wires ALI's registries into `aci`'s generic `CorePluginManager` machinery.
- `PluginManager extends CorePluginManager<...>` — singleton; sources plugins from `Services.getPlatform().getPlugins()` and constructs `AliCommonRegistry`/`AliClientRegistry`/`AliServerRegistry`.
- `AliCommonRegistry` — holds `AliConfig` (via `ConfigUtils.readConfiguration()`) and an entity-variant registry (e.g. sheep colors).
- `AliClientRegistry` — client-side widget/data-node factories.
- `AliServerRegistry` — the workhorse: entry/condition/function tooltip builders, value tooltips, chance/count/itemstack modifiers, function/condition/ingredient unwrappers, item listings, and the loot-table/trade parsing entry points `parseTable`/`parseTrade`, plus the tooltip cache.
  - Function and condition unwrappers flatten a wrapper into the functions/conditions it applies. `applyChanceModifier`/`applyCountModifier`/`applyItemStackModifier` and `NodeUtils.hasPredicates` work on the leaves `unwrapFunction`/`unwrapCondition` return, so a modifier nested in a wrapper still counts; tooltips keep the wrapper. An unwrapper returns `null` wherever flattening would not be exact — `any_of`, `inverted`, a reference carrying its own conditions — and references are resolved against the server's `LootDataManager`, where they may form cycles. An unwrapper that throws leaves its value as one leaf, and an item stack modifier that throws is skipped (both logged). A registered entry factory, entry/function/condition/ingredient/value tooltip or item listing that throws gets what an unregistered one gets — the missing node or tooltip, for a listing the `getOffer` fallback first — logged once per class per scan, so one broken renderer never takes its loot table or trader down. The same holds for operations: an `IOperation` predicate or factory that throws inside `NodeUtils.processOperations` leaves that item as it was, as if the operation did not apply there, logged once per operation class (the class that built the lambda) per scan. A removed item takes away only the list nodes it leaves without content; leaves that are not items (`EmptyNode`, `DynamicNode`, `MissingNode`, `GlobalLootModifierNode`) stay, and a list holding nothing but `EmptyNode`s counts as empty.
- `FakeLootDataManager` — a `SimpleJsonResourceReloadListener` on the `fake_loot` datapack folder; merges "fake" loot pools declared by other mods' compat shims into real tables at read time (see `datagen.FakeLootProvider` below).

### `plugin/Plugin.java` — the `@AliEntrypoint`
This is where every category and value type from `aci`'s two dispatch tiers actually gets instantiated for ALI. At a survey level:
- `registerCommon` — registers all translation keys from `LanguageHolder.TRANSLATION_MAP`; registers entity variants (`EntityUtils::getSheepVariants`).
- `registerClient` — registers a widget + data-node factory pair for every node ID: loot side (`LootTableNode/EntityLootTableNode/LootPoolNode/ItemNode/EmptyNode/ReferenceNode/DynamicNode/AlternativesNode/SequenceNode/GroupNode/ModifiedNode/GlobalLootModifierNode/MissingNode`) and trade side (`TradeNode/TradeLevelNode/TradeGroupNode/SubTradesNode/ItemsToItemsNode`; `TradeGroupNode` renders through `SubTradesWidget`).
- `registerServer` — the bulk of the file: ACI's `CommonNumberProviders` plus the loot number-provider→`NumberExpr` converters (`ConstantValue, UniformGenerator, BinomialDistributionGenerator, ScoreboardValue`, see "Numbers" below), entry→node builders, 8 entry tooltips (`EntryTooltipUtils`), ~18 condition tooltips and ~24 function tooltips (`ConditionTooltipUtils`/`FunctionTooltipUtils`), an ingredient tooltip, ~35 value tooltips (vanilla-registry values via `RegistriesTooltipUtils`, e.g. `Block/Item/EntityType/Enchantment/Attribute`; structural predicate/misc values via `ValueTooltipUtils`, e.g. `EntityPredicate/ItemPredicate/NumberProvider/MinMaxBounds`), chance/count/item-stack modifier appliers, unwrappers for the vanilla wrappers (`all_of`, predicate/item-modifier references and the composites a JSON-array predicate or item modifier file loads as), the three vanilla global-loot-modifier page resolvers, and villager-trade `IItemListing` registrations covering all 10 `VillagerTrades.*` inner classes (most via generic `TradeUtils`; `EmeraldsForVillagerTypeItem` gets a dedicated node).

Check this file (and `awi/common/.../plugin/Plugin.java` for naming conventions) before adding a new category — see `aci/CLAUDE.md`'s "Adding a new category" recipe.

### `plugin/server` — ALI data-scan tooltip builders
Builds the `TooltipBuilder`/`TooltipNode` tree from vanilla loot-table entries/conditions/functions/ingredients, driven by the registrations above. Key classes: `TooltipUtils` (chance/count/itemstack modifier application and the vanilla unwrappers — the central helper), `EntryTooltipUtils`, `ConditionTooltipUtils`, `FunctionTooltipUtils`, `IngredientTooltipUtils`, `ValueTooltipUtils`, `RegistriesTooltipUtils`, `GenericTooltipUtils`, `MissingTooltipUtils` (fallback), `LootConditionTypes`/`LootFunctionTypes` (registry-type lookup helpers), `LootCount` (a count expression plus the condition tooltips its `Cond` branches point at). Convention: one `getXTooltip`/`collectX`/`applyX`/`unwrapX` static method per vanilla class, registered by exact `.class` in `Plugin.registerServer`.

### Numbers

Counts, chances, trade prices and every loot number provider are ACI `NumberExpr`s rendered as number nodes (see `aci/CLAUDE.md`'s "Number model"); nothing in ALI formats a range by hand.

- **Two conversions per provider.** Vanilla's `NumberProvider.getInt` is not a rounded `getFloat` for every type — `UniformGenerator.getInt` draws a uniform integer between the rounded bounds — so `registerNumberProvider` takes a float converter and optionally an int one, and `IServerUtils` offers `convertNumber` (float) and `convertIntNumber` (int; `round(float)` when no int converter is registered, like vanilla's default). Both take the conditions list of ACI's `NumberConverter` contract; a tooltip shows a provider through `TooltipUtils.getNumberTooltip`/`getIntNumberTooltip`, which attach it. A consumer calls the variant vanilla calls: `set_count`, `limit_count`/`IntRange`, pool `rolls`, `enchant_with_levels`, `set_enchantments`, `set_stew_effect` and `value_check` use int; `looting_enchant`, `bonus_rolls`, `set_damage` and `set_attributes` use float.
- **Modifiers transform an expression.** `registerCountModifier`/`registerChanceModifier` take a `NumberModifier` `(utils, T, NumberExpr, conditions) → NumberExpr`; `NodeUtils.getCount` starts from `1` and `NodeUtils.getChance` from the entry's weighted chance (a fraction, rendered as a percent), both returning a `LootCount` whose conditions `getCountTooltip`/`getChanceTooltip` attach. An enchantment level is `TooltipUtils.level(enchantment)`, so level rows come from binding it, not from precomputed tables. A modifier that throws turns the value into `Opaque(<function/condition type>)` (logged), never the whole loot table.
- **Conditional functions.** `AliServerRegistry.applyCountModifier` wraps a modifier whose function carries predicates: only `random_chance` predicates give `Weighted(p · modified, (1 − p) · original)`, anything else gives a `Cond` whose branch points at a condition tooltip collected into the `LootCount` and added as a child of the count node. Build the count through `NodeUtils.getCount` and render it with `TooltipUtils.getCountTooltip`, or the branch indices point at nothing.
- **Entry weights.** `registerEntryWeight` (`NumberConverter`) and `registerEntryChildren` are `ClassKeyedMap`-backed, so a registration covers subclasses — a modded `LootPoolSingletonContainer` gets its weight without registering anything. Vanilla: a singleton weighs `max(0, weight + floor(quality · luck))` (`TooltipUtils.luckBased`, `luck` ∈ −1…4, a stepped ACI variable, so a chance or roll count depending on it shows luck 0 plus a `Bad Luck` row and one `Luck n` row per positive value), a composite the sum of its children, `alternatives` the weight of its first unconditioned child (none → `0`) with a `Cond` branch per conditioned child before it, and its children get the pool sum with that weight replaced by their own; an unregistered entry weighs `0`. A pool sums its entries' weights into a conditions list started from its parent chance's conditions, and that list goes read-only to every entry factory (`EntryFactory.create(..., chance, sumWeight, chanceConditions, ...)`) as the index space of both `chance` and `sumWeight`; an entry copies it before adding its own. A node's `float` chance (sorting only) is that expression at luck 0 (`NodeUtils.toFloat`). `getEntryChildren` is what `AbstractServer` walks to collect referenced tables.
- **Clamping.** `set_count` clamps at 0 inside its own transformation, because vanilla clamps on every application and later functions (looting) add on top of the clamped value. The upper bound — the item's max stack, the largest one in a tag — is a consumer limit, never part of the expression: `NodeUtils.getCountLimit` feeds the count tooltip, and the viewers' slot text comes from `plugin/client/TooltipUtils.getSlotCount`.

### `plugin/common` (+ `nodes`, `trades`) — shared client/server tree model
`plugin/common/nodes`: one `IDataNode` implementation per node kind (`LootTableNode, EntityLootTableNode, LootPoolNode, ItemNode, AlternativesNode, SequenceNode, GroupNode, EmptyNode, DynamicNode, ReferenceNode, ModifiedNode, GlobalLootModifierNode, MissingNode`, plus `CompositeNode` base). Convention: each declares `public static final ResourceLocation ID = Utils.modLoc("<snake_case_name>")`, the shared key between its data-node factory and widget factory registered in `Plugin.registerClient`. `plugin/common/trades`: villager-trade equivalents (`TradeNode, TradeLevelNode, TradeGroupNode, SubTradesNode, ItemsToItemsNode, EmeraldsForVillagerTypeItemNode`), plus `TradeUtils` (`getNode` for most `VillagerTrades.ItemListing` subclasses; the slot builders `getSlotNode` for a loot pool entry or for a list of option nodes — joined under a `GroupNode` — `getItemSlotNode` for a list of stacks sharing one count, and `getEmptySlotNode`).

A trader's levels are `api.TradeLevel`s: `OfListings` (an `ItemListing[]`, what `registerTrades` produces) or `OfTrades` (prebuilt trade nodes). `registerTradeOverride` replaces a registered trader's levels at scan time — the overrides are asked in registration order, the first non-`null` answer wins, so a mod that swaps a trader's trades for its own data (VillagerConfig) needs no plugin ordering. A level's children are trades or `TradeGroupNode`s, each picking its own number of trades; the level's selection count is capped at the trades below it, counting into groups. An `ItemsToItemsNode` slot is any node subtree — an `ItemNode` for a fixed stack, the node an entry factory builds for a loot pool entry otherwise — and its `IItemNode` leaves are the slot's options (`getSlotOptions`), cycled by the viewers on one clock, so two slots whose items vary together list their options in the same order and number. `NodeUtils`/`EntityUtils`/`ReflectionUtils` are top-level helpers (entry→node dispatch, sheep-variant entity spawning, reading a lambda's captured instances out of its synthetic fields).

`EntityLootTableResolver` maps a loot table id back to the entity types that can drop it — the inverse of asking every entity type what it drops, and the reason the server scan constructs no sample entities (one entity per registered type with goals/attributes/brains is by far the most expensive thing the scan could do). It runs on the server only: the owning entity type is written into `EntityLootTableNode` and the viewer registration reads it from there, so the client resolves nothing and builds no entity for it. It needs no instance because `EntityType.getDefaultLootTable()` is derived from the registry key and `Mob#getLootTable` is `final`, delegating to `getDefaultLootTable`; the only types that can drop something else are those overriding it, and vanilla's sole case (`Sheep`) puts its per-color tables one path segment below the type's own table, so trimming trailing segments off an unmatched `entities/` table finds the owner **without any variant registration**. A table that still resolves to nothing falls back to building the entities of *that table's namespace only* (`scanNamespace`), so the cost tracks the number of unusual mods, not the registry size — vanilla data never triggers it.

The config's `entityLootTables` (entity type id → loot table ids) is seeded before anything derived and therefore wins over it — that is the escape hatch for a mod whose loot table id follows no convention at all, and it works for tables outside `entities/` too.

Consequences worth knowing before touching it: `registerEntityVariants` is only needed for *rendering* a variant (an unregistered variant entry falls back to any instance of its type, see `EntityStorage`), a table under `entities/` is attributed to its type even when that type is not a `Mob`, and the only place needing instances is global loot modifiers — the `ILootModifier<Entity>` predicate and the entity sub-predicate resolvers that read samples — which `AbstractServer` therefore reaches through the lazy, memoised `LootPage#samples` built from `EntityLootTableResolver#getEntities`, never touched when no GLMs are installed. A variant table is matched against the sample instances that report exactly that table (`Mob#getLootTable` is `final`, so an instance always answers for itself), which keeps a modifier bound to one variant off its siblings; when no instance claims the table — a mapping that came from `entityLootTables` or from `fake_loot` — the whole sample of the type is used instead.

Since the attribution travels with the node, `disabledEntities` and `entityLootTables` take effect on the server alone. `entityCategories` still apply on both sides: the server decides what is scanned and sent, the client picks the viewer category for an entry and drops it when the matching category is hidden (`addRecipe` in each viewer module).

### `plugin/client` (+ `widget`, `widget/trades`)
Client-side rendering. `ClientUtils`/`WidgetUtils` helpers; one `ListWidget`/`IWidgetFactory` per node ID mirroring `plugin/common/nodes` (`LootTableWidget, LootPoolWidget, ItemWidget, AlternativesWidget, SequentialWidget, GroupWidget, EmptyWidget, DynamicWidget, ReferenceWidget, ModifiedWidget, GlobalLootModifierWidget, MissingWidget, TextureWidget`), plus `widget/trades` (`TradeWidget, TradeLevelWidget, SubTradesWidget, ItemListingWidget`). The pairing is one widget per node ID rather than per class - `EntityLootTableNode` renders through `LootTableWidget`, the same widget its superclass uses.

### `plugin/glm` — Global Loot Modifier compatibility
Forge/NeoForge GLM datapack modifiers layer: `IGlobalLootModifierPlugin` (extra `IPlugin` extension GLM-integrating mods implement, `registerGlobalLootModifier`), `IGlobalLootModifierWrapper` (loader-agnostic view over one GLM), `LootPage`/`Match`/`Verdict`/`ParamState` (the page model), `IPageLootModifier` (one GLM, judged per page: `test` returns a `PageMatch` — the match plus the conditions that page leaves unexplained — and `getOperations(page, match)` builds the operations from it), `GlobalLootModifierUtils` (turns a GLM's conditions plus its operations into an `IPageLootModifier`, with `getMissingGlobalLootModifier` as the fallback for modifier classes no plugin adapts; its modifiers report `isAutoDetected`, and such a modifier alone never keeps a block page that `hideDefaultBlockLoot` would hide).

A **page** is one entry of the scan: `LootPage(tableId, paramSet, blocks, entityTypes, samples)`, built by `AbstractServer` for every block, entity and gameplay page. `paramSet` is the set vanilla rolls that page with — `BLOCK` for block pages, `ENTITY` for entity pages, the table's own type for gameplay pages, and `ALL_PARAMS` for a table declaring none, which makes the page *generic*. `samples` is a lazy, memoised list of sample entities. Every page carries a table id, so a table-id condition is meaningful on block and entity pages too.

A modifier is evaluated **against each page** in three-valued logic. `Match.NO` means it can never pass there, `Match.YES` that the page selects it, `Match.UNKNOWN` that nothing decides it statically; `Verdict` pairs the match with `explained`, true when the page fully accounts for the condition. A modifier is **bound** on a page when no term answers `NO` and at least one answers `YES`. A modifier that is bound on no page at all falls back to today's unbounded rule: it is attached where nothing rules it out, gated by `showUnboundedGlobalLootModifiers`.

`IServerUtils.testPage` decides one term — a condition, or the modifier object itself — in this order: the `IPageResolver` registered for its exact class through `IServerRegistry.registerPageResolver`, where `null` means "no opinion" and falls through; `AllOfCondition`/`AnyOfCondition`/`InvertedLootItemCondition`, descended in Kleene logic (a composite counts as explained only when every term is an explained `YES`, and inverting anything short of an explained `YES` yields `UNKNOWN`); otherwise the probe. The built-in resolvers live in `plugin/Plugin` (`LootItemBlockStatePropertyCondition`, `LootItemEntityPropertyCondition`, `DamageSourceCondition`).

The **probe** (`LootContextProbe`) runs the condition's own `test` against a `LootContext` built for the page. Its parameter map answers `hasParam` from `ParamState` — `DISALLOWED` is `false`, `REQUIRED` is `true`, `OPTIONAL` and `GENERIC` trap — returns `null` for a disallowed parameter's value and traps on every other read; the `RandomSource` traps on every call and the level is `null`. Returning without trapping is a definitive verdict (`YES` explained, or `NO`); a trap or any other `Throwable` is `UNKNOWN`. The trap is a preallocated `Error` subclass, so a mod's `catch (Exception)` cannot swallow it. This is what decides the loaders' loot-table-id conditions, once an `ILootContextPreparer` registered through `registerLootContextPreparer` has written the page's id into the carrier the condition reads — `ForgePlugin` on Forge, ALICompat's `portinglib` compat on Fabric. The modifier object is never probed, because `doApply` has side effects in real mods; it is decided by page resolvers only.

Entity sub-predicates (`type_specific`) are opt-in through `registerEntitySubPredicateResolver`: samples are bare `EntityType.create` instances carrying no spawn-time or runtime state, so only a resolver that declares the predicate a function of the entity class may read them. Anything unregistered is `UNKNOWN`.

`AbstractServer.readLootTables` collects every page first, evaluates all modifiers against all pages, and only then builds the nodes — the bound-elsewhere rule needs the whole picture before any page is rendered. Candidate items for a page come from parsing its table (plus any `fake_loot` pools for it) with no modifiers applied; a bound modifier survives when one of those items matches one of its operations **or** the page yields no candidates at all, while an unbounded one needs a real item match. The operations are asked for per page with the `PageMatch` the evaluation produced, so the conditions that page explains are left out without deciding them again — a table-id condition disappears on the table it names while an entity predicate carrying more than its type stays visible. A modifier's terms are tested until the first `NO`, and the term that answered `NO` moves to the front of that modifier's order, since consecutive pages of one kind are usually ruled out by the same term; the result does not depend on the order. Nothing on this path is timed per call: `System.nanoTime` on a machine whose clocksource is `hpet` costs about a microsecond, more than a resolver or probe call itself.

A page parses its table without operations at most once (`AbstractServer.PageTable`), for the candidate items and, when no modifier attaches, as the page's node; its `fake_loot` pools are parsed once as well. Everything kept for the scan — the loot table map used for references, the `fake_loot` tables and the tooltip palette — is released in the `finally` of `readLootTables` — the `fake_loot` tables directly, the rest through ACI's `clearCaches` (see `aci/CLAUDE.md`), and a plugin's own scan cache belongs in `registerCacheCleaner`. Hand-built `ILootModifier`s (`registerLootModifiers`, LootJS) keep their own `IType` path. Modifiers that end up on no page are counted into the log.

- `datagen.FakeLootProvider` — a `DataProvider` generating datapack JSON under `fake_loot/` for drops not expressible as a real loot table (e.g. mob-equipment drops for fox/piglin/skeleton/zombie/wither/drowned/etc), consumed back by `FakeLootDataManager`.

## Networking (canonical pattern — `awi/CLAUDE.md` mirrors this)

`ali/common/.../network` implements ALI's data-sync protocol — on-demand in its *transfer* only, the data itself is built eagerly at server start (see the root `CLAUDE.md` and step 3 below); packet registration/codec wiring itself lives in the loader modules (`ali/fabric/CLAUDE.md`, `ali/forge/CLAUDE.md`), this package holds the shared logic and abstract template.

**Packets**: `StartMessage(int totalMessages)`, `DoneMessage()` (empty marker), `LootDataChunkMessage(int index, byte[] data)` (chunk payload), `RequestLootDataMessage()` (empty client→server request marker).

**Flow**:
1. Client-side, `compatibility.common.GenericUtils.register(...)` — called while the recipe viewer builds its own data (viewer plugin registration at client/world load, **not** when a loot category is opened) — checks `PluginManager.getInstance().clientRegistry.getCurrentDataFuture()`; if not yet resolved, it calls `AbstractClient.INSTANCE.sendLootDataToPlayer(new RequestLootDataMessage())` and blocks up to 30s per attempt, 3 attempts.
2. Server-side, the loader's `Server` class receives the request (wired via the loader module's own `NetworkUtils.registerCommon` — unrelated to `aci.network.NetworkUtils`, same name, different class) and calls `AbstractServer.syncLootTables(player)`.
3. `AbstractServer.readLootTables(LootDataManager)` (called at world-load/reload time, not per-request) parses all block/entity/gameplay loot tables and trades into `IDataNode`s, writes the tooltip palette header (see `aci/CLAUDE.md`'s tree-model section) followed by the node data into a `FriendlyByteBuf` (both write steps go through `aci.network.NetworkUtils`, see `aci/CLAUDE.md`), gzips it, and slices it into ≤32KB chunks, cached in memory.
4. `syncLootTables` sends `StartMessage(chunks.size())`, then each `LootDataChunkMessage(index, data)`, then `DoneMessage()`.
5. `AbstractClient.onStart`/`onLootDataChunk`/`onDone` forward into `PluginManager.getInstance().clientRegistry` (`startLootData`, `addChunkData`, `doneLootData`), which decompresses and decodes the reassembled buffer into the cached node tree (client-side chunk reassembly itself is `aci.compatibility.DataReceiver`, used inside `CoreClientRegistry`).

The two top-level maps are written differently: trades go through `aci.network.NetworkUtils.writeMapData`, while loot tables go through `AbstractServer.writeLootData`, which writes each entry's node ID next to its table id. A top-level node is otherwise not self-describing — `CoreListNode.encode` writes IDs for children only — so without it `GenericUtils.readLootData` could not tell an `EntityLootTableNode` from a plain `LootTableNode`.

### The item pipeline: nothing item-shaped is sent

The payload carries the node tree and nothing else — the flat item lists a recipe viewer needs (a recipe's outputs, a trade's costs and results, the reverse ingredient index) are derived **client-side** from that same tree, by `compatibility/common/GenericUtils.collectItems`/`collectTradeItems`. This is the same arrangement as AWI's block-tag pipeline (`awi/CLAUDE.md`), for the same two reasons: the lists cannot drift from what is rendered, and a tag is resolved against the *client's* current registry, so it re-resolves on every datapack/tag reload instead of being frozen at scan time.

- `IItemNode.getItem()` is what the slot stands for (`Either<ItemStack, TagKey<? extends ItemLike>>`), `getItems()` the stacks it resolves to (tag members expanded, empty stacks dropped, list mutable), `retainItems(Predicate)` drops the members the viewer hides. Resolution goes through `NodeUtils.resolveItems`, used by both sides.
- `GenericUtils.pruneHiddenItems`/`pruneHiddenTrades` must run before anything asks for the lists — pruning narrows `getItems()` in place, which is what keeps tree, outputs and index in agreement. A node standing for an empty stack is kept: it is the placeholder second input of a single-input trade, and `requiresAllChildren` would drop the whole trade with it.
- In loot tables an empty stack is never an item: `NodeUtils.replaceEmptyItems`, run by `removeEmptyLootTable` after all operations, turns every `IItemNode` standing for one into an `EmptyNode` with the same chance and tooltip. Trades are not passed through it.
- **Inputs vs outputs live on `ITradeNode`, not on the leaf.** A leaf is one stack and cannot know which side of a trade it sat on; `ItemsToItemsNode` adds its children cost-first and encodes how many of the leading ones are costs, so the split survives the wire without relying on child count. The order survives because the node is `isOrdered()`, so `CoreListNode`'s decode does not sort its children by chance.
- The server still walks the tree (`AbstractServer.collectItems`) for two things only: telling an empty loot table from a real one in `removeEmptyLootTable`, and collecting a page's candidate items to match global loot modifiers against (see `plugin/glm`). Neither list is sent.
- There is **no item collector registration at all**, on either side: a table's items come from walking its parsed nodes and a trade's two sides from `ITradeNode`, so nothing in the API answers "what items does this entry/function/`ItemListing` produce". `registerItemListing` (the node factory) is the only trade-side registration.

`AbstractServer`/`AbstractClient` are template-method base classes: they hold all the shared logic above and declare `protected abstract send*` methods that each loader's `Server`/`Client` subclass implements over its native networking API (Fabric's `ServerPlayNetworking`/`ClientPlayNetworking`, Forge's `SimpleChannel`).

## `mixin`
`MixinBushBlock` (invoker accessor exposing protected `mayPlaceOn` for loot-modifier predicate checks). `MixinClientPlayNetworkHandler` (injects into `handleUpdateTags` tail to trigger `clientRegistry.reloadData()` on tag reload). `MixinGuiGraphics` (client; feeds `ScrollableTooltip` the components of the tooltip being rendered — see `aci/CLAUDE.md`).

## `platform` / `platform/services`
`Services` (static holder loading `IPlatformHelper` via `ServiceLoader`), `IPlatformHelper` (loader-specific operations: get plugins, config dir, fake-loot-table parsing) — implemented per-loader, see `ali/fabric/CLAUDE.md`/`ali/forge/CLAUDE.md`.
