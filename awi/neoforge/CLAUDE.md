# awi/neoforge/CLAUDE.md

Guidance for `awi/neoforge` (`com.yanny.awi.neoforge`) — AWI's NeoForge loader entry point. See `awi/CLAUDE.md` for the mod logic this glues into, and `aci/CLAUDE.md`'s "platform" section for the `ICorePlatformHelper`/`Services` abstraction being implemented here. This module is a near copy-paste of `ali/neoforge` (see `ali/neoforge/CLAUDE.md`) with the loot domain stripped out — **when something misbehaves here, diff against `ali/neoforge` first**, that module is the maintained reference and every non-loot difference between the two is a porting gap rather than intentional. `awi/forge` is the Forge-vs-NeoForge-API sibling but is not built on this branch (see `awi/forge/CLAUDE.md`); `awi/fabric/CLAUDE.md` is the other live loader.

## Entry point

Single `AwiMod` (`@Mod`, constructor takes the mod `IEventBus`). Unlike Forge it builds **no** `SimpleChannel`: `SERVER`/`CLIENT` are plain instances and payload registration happens in `RegisterPayloadHandlersEvent` (`registrar(MOD_ID).optional().versioned("1")`). Mod-bus listeners: `DataGeneration::generate` (typed `GatherDataEvent.Client`, like `ali/neoforge`'s — `GatherDataEvent` is abstract with `Client`/`Server` subclasses, and a listener on the abstract class fails mod loading outright with `Cannot register listeners for abstract class ...`), common/client setup → `PluginManager`, and `RegisterPictureInPictureRenderersEvent` → `BlockRenderState`/`BlockPictureInPictureRenderer` (the NeoForge counterpart of `awi/fabric`'s `SpecialGuiElementRegistry.register`; without it the block-in-GUI slots in the JEI/REI views have no renderer). There is no `AddServerReloadListenersEvent` listener — that one exists in `ali/neoforge` only, to register its fake-loot data manager; AWI has nothing to reload.

`NeoForgeCommonBusSubscriber` (`ServerStartingEvent` → `registerServerEvent` + `SERVER.readWorldgenInfo(overworld)`, `ServerStoppingEvent` → `deregisterServerEvent`) and `NeoForgeClientBusSubscriber` (`ClientPlayerNetworkEvent.LoggingIn`/`LoggingOut`) are the game-bus halves, both `@EventBusSubscriber(bus = Bus.GAME)`. There is no client level-unload handler — AWI has no per-level client cache to drop (`ali/neoforge` has one for `EntityStorage`).

## Platform + networking implementation

- `platform.NeoForgePlatformHelper implements IPlatformHelper` — only `getPlugins` (`ModFileScanData`/`@AwiEntrypoint` ASM type match, memoized) and `getConfiguration` (`FMLPaths.CONFIGDIR`), because AWI's `IPlatformHelper` adds nothing to `ICorePlatformHelper`.
- `platform.NeoForgeClientPlatformHelper implements IClientPlatformHelper` — `renderBlockInGui` via `guiGraphics.submitPictureInPictureRenderState(...)` (NeoForge exposes the helper method; `awi/fabric` goes through `guiGraphics.guiRenderState.submitPicturesInPictureState(...)`). Both platform services are registered in `META-INF/services/`; a missing service file here is not a compile error, it throws at first render from `Services.getClientPlatform()`.

Plugin discovery is by **annotation**, so a new plugin class must also be added to `fabric.mod.json`'s `awi` entrypoint for Fabric.
- `network.{Client,Server,NetworkUtils}` — the 4 worldgen messages registered as native `CustomPacketPayload`s: `registrar.executesOn(HandlerThread.NETWORK).playToClient/playToServer(TYPE, CODEC, handler)`. No codec casting is needed (NeoForge accepts the `StreamCodec<RegistryFriendlyByteBuf, ...>` that `awi/common` declares) and there is no `setPacketHandled` boilerplate — this is the main reason the classes are shorter than `awi/forge`'s. Sends go through `PacketDistributor.sendToPlayer`/`sendToServer`, each guarded by `hasChannel(<payload>.TYPE)` so nothing is written to a client without the mod. The client's login check uses `NetworkRegistry.hasChannel(connection, ConnectionProtocol.PLAY, RequestWorldgenDataMessage.TYPE.id())`.

## Mixins

None — `awi/neoforge` has no `mixin` package and no mixin config of its own, same as `awi/forge`: the worldgen scan is not re-run on datapack reload. Mixin configs are declared **once** here, in `META-INF/neoforge.mods.toml`'s `[[mixins]]` blocks — there is no `loom { forge { mixinConfig ... } }`/manifest duplication like on Forge. On this branch that list is exactly `awi.mixins.json`, matching `neoforge_emi_enabled=false`; `awi.emi.mixins.json` is out of it because `awi/common-emi` is not shadowed in. Re-enabling EMI for NeoForge means adding that block back, or `MixinRecipeScreen` silently never applies (`ali/neoforge` is in the same state).

## Access transformers

NeoForge does not read access wideners, so the jar ships `META-INF/accesstransformer.cfg`, generated by loom from `awi/common`'s `awi.accesswidener` — `build.gradle` declares `loom { neoForge { convertAccessWideners(tasks.named("remapJar"), "awi.accesswidener") } }`, and the accesswidener itself is dropped from the NeoForge jar. See `ali/neoforge/CLAUDE.md`'s section of the same name for the conversion rules and the loom/Gradle version requirement.

## Viewer wiring

JEI and REI are enabled for NeoForge on this branch (`neoforge_jei_enabled`/`neoforge_rei_enabled=true`) but EMI is not (`neoforge_emi_enabled=false`), so `runAwiNeoforgeJeiClient`/`runAwiNeoforgeReiClient` exist and there is no EMI run task. JEI (`@JeiPlugin`) is discovered by annotation from the shadowed common module; REI needs `compatibility.ReiCompatibilityWrapper`, a `@REIPluginClient`-annotated subclass of `awi/common-rei`'s `ReiCompatibility`, because that annotation is loader-specific and cannot live in `awi/common-rei` (mirrors `ali/neoforge`). EMI would be annotation-discovered (`@EmiEntrypoint`) if re-enabled.
