# ali/CLAUDE.md

Guidance for working on **ALI** (`AdvancedLootInfo`, `com.yanny.ali`) — the recipe-viewer plugin that displays loot table and villager trade information. See the repo-root `CLAUDE.md` for the multi-mod monorepo layout, and `aci/CLAUDE.md` for the shared tooltip/plugin-manager mechanism this mod instantiates (read that first — this doc assumes it).

## Module layout

- `ali/common` — platform-agnostic mod logic, covered by this file.
- `ali/common-emi`, `ali/common-jei`, `ali/common-rei` — recipe-viewer integrations. See `ali/common-emi/CLAUDE.md` (canonical pattern doc), `ali/common-jei/CLAUDE.md`, `ali/common-rei/CLAUDE.md`.
- `ali/common-lootjs` — optional LootJS compatibility module, **not built on this branch** (`lootjs_enabled=false`). See `ali/common-lootjs/CLAUDE.md`.
- `ali/fabric`, `ali/neoforge` — per-loader entry points. See `ali/fabric/CLAUDE.md`, `ali/neoforge/CLAUDE.md`. `ali/forge` still exists in the tree but is excluded from the build on this branch and unported to 1.21.11 — see `ali/forge/CLAUDE.md`.
- `ali/common-emi` is also excluded on this branch (`emi_enabled=false`).

## `ali/common` package map (`com.yanny.ali`)

### `api`
Public contract layer implemented/consumed by plugins: `IPlugin` (entrypoint: `getModId`, `registerCommon/Client/Server`), `@AliEntrypoint` (ServiceLoader discovery marker), `ICommonRegistry`/`IClientRegistry`/`IServerRegistry` (registration surfaces extending `aci`'s generics), `ICommonUtils`/`IClientUtils`/`IServerUtils` (runtime helper contexts), `IDataNode`/`IItemNode`/`ITradeNode`/`ListNode` (tree node contracts, encode/decode over `FriendlyByteBuf`), `ListWidget` (client widget contract), `ILootModifier`/`IOperation` (the hand-built loot modifier abstraction behind `registerLootModifiers` and LootJS; GLM-derived modifiers are `plugin/glm`'s `IPageLootModifier` instead, see below).

### `manager`
Wires ALI's registries into `aci`'s generic `CorePluginManager` machinery.
- `PluginManager extends CorePluginManager<...>` — singleton; sources plugins from `Services.getPlatform().getPlugins()` and constructs `AliCommonRegistry`/`AliClientRegistry`/`AliServerRegistry`.
- `AliCommonRegistry` — holds `AliConfig` (via `ConfigUtils.readConfiguration()`) and an entity-variant registry (`registerEntityVariants` factories).
- `AliClientRegistry` — client-side widget/data-node factories.
- `AliServerRegistry` — the workhorse: item collectors, entry/condition/function tooltip builders, value tooltips, chance/count/itemstack modifiers, function/condition/ingredient unwrappers, item listings, and the loot-table/trade parsing entry points `parseTable`/`parseTrade`, plus the tooltip cache.
  - Function and condition unwrappers flatten a wrapper into the functions/conditions it applies. `applyChanceModifier`/`applyCountModifier`/`applyItemStackModifier` and `NodeUtils.hasPredicates` work on the leaves `unwrapFunction`/`unwrapCondition` return, so a modifier nested in a wrapper still counts; tooltips keep the wrapper. An unwrapper returns `null` wherever flattening would not be exact — `any_of`, `inverted`, a reference carrying its own conditions — and references are resolved against the server's reloadable registries (`reloadableRegistries().lookup()`), where they may form cycles. An unwrapper that throws leaves its value as one leaf, and an item stack modifier that throws is skipped (both logged). A registered entry factory, entry/function/condition/ingredient/value tooltip or item listing that throws gets what an unregistered one gets — the missing node or tooltip, for a listing the `getOffer` fallback first — logged once per class per scan, so one broken renderer never takes its loot table or trader down. The other hooks are cut down to the smallest part they produce, logged once per hook class per scan (`Failed to run <hook> <class>`): an ingredient unwrapper or a page or entity sub-predicate resolver that throws has no opinion, a loot modifier getter contributes no modifiers, a trade override or item-listing supplier leaves its trader with no levels (an override that throws has claimed the trader, so ALI's default levels would show trades it replaces), a level-info function gives that level an opaque offer count, and an `OfTrades` level whose function throws is left out. The same holds for operations: an `IOperation` predicate or factory that throws inside `NodeUtils.processOperations` leaves that item as it was, as if the operation did not apply there, logged once per operation class (the class that built the lambda) per scan. A removed item takes away only the list nodes it leaves without content; leaves that are not items (`EmptyNode`, `DynamicNode`, `MissingNode`, `GlobalLootModifierNode`) stay, and a list holding nothing but `EmptyNode`s counts as empty.
  - `getIngredientTooltip` runs the `registerIngredientUnwrapper` hooks before the usual exact-class dispatch; each returns the object a loader-specific composite `Ingredient` really wraps, or `null`; a non-`null` result is rendered by the value tooltip registered for its class, and one without any falls back to the auto-detected JSON tooltip of the wrapping `Ingredient` (`getMissingIngredientTooltip`), which the loader's `Ingredient` codec serializes including the custom part. That exists because `registerIngredientTooltip` is keyed by the exact `Class<? extends Ingredient>`, which cannot tell custom ingredients apart on loaders where every one of them arrives in the same class: Fabric's `CustomIngredientImpl` and NeoForge's plain `Ingredient` wrapping an `ICustomIngredient`. `ali/fabric` and `ali/neoforge` therefore register an unwrapper plus ordinary **value** tooltips for their ingredient types; Forge's `AbstractIngredient` subclasses are still dispatched directly. Deliberately *not* solved by having the loader plugin re-register `Ingredient.class`: that override would win only if it happened to land after `ali/common`'s, and plugin order comes from an unordered annotation/entrypoint scan. Nor by making `ingredientTooltips` a `ClassKeyedMap` — supertype resolution cannot bridge a wrapper→wrapped hop, and it would also turn the missing-entry JSON fallback for unrecognised `Ingredient` subclasses into a blank vanilla tooltip.
- `FakeLootDataManager` — a `SimpleJsonResourceReloadListener` on the `fake_loot` datapack folder; merges "fake" loot pools declared by other mods' compat shims into real tables at read time (see `datagen.FakeLootProvider` below). Obtained via `AbstractServer.getFakeLootDataManager(HolderLookup.Provider)` — the provider is passed in by each loader's reload wiring, which is why ALI no longer needs a `getLookupProvider()` platform method.

### `plugin/Plugin.java` — the `@AliEntrypoint`
This is where every category and value type from `aci`'s two dispatch tiers actually gets instantiated for ALI. At a survey level:
- `registerCommon` — registers all translation keys from `LanguageHolder.TRANSLATION_MAP`.
- `registerClient` — registers a widget + data-node factory pair for every node ID: loot side (`LootTableNode/EntityLootTableNode/LootPoolNode/ItemNode/EmptyNode/ReferenceNode/DynamicNode/AlternativesNode/SequenceNode/GroupNode/ModifiedNode/GlobalLootModifierNode/MissingNode`) and trade side (`TradeNode/TradeLevelNode/TradeGroupNode/SubTradesNode/ItemsToItemsNode`; `TradeGroupNode` renders through `SubTradesWidget`).
- `registerServer` — the bulk of the file: ACI's `CommonNumberProviders` plus the loot number-provider→`NumberExpr` converters (`ConstantValue, UniformGenerator, BinomialDistributionGenerator, ScoreboardValue, StorageValue, EnchantmentLevelProvider`) and the `LevelBasedValue` converters (see "Numbers" below), entry→node builders, 8 entry tooltips (`EntryTooltipUtils`), ~18 condition tooltips and ~24 function tooltips (`ConditionTooltipUtils`/`FunctionTooltipUtils`), an ingredient tooltip, ~35 value tooltips (vanilla-registry values via `RegistriesTooltipUtils`, e.g. `Block/Item/EntityType/Enchantment/Attribute`; structural predicate/misc values via `ValueTooltipUtils`, e.g. `EntityPredicate/ItemPredicate/NumberProvider/MinMaxBounds`), chance/count/item-stack modifier appliers, unwrappers for the vanilla wrappers (`all_of`, predicate/item-modifier references and the composites a JSON-array predicate or item modifier file loads as), the three vanilla global-loot-modifier page resolvers, and villager-trade `IItemListing` registrations covering all 11 `VillagerTrades.*` inner classes (most via generic `TradeUtils`; `EmeraldsForVillagerTypeItem` gets a dedicated node; `FailureItemListing`, which offers nothing, becomes an `EmptyNode` that `SubTradesNode` and `TradeLevelNode` leave out, and the level's selection count does not include it, since vanilla retries the pick).

Check this file (and `awi/common/.../plugin/Plugin.java` for naming conventions) before adding a new category — see `aci/CLAUDE.md`'s "Adding a new category" recipe.

### `plugin/server` — ALI data-scan tooltip builders
Builds the `TooltipBuilder`/`TooltipNode` tree from vanilla loot-table entries/conditions/functions/ingredients, driven by the registrations above. Key classes: `TooltipUtils` (chance/count/itemstack modifier application and the vanilla unwrappers — the central helper), `EntryTooltipUtils`, `ConditionTooltipUtils`, `FunctionTooltipUtils`, `IngredientTooltipUtils`, `ValueTooltipUtils`, `RegistriesTooltipUtils`, `GenericTooltipUtils`, `MissingTooltipUtils` (fallback), `LootConditionTypes`/`LootFunctionTypes` (registry-type lookup helpers), `LootCount` (a count expression plus the condition tooltips its `Cond` branches point at). Convention: one `getXTooltip`/`collectX`/`applyX`/`unwrapX` static method per vanilla class, registered by exact `.class` in `Plugin.registerServer`.

### `plugin/server/bytecode` — trades worked out from bytecode
`BytecodeInterpreter` covers code nobody wrote a renderer for: `getItemListing` turns an unregistered `ItemListing` into an `ItemsToItemsNode` (`computeItemListing` also says whether a path of it failed, which makes ALI warn about the listing), `getTradeLevels` an unregistered trader into its `TradeLevel`s and `getItemStack` (for shims) a `Supplier<ItemStack>` into its possible stacks and their count. `Interpreter` holds one run, whose `Machine` executes the method's bytecode over symbolic values: a field read goes to `FieldModel`, an `invokedynamic` to `Indy` (a lambda or a string concatenation), and each call to `Dispatcher`, which asks the `MethodModel`s of each phase of the run's `Profile` (`Profile.TRADE` for trades, `Profile.LOOT` and `Profile.ROLLED` for loot tables, below) in list order and takes the first answer — the constructor phase for `new`, then the owner, undistributed, receiver and JDK phases, between them spreading the call over a choice and resolving it — and otherwise interprets the method, with a fallback when that fails. A model — `FieldModel` and `Indy` included — reaches the state of the run only through the operations of `CallContext`, which `Dispatcher` implements, so it can be tested on its own against a fake one; among them is the run's `Subject` — a `TraderSubject` (the trader's class, its symbolic offers and where its listings came from) when a trader is interpreted, a `ListingSubject`, which has no self, for an item listing, a `getItemStack` supplier or a lambda's identification run — both `TradeSubject`s, which keep the collections of the run that became symbolic offers —, an `EntitySubject` (the entity type, its class and the loot tables observed) for an entity's loot — an unknown value whose origin is `Origin.SELF` is that subject — and an `InstanceSubject` (a real object and the loot tables observed) for the loot tables an object rolls, whose subject is that object itself; helpers that hold no state of the run (`Interpreter.num`, `Arithmetic.intOf`) it calls directly. Per run, `Heap` keeps what is known of each object — whether the run created it and in what order, whether it is frozen inside a call spread over a choice, whether it is uncertain, its shadow copy, the stack it is part of, and for a collection its `CollState` (removals, a random index set, a shuffled view, a draw count, whether it is a pool) — and `ValueStore` keeps the frames and the static fields and the fields of the subject the run wrote, through which every rewrite of the run's values goes. `Decisions` holds the run's decisions and answers every branch on a symbolic value — a comparison, `switch`, null check, reference comparison or `instanceof` — from the path script, `NumberDomain` holds the run's draws and narrows them on the side a branch took, and `OpaqueCalls` the world calls counted in the run and the ones made opaque across the runs of one exploration. `Explorer` runs one exploration — one `Interpreter` per path script, the other side of each new decision queued, restarts after a call became opaque — and the trader's second one over the trader's offers writer, yielding one `Outcome` per path (its result or its failure, with its decisions and its subject) — and `Limits` holds the interpreter's limits (paths, decisions, steps, call depth, choice size, restarts). `Aggregation` turns the outcomes into what `Renderer` renders, by the rules below, kept apart for listings (offers with their conditions) and traders (groups per level, the incomplete levels), and the result of `getItemStack` into its options. `Renderer` turns a listing's offers into its node and a trader's groups into its `TradeLevel`s, builds the trade slots and writes the log lines below, a failure once per class and reason; `BytecodeInterpreter` holds only the entry points, each exploring, aggregating and rendering. The engine reports every value read from a concrete map by a key and every element loaded from an array to the subject (`Subject.keyedRead`/`elementRead`, ignored by every subject but the trader's); `TraderSubject` keeps from them where the run's listings came from — the level key of a list read from a concrete map, the array an element was loaded from — and the bound offers made per element, for `PickModel`, which turns an offer call on a drawn or a known listing into a pick, while `OffersModel` models every call on symbolic offers.

Fields and statics are read by reflection; every `RandomSource`/`java.util.Random` draw becomes a `NumberExpr` (`nextInt(n)` is `uniform_int(0, n-1)`, a constant added to a range is folded into it, and a number whose bounds are one value is that constant — `Math.min(0, k)` of a non-negative `k` is `0`); a `List.get` or array load at a uniform index becomes a choice of those elements (at most 1024, so that a pick from a large tag fits — `minecraft:wooden_doors` exceeds 256 in packs with many wood mods), tied to the draw of that index — loads from several lists at one index stay paired — and every value computed from that choice stays tied to its draw, so a call taking several of them is evaluated once per element, never over every combination, and the offers a Minecraft or mod method returns per element — modelled or real ones — are one offer when they share uses, XP and price multiplier, each slot whose stacks differ being a slot of all of them (a `List.get` from a list of offers stays a pick of those offers); constructing anything other than an `ItemStack`, `ItemCost` or `MerchantOffer` from a choice or from a uniform integer draw builds one object per value; `ItemStack`, `ItemCost` and `MerchantOffer` construction and `setCount`/`grow`/`shrink`/`copy` are modelled — a stack constructed from a choice, or combined from the stacks a call spread over a choice returned, whose items are exactly the contents of an item or block tag the run has read (a `TagKey` it handled) shows as one slot of that tag while its non-empty options, repeats aside, are still exactly those items, with no components and no random properties, otherwise item by item — and so is constructing a `MerchantOffer` subclass from symbolic arguments when its constructor only forwards its parameters to the `MerchantOffer` constructor of the same descriptor (Goblin Traders' `GoblinMerchantOffer`) — an `ItemCost` is the stack it shows (`itemStack()`), its canonical constructor given a modelled stack is that stack with the count argument (NeoForge's `BasicItemListing`), so `count()`, `itemStack()` and `withComponents` act on that stack, and an empty `Optional` in its place is an empty slot — and a stack handed to a call that needs a random or unknown value, or a call on a stack that returns one, keeps its item and is marked `Random properties` when the call returns nothing or a stack, which is marked as well, since such a call may change the stack and return it, or when it writes a data component (`set` and `update` of the stack, NeoForge's `Supplier` overloads included, and `EnchantmentHelper.updateEnchantments`), whose result is an unknown value (any other result aborts). An `Optional` of a modelled stack is that stack: `Optional.of`/`ofNullable` of one returns it, and `isPresent`, `isEmpty`, `get`, `orElseThrow`, `orElse`, `orElseGet`, `ifPresent` and `map` on it, or on a concrete `Optional` given a lambda or a symbolic argument, are worked out — a lambda runs on the value, and a stack `map` returns is the `Optional` again (any other `Optional` call there aborts). A call handed several stacks gets all but one of them as real stacks when they hold one item with a constant count and no random properties (`simpleTrade(cost, result, uses)`), and aborts if it changes one of those. JDK code runs for real only from a whitelist of pure and read-only methods, or on a stream, which is single-use and so belongs to whoever consumes it, and a pure static method of that whitelist given unknown values and otherwise only numbers, strings or `null` (`String.valueOf(trader.getOffers().size())`) returns an unknown value instead, and so do `String.valueOf` of a random number and a string concatenation with a random or unknown value; Minecraft and mod methods are interpreted, and run for real only when interpreting them fails with every argument concrete — code `getOffer(null, null, null)` would run anyway — and never when the method itself writes a static field: a lazy initialiser run out of its usual order can leave the mod's global state broken for the rest of the game (Iron's Spellbooks' `SpellRarity.getRarityConfig`), so that path fails instead. A call to a logger (`org.slf4j`, `org.apache.logging.log4j`, `java.util.logging`) does nothing — a `boolean` it returns is `false`, any other result unknown — so a scan never writes a mod's messages to the log.

A call is resolved (`Resolution`, which also loads classes, reads their bytecode and finds methods, constructors and fields, caching all of it until the scan clears its caches) as the JVM selects it: the class and its superclasses first, a JDK class among them ending the search, then a default method of a non-JDK interface. The bytecode comes from the class file, not from what the JVM runs, so a method a mixin changed is never interpreted (`MixinChanges`): one carrying `@MixinMerged` (an overwrite), one an injector annotation's `method` selector or `target` `@Desc` of a mixin applied to its class names (remapped through that mixin config's refmap the way Mixin does), and every method of a class one of whose applied mixins has a selector naming none of its methods — an injector that remaps names by itself, like Fabrication's `@FabInject`. The applied mixins are the ones the class's `@MixinMerged` members name, and a class whose methods cannot be read reflectively (a signature naming a class missing on this side) counts as changed entirely when a mixin configuration targets it; `Mixins.getMixinsForClass` answers only for a mixin's own class, not for its target.

Nothing the interpreter did not create is ever written: an `ItemStack` read from a field and then changed gets a shadow copy, any other such write aborts. An object the run created that a change with a random or unknown value cannot be carried out on (a failing call, an array store, a JDK collection taking a random or unknown element, a call on an unknown value or a world call it is handed to, which may write into it) is uncertain instead: the change is skipped, reading it (an array element, a read-only JDK method) aborts, a call passing it is skipped and leaves its receiver uncertain, the data read out of it — a collection, map, array, NBT tag or data component map or patch held in its fields or returned by a call taking it — and an object constructed from it are uncertain too, and a stack it reaches — passed into a stack call, or an object a stack call returned, like one of the stack's components — is marked `Random properties`. A static field the run writes reads back what was written; the real field is never written. Inside a call spread over the elements of a choice, an object that existed before the call is not written either, since every element's run would change the same object (`list.remove(pick)`). A null check, reference comparison or `switch` on a choice is decided outright only when all its elements agree, and a branch only when its operands are concrete or their bounds decide it; otherwise it is a random decision (below), after which the choice, and every choice tied to its draw, keeps only the elements on the side taken. A bit operation on a random value aborts its path.

The trader and everything reached from it are unknown values carrying their static type; arithmetic on them stays unknown, and so does an object constructed from one (`new Bee(EntityType.BEE, trader.level())`). Only the server generates offers, so the trader's `Level` is a `ServerLevel` (`instanceof` holds, `isClientSide()` is `false`), the `ServerLevel` that `getOffer`, `updateTrades` and `addOffersFromItemListings` take is an unknown value of the world (`Origin.WORLD`), and its `registryAccess()` is the server's, since registries do not depend on where the trader stands — `Level`'s and `Entity`'s alike, which are two methods under Fabric's intermediary names. A Minecraft or mod method that fails on a random or unknown argument, all others concrete, returns an unknown value whose origin is that call (nothing for `void`), unless it returns an `ItemStack`, `ItemCost`, `MerchantOffer(s)` or a random source; objects of the run it was handed become uncertain. Such a call taking more than one decision is remembered, and when a run then exceeds 8 decisions — or a budget is exceeded inside such a call — the heaviest one becomes opaque: from then on it returns that unknown value without running, and the exploration of the listing or trader starts over (at most 7 times), so a mod method checking every structure of a tag against the world (`mapValid`) is one decision. An unknown value remembers where it came from (`Origin`: receiver, member and arguments, rooted at the trader or the world), and two with the same origin are taken to be the same value.

A branch on an unknown or random value (null check, comparison, `instanceof` the type does not decide, a `switch`) is a `Decision` explored both ways — a `switch` once per case key the value can reach, plus the default unless those keys cover its whole range: `getItemListing` re-runs `getOffer` once per path, replaying the decisions taken so far (at most 8 per run, an equality that does not hold not counted, since a chain of them — a lookup in a map of many keys — adds paths one at a time rather than doubling them; 128 runs; a failed run loses only its path — so does one returning something other than nothing or an offer with a stack in every slot — and a listing with a failed path or cut short by the limit shows the offers of the others with `Unable to auto-detect some variants of this trade` added to its condition); a decision with the same test as an earlier one in the run is answered from it, and once an unknown value equals one concrete value it equals no other. A lookup in a concrete `Map` (`get`, `getOrDefault`, `containsKey`, any implementation including fastutil's `get(int)`) by an unknown key is one equality decision per key plus the missing-key case, the keys tried in the order of their text, since a key's hash may be its identity and an exploration cut short by the path limit has to come out the same on every start. A decision is an equality with a concrete value (`==`, `equals`, a map key), a test with one concrete argument (`holder.is(tag)`), a found structure (the null check of `findNearestMapStructure`), a random one (a random value, or a choice whose elements disagree; each is its own decision, never answered from an earlier one, since two draws are independent), or unknown (numbers, `instanceof`, two unknowns). A draw is one call on the random source, recognised by its expression object, which survives being stored, unboxed, widened or shifted by a constant; a branch or `switch` comparing it with a constant narrows the values (an integer draw) or the interval (a float draw) it can still take, so a later comparison of the same draw is decided outright when what is left decides it and otherwise gets the probability conditioned on the earlier ones — `x = nextInt(3); if (x == 0) … else if (x == 1) …` is 1/3 and 1/3, and the path `x != 0, x == 0` does not exist.

Paths returning no offer drop out, paths returning the same offer merge, an offer takes in the paths of another one whose paths differ from its own only in unknown decisions and which differs from it only in slots where its own stack is the same items and count marked `Random properties` (a name set or left empty on an unknown text), and each offer gets the condition of its paths (`PathCondition`: negations implied by an equality dropped, paths differing in one decision merged, a part common to all paths factored out). A condition value is labelled by its registry — the `Lang.Value` that `PathCondition.Is` maps that registry to (`dimension`, `biome`, `villager_type`, `structure`, …), `Value` for one it does not list — a random decision shows as `Random chance` whichever way it went, and an unknown one as `Unknown additional predicate`, in the tooltip error color like every other note that something was not worked out. One offer gets its condition added to the listing's; several become a `ConditionalTradesNode` (a `SubTradesNode` carrying the listing's condition) of trades carrying their own.

`getTradeLevels` interprets a trader's own `getOffers` when its mod overrides it, its own `updateTrades` otherwise and nothing when its mod overrides neither (vanilla's `updateTrades` offers a profession's or the wandering trader's trades, which have pages of their own), with the trader as an unknown value of its entity class: a call on it runs the trader's method when a mod declares it (`SelfModel`) — not Minecraft, Mojang or a loader (`net.minecraft`, `com.mojang`, `net.minecraftforge`, `net.neoforged`, `net.fabricmc`), whose interfaces add default methods to vanilla classes — and stays unknown otherwise, its `RandomSource` field is a random source, and — unless its mod overrides `getOffers` — its `getOffers()` and the field `AbstractVillager.offers` (identified by declaring class, since a mod's own field may share the name) are one symbolic `MerchantOffers`; so is `new` of `MerchantOffers` or of a subclass that does not override `add`. Any other field of the trader the run writes reads back what was written, and a `MerchantOffers` field it has not written is `null`, as on a trader that has never been asked for its offers. When no path of that run offers anything and exactly one other method of the trader declared outside `net.minecraft` writes `AbstractVillager.offers` — a mod filling its offers on interaction (`mobInteract`) — that method is interpreted instead, with unknown arguments, and its trades are what it writes there. `clear` empties the symbolic offers, and sorting, reversing or shuffling them changes nothing, since a level shows no order; `addAll` of a collection whose contents are known adds each of its elements as one trade, and `removeIf` drops the trades its predicate holds for and keeps picks of listings only for `Objects::isNull`, since a listing that offers nothing shows nothing. `Objects.isNull` and `nonNull` are null checks like any other. Vanilla `addOffersFromItemListings(level, offers, listings, n)` adds a group of `n` picks from those listings. A selection without replacement is a group too, in each of the three shapes mods copy from vanilla versions: `remove(random.nextInt(size()))` — or `remove(element)` of an element drawn from the whole remaining list — from a list the run owns, a set the run fills with `random.nextInt(n)` until it holds `count` indices (then iterated), and `Collections.shuffle` of an owned list followed by `subList(0, k)` — `k` may be random, and then it is the group's count, without a cap at the pool's size, which no draw can exceed anyway. Such a selection is a placeholder (an empty view, or the list without its removals applied), so passing it to code that runs for real — a JDK call, a real run of a method, a constructor — aborts that path rather than let it read the placeholder; interpreted code taking it is fine. `getOffer` on an element drawn that way, on distinct listings drawn at a uniform index (`listings[random.nextInt(listings.length)]`, as in vanilla's wandering trader), or on a listing read from an array, is a pick of its pool; so is any other method returning a `MerchantOffer` called on such an element of a mod's own type, its other arguments the world, the trader, the random source or concrete values (Goblin Traders' `BaseTrade.createVanillaOffer(goblin, random)`): each element becomes a `BoundOffer`, an `ItemListing` holding the element and that call, which `getItemListing` explores by making the call and which the logs and the missing-listing tooltip name by the element (`listingSource`), and a list read from a concrete map gives the pick the level of its key like a list of listings; `add` of picks of one pool counts them into one group (listings read one by one from one array join into a group of exactly those listings), `add` of any other offer is one trade, and the same trade added several times in one path is one trade offered that many times (`TradeGroupNode.repeated`); the same listings added twice in one path give up. Elements of a list of offers drawn without replacement are a group of those offers, counted like picks of listings. A collection the run created that receives an offer, a pick or such an element becomes symbolic offers itself, so every further call on it acts on them, and `addAll` of it adds its trades and groups to the trader's offers. Paths with no trades drop out. A run that fails — an unsupported construct, more than 8 decisions — loses only its own path, and reaching 128 paths stops the exploration; the trader's result is then incomplete. A failed path whose decisions name its level (a held equality with an integer) marks that level, any other failure marks every level, and so does a level that cannot be put together (a group whose chance differs between the conditions it holds under, the same listings twice in one path, something added that is not an offer with a stack in every slot, which is left out); a marked level shows what was worked out plus a `MissingNode` saying `Unable to auto-detect some custom trades` (a level no path completed shows only that). `getTradeLevels` returns the levels together with that flag (`ComputedTrades`). A random decision whose probability is known — a uniform draw, or the remainder of an integer draw divided by a constant, compared with a constant, `random.nextDouble() > includeChance`, a test of a choice drawn at a uniform index (the share of its elements that pass) — weighs its path by that probability and narrows the draw on it, so the numbers and stack counts computed from that draw hold only its values left on the path (`level > 1` of `nextInt(2) + 1` makes `level * level` 4), and a group's chance is the summed weight of the paths holding it under each of its conditions, which has to be the same under every one of them. When every group of a level shares one chance it becomes the level's `TradeLevelInfo` chance; otherwise the level's chance is 1 and every group shows its own chance (`Chance: n%` on each of its trades), adding to the level's number of offers only with that chance. The level's number of offers sums only the groups offered together, once per condition its paths hold under, and is a `NumberExpr.Cond` of those sums when they differ (`cold ? chisel : brush` counts one trade, not two). A group of the same listings or offers on paths that differ only in random decisions is one group, whose number of offers is the distribution of its counts over those paths (`NumberExpr.Weighted`) — a trade added a random number of times included, which is one repeated trade. Apart from those, a held equality with an integer is a lookup of the level by a value of the trader (`TRADES.get(getTradeLevel())`) and that integer is the path's level (level 1 without one, two give up); every other decision — on what the trader holds, the world, a random value of unknown probability — becomes the `PathCondition` of the groups of that path, merged over the paths holding a group as for listings (a single trade takes in another of its level as an offer does), and is shown on each of its trades, which makes the level an `OfTrades` one. The probability rides on the decision for listings too, where it changes nothing shown. A group whose listings (an array or a list, of listings or of the elements bound to them) came out of a concrete map under an integer key (`TRADES.get(2)`) takes that key as its level, under an enum key its ordinal plus one, as vanilla's wandering trader and the shims built on such maps show them, everything else the level of its path. A level holding one group is an `OfListings` level; several groups or single trades are one `OfTrades` level with a `TradeGroupNode` per group (a group's listings identified by `TradeUtils.listingKey`, so equal listings a mod builds anew on every path are one group whose condition is merged over those paths), except a group whose count is at least the number of its listings, which takes them all and adds them as plain trades.

Vanilla's explorer-map API is modelled the way `ItemStack` is: `findNearestMapStructure` yields a position known only by its target, `MapItem.create` a `filled_map`, `renderBiomePreviewMap` nothing, and `addTargetDecoration` puts the target and the decoration into the slot's tooltip, as the renderer of vanilla's `TreasureMapForEmeralds` shows them.

The runtime names of the Minecraft methods and fields it models come from `RuntimeNames`, which reads the calls and field reads its own never-called helpers make — loom remaps those, so no mappings are involved; when one cannot be read, auto-detection is off and the server log names the missing ones. A missing loot name turns off only the loot analysis (`LOOT_AVAILABLE`), never trades.

The JDK offers no way from a lambda to its target method, so `LambdaResolver` takes the `invokedynamic` sites of the defining class whose interface and captured types match; when several remain, it first looks the lambda up where the defining class's `<clinit>` stored it — a static field of that class assigned it directly, the n-th `add(Object)` to a static `List` of it, or index n of an array then stored into one, read with ASM's `SourceInterpreter` up to the first jump; a list passed to a call or called with anything else in that part is not trusted, nor one whose size at resolution differs from the number of those `add`s — and takes the site whose instance the field, list or array holds (by identity). Otherwise it runs the lambda with `StubRandom` as its random argument (every draw returns its lowest value, then in a second round its second-lowest; the first round runs even when one candidate is left), leaving out every candidate that reads a static `Random`/`RandomSource`, since nothing outside the run is ever changed to make such a field deterministic, twice per round to reject nondeterministic code, and keeps the candidates whose interpretation in the same stub mode returns the same result (compared by `TradeUtils.valueKey`, also between the two real runs) — one, or several whose instructions are identical (operands compared, labels by position, no exception handlers), which differ only in name and so give the same trade. That run only picks the method; nothing it returns is shown. Every run gets a `StubRandom` of its own, which throws after 1000 draws, since mod code looping until a draw comes out differently (a rejection loop, `while (nextInt(50) <= level)` over enchantments compatible with themselves) never ends against a stub returning one value; that run then fails. A real run that throws — the draw limit, a `null` trader — names its target instead: the outermost stack frame of the defining class whose method is a candidate is the method the lambda called (only the proxy's own frame is hidden; two candidates sharing that method's name leave it unresolved), and that candidate is taken without comparing results.

`LootTableAnalysis.getEntityLootTables` works out which loot tables an entity type drops, from its class alone, with `Profile.LOOT`: the core models plus `EntityModel`, `LootTableModel` and `ForeignReceiverModel`, and none of the trade models. Its result (`ComputedLootTables`) has two maps of the same shape, path world decisions → table → probability, where the key holds every decision of the paths except the random ones of known probability and the probability is the summed weight of those random decisions (and of the draw, for a table picked from a choice) over the paths of that key, each observation counted once per table and decision snapshot (`LootAggregation`). `own` is what the entity's loot-table selector picks (`LootTableAnalysis.ownLootSelector`, a mod override, never a platform one: `LivingEntity.dropFromLootTable(ServerLevel, DamageSource, boolean)`, whose tables are the keys it hands to the drop sinks below, or, since `Mob#getLootTable` is `final`, `Entity.getLootTable()` of an entity that is not a `Mob`, whose tables are what it returns), interpreted with the entity as `Origin.SELF` and cached per type until the scan clears its caches: `getType()` on the entity is its type, its `getLootTable()` runs its own override (a `super` call looks from the calling class up) and is the type's default otherwise, a `super.dropFromLootTable(level, source, flag)` that reaches the platform drops the type's default, and the type's default stays only on a key where it is less than certain. `events` is every table the entity's code rolls through one of the sinks in `LootTableAnalysis.SINKS`, `ReloadableServerRegistries.Holder.getLootTable(ResourceKey)`, `HolderGetter.Provider.get(ResourceKey)` (`LootContext.getResolver()`), any call taking a `ResourceKey` or `Identifier` and returning an object on a loot table view — a `HolderGetter` or `Registry` returned by a call on a `HolderGetter.Provider` or `HolderLookup.Provider` whose only argument is `Registries.LOOT_TABLE` (`lookupOrThrow`, recognised by its descriptor, not its name) — and the six `LivingEntity` drop helpers (`dropFromLootTable` with a key, with a key and a consumer or with a `LootParams` function, `dropFromEntityInteractLootTable`, `dropFromGiftLootTable`, `dropFromShearingLootTable`), each with the index of its key argument — `CallSites` never descends into platform code, so a helper reaching a sink is a sink itself (`LootTableModel` records the key argument, a `ResourceKey` as its location, with the decisions taken at that moment and returns an unknown value of the call's return type; a loot table view is an unknown value whose origin marks it), found by `CallSites`: from every non-static method of the entity's mod classes, except the selector, it follows calls three levels deep (only those whose subtree reaches the sink by name) and traces the table argument with ASM's `SourceInterpreter` through `DUP`, casts, `ResourceKey.create`'s location argument (a key created for a registry other than `Registries.LOOT_TABLE` is no table), locals and the parameters of the callers — a static field is a constant and is taken as read, the entity's own `getLootTable()` passed down to a helper, also unwrapped by `Optional.get`/`orElseThrow`/`orElse`, is skipped (its tables are `own`), a parameter of the starting method cannot be traced and is skipped, and a value computed anywhere else has its method interpreted, its receiver and the parameters that receive the entity's `this` along that call chain being the entity, everything else unknown. One `CallSites` serves every method of a class, so the reachability it works out is shared by all of them, and its sites are cached per class until the scan clears its caches. For an entity, a method of a class from one of the entity's own jars is followed only when its name and descriptor lie within three calls of a sink call in that jar (`ModJarIndex.reaching`, matched by name and descriptor, any owner; a level of more than 64 names drops the filter for that jar), so a chain that leaves the entity's jars on its way to the sink is not found — dozens of entities share one hierarchy, which makes walking it per entity the analysis's largest cost otherwise; an object's classes are walked without that filter. A computed site's method is interpreted only as far as it can still reach a sink call or a call leading to one (`Machine.Cutoff`, from the method's control flow): the run ends there, since nothing after the last table rolled changes the tables, and the branches after it are never explored. The type's default is never an event. Both match a sink by runtime name or descriptor and by a receiver type assignable to the sink's declaring type, since in a Mojang-named run a mod's own `getLootTable(ResourceKey)` or `get` shares the name, the `HolderGetter.Provider` sink only for a key of `Registries.LOOT_TABLE` (`CallSites.isLootTableKey`: a constant key has to be one, or a location traced out of `ResourceKey.create`, and so does the key value an interpretation reaches the call with) and a view sink only when its receiver traces to a view, like the table argument — the same calls read every other registry. A view kept in a field, unwrapped from an `Optional` (`lookup`) or handed in through a parameter of a class's own jar method that `ModJarIndex` reads is not covered. `ModJarIndex` finds a view sink's callers in the class files that contain the runtime name of `Registries.LOOT_TABLE`, a sink name to look for otherwise. `ForeignReceiverModel` interprets a call on an unknown receiver other than the entity when a mod declares the method (`this.lootHandler.prepareDrops(this)`); a non-budget failure inside it returns an unknown value instead of failing the path.

`LootTableAnalysis.getRolledLootTables` finds the tables a real object rolls — a global loot modifier, whose table comes from its fields — the way `events` finds an entity's: from the methods of its class up to the first platform class, with `Profile.ROLLED` (`Profile.LOOT` without `EntityModel`), the object itself as the receiver and as the parameters that receive its `this`, every other argument unknown. The object is live state: a field the run writes on it goes to the subject's fields and reads back from there, the real object is never written, and a call whose interpretation failed is not run for real when the object is its receiver or an argument — the path fails instead. `getReferencedLootTables` reads a whole mod jar instead (`ModJarIndex`, one per code-source location — a jar file read directly, also behind a Forge `union:` location, whose path precedes the `%23`, since walking the union file system costs ten times more; a directory as it is; anything else through its file system — whose class files are read once and parsed only when their bytes contain the method name looked for, the sink's callers kept, released as soon as `EntityLootTableResolver.resolveAll` is done, since the class bytes of every jar read would otherwise stay in memory for the rest of the scan): a sink call taking a constant in a class that is not an entity is a table, and so is a constant that such a class passes to a parameter a method hands to the sink, one level up (Bumblezone's `injectLoot`). An entity's own calls are left to `events`; a `@Mixin` class is never loaded, and is not an entity.

`LootTableAnalysis.getVariantHints` reads what a type's variants differ in from the decisions of its cached `own` run, with no second interpretation: an entity data read (`SynchedEntityData.get` of a known `EntityDataAccessor`) a path decided on is a `VariantHint.Data` over the values it was compared with, and a platform getter called on the entity (`Sheep.isSheared`) is a `VariantHint.Setter` for every non-static one-argument `void` method of the entity's hierarchy that reads one of the getter's static `EntityDataAccessor` fields and calls `SynchedEntityData.set` (`setSheared`, `setColor`), over every constant of an enum argument, both booleans, or 0 and every int a decision compared with — any other argument type gives no hint. A mod's own getter is interpreted, so it shows up as the data read inside it. Hints are grouped per path, only hints decided on the same path are combined, and a group contained in another is dropped. They are guesses: `plugin/common/EntityVariants` builds every combination of a group (a group of more than 64 is skipped), a data hint adding the instance's current value and, for a boolean, its negation, and keeps an instance only when its table is one no instance gave before. An instance's table is `EntityLootTableResolver.getLootTable`: for a `dropFromLootTable` selector, with `entityVariants` on, the one table every path of the selector drops when it is interpreted on the real instance (`LootTableAnalysis.getInstanceLootTable`, `null` when they differ), and the instance's `getLootTable()` otherwise.

Under `logMoreStatistics` the scan logs how many listings were worked out and, once per class and reason, why one was given up or shown only in part (`Computed only some variants of trade item listing`); `-Dali.debug.trades=true` also logs every offer worked out, one line each, and for every auto-detected trader each level (chance, `OfListings` or `OfTrades`, offer count), each of its groups (kind, count, whether it shows as a group, condition, its offers or listing keys) and each incomplete level with its reason, for diffing two runs.

### Numbers

Counts, chances, trade prices and every loot number provider are ACI `NumberExpr`s rendered as number nodes (see `aci/CLAUDE.md`'s "Number model"); nothing in ALI formats a range by hand.

- **Two conversions per provider.** Vanilla's `NumberProvider.getInt` is not a rounded `getFloat` for every type — `UniformGenerator.getInt` draws a uniform integer between the rounded bounds — so `registerNumberProvider` takes a float converter and optionally an int one, and `IServerUtils` offers `convertNumber` (float) and `convertIntNumber` (int; `round(float)` when no int converter is registered, like vanilla's default). Both take the conditions list of ACI's `NumberConverter` contract; a tooltip shows a provider through `TooltipUtils.getNumberTooltip`/`getIntNumberTooltip`, which attach it. A consumer calls the variant vanilla calls: `set_count`, `limit_count`/`IntRange`, pool `rolls`, `enchant_with_levels`, `set_enchantments`, `set_stew_effect`, `set_ominous_bottle_amplifier`, `set_custom_model_data` and `value_check` use int; `enchanted_count_increase`, `bonus_rolls`, `set_damage`, `set_attributes` and `random_chance` use float.
- **Modifiers transform an expression.** `registerCountModifier`/`registerChanceModifier` take a `NumberModifier` `(utils, T, NumberExpr, conditions) → NumberExpr`; `NodeUtils.getCount` starts from `1` and `NodeUtils.getChance` from the entry's weighted chance (a fraction, rendered as a percent), both returning a `LootCount` whose conditions `getCountTooltip`/`getChanceTooltip` attach. An enchantment level is `TooltipUtils.level(enchantment)`, so level rows come from binding it, not from precomputed tables. A modifier that throws turns the value into `Opaque(<function/condition type>)` (logged), never the whole loot table.
- **Conditional functions.** `AliServerRegistry.applyCountModifier` wraps a modifier whose function carries predicates: only `random_chance` predicates give `Weighted(p · modified, (1 − p) · original)`, anything else gives a `Cond` whose branch points at a condition tooltip collected into the `LootCount` and added as a child of the count node. Build the count through `NodeUtils.getCount` and render it with `TooltipUtils.getCountTooltip`, or the branch indices point at nothing.
- **Entry weights.** `registerEntryWeight` (`NumberConverter`) and `registerEntryChildren` are `ClassKeyedMap`-backed, so a registration covers subclasses — a modded `LootPoolSingletonContainer` gets its weight without registering anything. Vanilla: a singleton weighs `max(0, weight + floor(quality · luck))` (`TooltipUtils.luckBased`, `luck` ∈ −1…4, a stepped ACI variable, so a chance or roll count depending on it shows luck 0 plus a `Bad Luck` row and one `Luck n` row per positive value), a composite the sum of its children, `alternatives` the weight of its first unconditioned child (none → `0`) with a `Cond` branch per conditioned child before it, and its children get the pool sum with that weight replaced by their own; an unregistered entry weighs `0`. A pool sums its entries' weights into a conditions list started from its parent chance's conditions, and that list goes read-only to every entry factory (`EntryFactory.create(..., chance, sumWeight, chanceConditions, ...)`) as the index space of both `chance` and `sumWeight`; an entry copies it before adding its own. A node's `float` chance (sorting only) is that expression at luck 0 (`NodeUtils.toFloat`). `getEntryChildren` is what `AbstractServer` walks to collect referenced tables.
- **Level-based values.** `LevelBasedValue` types convert like number providers, through a registry: `registerLevelBasedValue(Class, (utils, T, level) → NumberExpr)` and `IServerUtils.convertLevelBasedValue(utils, value, level)`, where `level` is the expression the value is evaluated at; an unregistered type is `Opaque`. `random_chance_with_enchanted_bonus` is `Lookup(LVL, [unenchanted], enchanted(LVL))`, and its tooltip is that same expression as one number node. `EnchantmentLevelProvider`, and the value tooltip of a bare `LevelBasedValue`, evaluate at `ali:enchantment_level` (`TooltipUtils.anyEnchantmentLevel()`, the context's level, enchantment unknown; domain `1 … max` over the registry, so its tooltip gets one `Level n` row per level) and `StorageValue` is the `ali:storage` variable; both are labelled through `Lang.Numbers`, like `ali:luck`.
- **Clamping.** `set_count` clamps at 0 inside its own transformation: vanilla writes the count unclamped, but `ItemStack.getCount()` reads a non-positive count as 0 and later functions (looting) add on top of that. There is no upper bound — `set_count` does not clamp to the max stack, an oversized stack is split by the loot table — so `NodeUtils.getCountLimit` only bounds at 0. It is a consumer limit, never part of the expression: it feeds the count tooltip, and the viewers' slot text comes from `plugin/client/TooltipUtils.getSlotCount`.

### `plugin/common` (+ `nodes`, `trades`) — shared client/server tree model
`plugin/common/nodes`: one `IDataNode` implementation per node kind (`LootTableNode, EntityLootTableNode, LootPoolNode, ItemNode, AlternativesNode, SequenceNode, GroupNode, EmptyNode, DynamicNode, ReferenceNode, ModifiedNode, GlobalLootModifierNode, MissingNode`, plus `CompositeNode` base). Convention: each declares `public static final ResourceLocation ID = Utils.modLoc("<snake_case_name>")`, the shared key between its data-node factory and widget factory registered in `Plugin.registerClient`. `plugin/common/trades`: villager-trade equivalents (`TradeNode, TradeLevelNode, TradeGroupNode, SubTradesNode, ItemsToItemsNode, EmeraldsForVillagerTypeItemNode`), plus `TradeUtils` (`getNode` for most `VillagerTrades.ItemListing` subclasses; the slot builders `getSlotNode` for a loot pool entry or for a list of option nodes — joined under a `GroupNode` — `getItemSlotNode` for a list of stacks sharing one count, and `getEmptySlotNode`).

A trader's levels are `api.TradeLevel`s: `OfListings` (an `ItemListing[]`, what `registerTrades` produces) or `OfTrades` (prebuilt trade nodes). `registerTradeOverride` replaces a registered trader's levels at scan time — the overrides are asked in registration order, the first non-`null` answer wins, so a mod that swaps a trader's trades for its own data (VillagerConfig) needs no plugin ordering. Listings equal by `TradeUtils.listingKey` (the `TradeUtils.valueKey` of the listing, which keys any value the same way) — same class and field values, recursing into a mod's own objects that do not define `equals`, into records, Minecraft's and Mojang's included (a Minecraft record such as `ItemCost` holds an `ItemStack`, which has no `equals`) and into arrays, collections and maps element by element (sets and maps in any order), `ItemStack`s by item, count and components, other Minecraft, Mojang, JDK and enum objects by `equals`, and by identity whatever lies deeper than four levels, is met again inside itself or cannot be read, so building a key never fails — are shown once per level or group (`distinctListings`), since mods append the same listings to `VillagerTrades` more than once (Bumblezone on every world load); the selection count still counts them all, as the trader picks from the whole array, except those that render as an `EmptyNode`. A level's children are trades or `TradeGroupNode`s, each picking its own number of trades; the level's selection count is capped at the trades below it, counting into groups. `TradeGroupNode.repeated(times, trade)` is one trade offered `times` times at once, with no cap at its single child, and counts `times` towards the level's cap; the flag is server-side only, since the cap is computed before encoding. An `ItemsToItemsNode` slot is any node subtree — an `ItemNode` for a fixed stack, the node an entry factory builds for a loot pool entry otherwise — and its `IItemNode` leaves are the slot's options (`getSlotOptions`), cycled by the viewers on one clock, so two slots whose items vary together list their options in the same order and number. `NodeUtils`/`EntityUtils`/`ReflectionUtils` are top-level helpers (entry→node dispatch, creating one initialised entity, reading a lambda's captured instances out of its synthetic fields).

An item listing with no registered handler is first worked out from its bytecode (`plugin/server/bytecode`) and falls back to `getOffer(null, null, null)` only when no path of it gives an offer; that one roll is shown with `Unable to auto-detect this trade, shows one random offer` in the error color added to its condition. Besides the interpreter's identification run, these are the only ways ALI or a plugin reads a listing's offer: nothing passes a real `RandomSource`, since one roll is a sample of a random trade, not the trade. A listing that needs its trader or random source throws there and renders as a `MissingNode`.

`TraderDetector` finds every entity type implementing `Merchant` that no `registerTrades` names and whose page no `tradeCategories` entry hides, so a hidden one is neither created nor interpreted; `AbstractServer.readLootTables` runs it before the trades are parsed, works each one's levels out with `BytecodeInterpreter.getTradeLevels` (see `plugin/server/bytecode`) and shows those under `<namespace>:entity/<path>` of the entity's id like registered trades — a registered trader keeps the bare id, and a profession may share its name with an entity (`wan_ancient_beasts:paleontologist`) — and also the traders whose trades it could work out only in part or not at all: their page carries what was worked out, a level missing some says so, and a trader left without any level — its interpretation throwing or `RuntimeNames` unable to read its helpers included, logged with the cause — gets a single `MissingNode` saying `Unable to auto-detect custom trades` (`AliServerRegistry.parseTrade`). The log names the partial ones with `Computed only some trades of trading entity <id> (<class>)` and those without any level with `Unregistered trading entity <id> (<class>)`; one whose code runs without a decision and offers nothing has no trades to show and is not warned about. It needs no instance for nearly every type (`EntityClasses`, shared with `EntityLootTableResolver`): the type's factory is a lambda, the class defining that lambda declares the static field holding the type, and the entity class is the first `Entity` subclass among that field's generic type arguments (`EntityType<X>`, `RegistryObject<EntityType<X>>`, a mod's `MobReg<X>`). The field holds the `EntityType` itself or a registry wrapper reaching it through instance fields within three levels, which are read and never called; a field reaching more than one type is ignored. A type no field claims — registered without a static field, or with a factory that is not a lambda — is created through `createEntities` instead, and their count is logged under `logMoreStatistics`.

`EntityLootTableResolver` maps a loot table id back to the entity types that can drop it — the inverse of asking every entity type what it drops, and the reason the loot scan constructs no sample entities (one entity per registered type with goals/attributes/brains is by far the most expensive thing the scan could do). It runs on the server only: the owning entity type is written into `EntityLootTableNode` and the viewer registration reads it from there, so the client resolves nothing and builds no entity for it. It needs no instance because `EntityType.getDefaultLootTable()` is derived from the registry key and `Mob#getLootTable` is `final`, falling back to it; the only types that can drop something else are those with a loot-table selector (above), and vanilla's `Sheep` puts its per-color tables one path segment below the type's own table, so trimming trailing segments off an unmatched `entities/` table finds the owner **without any variant registration**. An `entities/` table that still resolves to nothing has the entities of *that table's namespace only* worked out from their bytecode first (`LootTableAnalysis.getEntityLootTables`, entity classes from `EntityClasses`, below), then the code of their mod jars (`getReferencedLootTables`), and only a table still unexplained falls back to building those entities (`scanNamespace`), so the cost tracks the number of unusual mods, not the registry size — vanilla data never triggers it. Each step runs once per namespace; a table outside `entities/` never triggers them, so a table such an entity rolls outside `entities/` is attributed only when its namespace was analysed anyway.

What the analysis finds: every table the entity's code rolls (`events`) is a page of that entity, and so is every table its selector picks for certain on some path (a variant). A path that picks one of several tables at random, or the default table of another entity type (`isForeign`; a variant table several types share is not foreign and belongs to each of them), becomes a synthesized page instead: one pool, one roll, a `NestedLootTable` reference per table weighted by its probability (the smallest integer weights that give the probabilities exactly, an empty entry for the share that drops nothing). Its id is the type's default table when that is among the outcomes or none of them is the entity's own, the first own table otherwise; the own tables it holds get no page of their own (`EntityPage.absorbed`, removed from the gameplay candidates), a foreign one keeps its owner and page. The reference to the page's own id expands from the server's loot table map, which still holds the original table, and a synthesized page is exempt from the sub-table rule, since it references its own id. `resolveAll` returns `EntityPage`s (id, types, the synthesized table or `null`, the absorbed tables) — `entities/` tables first, so every analysis has run before a table outside `entities/` is looked up — and `AbstractServer.collectEntityPages` only turns them into pages. Before anything is resolved, every global loot modifier instance is analysed (`getRolledLootTables`) and the tables it rolls are excluded like referenced ones, since a modifier of one mod may roll a table of another namespace; the instances come from `GlobalLootModifierCollector`, which keeps each one on the `IPageLootModifier` it produced (`getGlobalLootModifiers`). Under `logMoreStatistics` each table attributed or excluded that way is logged with the time each step took.

The config's `entityLootTables` (entity type id → loot table ids) is seeded before anything derived and therefore wins over it — that is the escape hatch for a mod whose loot table id follows no convention at all, and it works for tables outside `entities/` too. Plugins declare the same mapping through `IServerRegistry.registerEntityLootTable` (kept by `AliServerRegistry` per loot table, handed to the resolver by `AbstractServer`), seeded right after the config: a table both claim lists the config's entity first, which makes it the owner. A table some other mechanism rolls — a global loot modifier, mod code — is declared through `IServerRegistry.registerLootTableReference` instead: it joins the tables other loot tables reference, so it belongs to no entity and costs no namespace scan.

Consequences worth knowing before touching it: a table under `entities/` is attributed to its type even when that type is not a `Mob`, and instances are needed only by global loot modifiers — the `ILootModifier<Entity>` predicate and the entity sub-predicate resolvers that read samples, which `AbstractServer` reaches through the lazy, memoised `LootPage#samples`, never touched when no GLMs are installed — and by the pages of a type with a loot-table selector. Both come from `EntityLootTableResolver#getEntities`: the plugin's `registerEntityVariants` instances (one default instance without them), plus, for a type with a selector, the variants its bytecode reveals (`EntityVariants`, above). Such a page carries the entity data of its variant (`getVariantData`): the `getNonDefaultValues()` of the instance reporting the page's table, sent in `EntityLootTableNode` only when a fresh instance given those values reports the same table. The client's `EntityStorage` creates an instance and assigns that data; a page without it gets the `createEntities` instance reporting its table, or any instance of the type. `registerEntityVariants` is therefore needed only for a variant neither the bytecode nor its entity data reproduces. Every page other than a type's own default table also carries why it belongs to its type (`EntityPage.reason`: a variant — any table that is not the type's default and no other reason claimed —, an event, a random page, `entityLootTables`, a plugin's `registerEntityLootTable`; the first one recorded for a table wins, in the order the mappings are added); `AbstractServer` writes it, with the table id, as the first lines of the node's info tooltip (`EntityLootTableNode.getInfoTooltip`), above the spawn tooltip, so the viewers show the (i) icon for such a page even when the mob does not spawn. A variant table is matched against the sample instances that report exactly that table (`EntityLootTableResolver.getLootTable`, so an instance answers for itself), which keeps a modifier bound to one variant off its siblings; when no instance claims the table — a mapping that came from `entityLootTables`, `registerEntityLootTable` or `fake_loot` — the whole sample of the type is used instead.

Since the attribution travels with the node, `disabledEntities` and `entityLootTables` take effect on the server alone. `entityCategories` still apply on both sides: the server decides what is scanned and sent, the client picks the viewer category for an entry and drops it when the matching category is hidden (`addRecipe` in each viewer module).

### `plugin/client` (+ `widget`, `widget/trades`)
Client-side rendering. `ClientUtils`/`WidgetUtils` helpers; one `ListWidget`/`IWidgetFactory` per node ID mirroring `plugin/common/nodes` (`LootTableWidget, LootPoolWidget, ItemWidget, AlternativesWidget, SequentialWidget, GroupWidget, EmptyWidget, DynamicWidget, ReferenceWidget, ModifiedWidget, GlobalLootModifierWidget, MissingWidget, TextureWidget`), plus `widget/trades` (`TradeWidget, TradeLevelWidget, SubTradesWidget, ItemListingWidget`). ### `plugin/glm` — Global Loot Modifier compatibility
Forge/NeoForge GLM datapack modifiers layer: `IGlobalLootModifierPlugin` (extra `IPlugin` extension GLM-integrating mods implement, `registerGlobalLootModifier`), `IGlobalLootModifierWrapper` (loader-agnostic view over one GLM), `LootPage`/`Match`/`Verdict`/`ParamState` (the page model), `IPageLootModifier` (one GLM, judged per page: `test` returns a `PageMatch` — the match plus the conditions that page leaves unexplained — and `getOperations(page, match)` builds the operations from it), `GlobalLootModifierUtils` (turns a GLM's conditions plus its operations into an `IPageLootModifier`, with `getMissingGlobalLootModifier` as the fallback for modifier classes no plugin adapts; its modifiers report `isAutoDetected`, and such a modifier alone never keeps a block page that `hideDefaultBlockLoot` would hide).

A **page** is one entry of the scan: `LootPage(tableId, paramSet, blocks, entityTypes, samples)`, built by `AbstractServer` for every block, entity and gameplay page. `paramSet` is the set vanilla rolls that page with — `BLOCK` for block pages, `ENTITY` for entity pages, the table's own type for gameplay pages, and `ALL_PARAMS` for a table declaring none, which makes the page *generic*. `samples` is a lazy, memoised list of sample entities. Every page carries a table id, so a table-id condition is meaningful on block and entity pages too.

A modifier is evaluated **against each page** in three-valued logic. `Match.NO` means it can never pass there, `Match.YES` that the page selects it, `Match.UNKNOWN` that nothing decides it statically; `Verdict` pairs the match with `explained`, true when the page fully accounts for the condition. A modifier is **bound** on a page when no term answers `NO` and at least one answers `YES`. A modifier that is bound on no page at all falls back to today's unbounded rule: it is attached where nothing rules it out, gated by `showUnboundedGlobalLootModifiers`.

`IServerUtils.testPage` decides one term — a condition, or the modifier object itself — in this order: the `IPageResolver` registered for its exact class through `IServerRegistry.registerPageResolver`, where `null` means "no opinion" and falls through; `AllOfCondition`/`AnyOfCondition`/`InvertedLootItemCondition`, descended in Kleene logic (a composite counts as explained only when every term is an explained `YES`, and inverting anything short of an explained `YES` yields `UNKNOWN`); otherwise the probe. The built-in resolvers live in `plugin/Plugin` (`LootItemBlockStatePropertyCondition`, `LootItemEntityPropertyCondition`, `DamageSourceCondition`).

The **probe** (`LootContextProbe`) runs the condition's own `test` against a `LootContext` built for the page. Its parameter map answers `hasParam` from `ParamState` — `DISALLOWED` is `false`, `REQUIRED` is `true`, `OPTIONAL` and `GENERIC` trap — returns `null` for a disallowed parameter's value and traps on every other read; the `RandomSource` traps on every call and the level is `null`. Returning without trapping is a definitive verdict (`YES` explained, or `NO`); a trap or any other `Throwable` is `UNKNOWN`. The trap is a preallocated `Error` subclass, so a mod's `catch (Exception)` cannot swallow it. This is what decides the loaders' loot-table-id conditions, once an `ILootContextPreparer` registered through `registerLootContextPreparer` has written the page's id into the carrier the condition reads — `ForgePlugin` on Forge, ALICompat's `portinglib` compat on Fabric. The modifier object is never probed, because `doApply` has side effects in real mods; it is decided by page resolvers only.

Entity sub-predicates (`type_specific`) are opt-in through `registerEntitySubPredicateResolver`: samples are bare `EntityType.create` instances carrying no spawn-time or runtime state, so only a resolver that declares the predicate a function of the entity class may read them. Anything unregistered is `UNKNOWN`.

`AbstractServer.readLootTables` collects every page first, evaluates all modifiers against all pages, and only then builds the nodes — the bound-elsewhere rule needs the whole picture before any page is rendered. Candidate items for a page come from parsing its table (plus any `fake_loot` pools for it) with no modifiers applied; a bound modifier survives when one of those items matches one of its operations **or** the page yields no candidates at all, while an unbounded one needs a real item match. The operations are asked for per page with the `PageMatch` the evaluation produced, so the conditions that page explains are left out without deciding them again — a table-id condition disappears on the table it names while an entity predicate carrying more than its type stays visible. A modifier's terms are tested until the first `NO`, and the term that answered `NO` moves to the front of that modifier's order, since consecutive pages of one kind are usually ruled out by the same term; the result does not depend on the order. Nothing on this path is timed per call: `System.nanoTime` on a machine whose clocksource is `hpet` costs about a microsecond, more than a resolver or probe call itself.

A page parses its table without operations at most once (`AbstractServer.PageTable`), for the candidate items and, when no modifier attaches, as the page's node; its `fake_loot` pools are parsed once as well. Everything kept for the scan — the loot table map used for references, the `fake_loot` tables and the tooltip palette — is released in the `finally` of `readLootTables` — the `fake_loot` tables directly, the rest through ACI's `clearCaches` (see `aci/CLAUDE.md`), and a plugin's own scan cache belongs in `registerCacheCleaner`. Hand-built `ILootModifier`s (`registerLootModifiers`, LootJS) keep their own `IType` path. Modifiers that end up on no page are counted into the log.

### `configuration` / `datagen` — data-driven mod compatibility
Backs the datapack-based `ali_config.schema.json` format:
- `AliConfig` — root config (`configVersion`, `blockCategories/entityCategories/gameplayCategories/tradeCategories` lists, `disabledEntities`, `tooltipColors` (shared `aci.configuration.TooltipColors`, see `aci/CLAUDE.md`), `logMoreStatistics`, `showInGameNames`, `hideDefaultBlockLoot` + `defaultBlockLootConditions`/`defaultBlockLootFunctions`, `showUnboundedGlobalLootModifiers`, `showEntitiesWithoutLoot`, `spawnInfo` (the shared `aci.configuration.SpawnInfoFilter` block, server-side — see `aci/CLAUDE.md`; `showEntitiesWithoutLoot` lists only what it lets through), `codeAnalysis` (`CodeAnalysis`, server-side, four switches for the bytecode analyses: `entityLootTables` — the namespace analysis, its jar and the global loot modifier instances in `EntityLootTableResolver`, off going straight to `scanNamespace` —, `entityVariants` — `EntityVariants`, leaving only plugin instances —, `traders` — `TraderDetector` and `getTradeLevels`, off giving unregistered traders no page —, `tradeListings` — `computeItemListing`, off going straight to the `getOffer` fallback), `showCharts` (client-only, turned into ACI `NumberOptions` by `plugin/client/TooltipUtils.getNumberOptions`, see `aci/CLAUDE.md`), `ignoredPredicateConditions`, `entityLootTables`); ships hardcoded defaults (`plant_loot`, `block_loot`, `entity_loot`, `chest_loot`, `fishing_loot`, `archaeology_loot`, `hero_loot`, `cat_morning_gift`, `piglin_bartering`, `sniffer_digging`, `gameplay_loot`, `trade_loot`).
- `LootCategory<T>` — abstract base (key/icon/type/hide/catalysts, JSON (de)serialization, abstract `validate(T)`). Subclasses match the schema's 4 category kinds: `BlockLootCategory` (block/tag list), `EntityLootCategory` (entity-type/tag list), `GameplayLootCategory`/`TradeLootCategory` (regex `pattern` list matched against the loot table's `ResourceLocation`). The schema's `type` enum (`BLOCK/ENTITY/GAMEPLAY/TRADE`) maps 1:1 to `LootCategory.Type`. Every field goes through `aci.configuration.ConfigCodecs` (see `aci/CLAUDE.md`): an invalid entry of `blocks`, `entityTypes`, `pattern` or `catalysts` is dropped on its own, and a category that still fails to decode (an unknown `icon`) is dropped from its list, both with a warning.
- `ConfigUtils` — reads/writes `config/ali/ali_common.json` (`Utils.COMMON_CONFIG_NAME`), handles `CURRENT_VERSION` migration by renaming the outdated file to a timestamped `.bak` and regenerating defaults. - `network.AbstractServer.readLootTables` filters blocks/entities/loot-tables/trades against these category lists on every reload — this is where the config actually gates ALI's data scan.
- `datagen.FakeLootProvider` — a `DataProvider` generating datapack JSON under `fake_loot/` for drops not expressible as a real loot table (e.g. mob-equipment drops for fox/piglin/skeleton/zombie/wither/drowned/etc), consumed back by `FakeLootDataManager`.
- `datagen.LanguageHolder` — aggregates `aci`'s `CoreLang` translations plus ALI-specific EMI category names and chest/loot-table display names into `TRANSLATION_MAP` (see `aci/CLAUDE.md`'s "Language wiring").

## Networking (canonical pattern — `awi/CLAUDE.md` mirrors this)

`ali/common/.../network` implements ALI's data-sync protocol — on-demand in its *transfer* only, the data itself is built eagerly at server start (see the root `CLAUDE.md` and step 3 below); packet registration/codec wiring itself lives in the loader modules (`ali/fabric/CLAUDE.md`, `ali/forge/CLAUDE.md`, `ali/neoforge/CLAUDE.md`), this package holds the shared logic and abstract template.

**Packets**: `StartMessage(int totalMessages)`, `DoneMessage()` (empty marker), `LootDataChunkMessage(int index, byte[] data)` (chunk payload), `RequestLootDataMessage()` (empty client→server request marker).

**Flow**:
1. Client-side, `compatibility.common.GenericUtils.register(...)` — called while the recipe viewer builds its own data (viewer plugin registration at client/world load, **not** when a loot category is opened) — hands `AbstractClient.INSTANCE.canRequestData` and `sendLootDataToPlayer(new RequestLootDataMessage())` to `clientRegistry.registerData` (see `aci/CLAUDE.md`'s `manager` section), which requests the data unless it is already received and blocks up to 30s per attempt, 3 attempts.
2. Server-side, the loader's `Server` class receives the request (wired via the loader module's own `NetworkUtils.registerCommon` — unrelated to `aci.network.NetworkUtils`, same name, different class) and calls `AbstractServer.syncLootTables(player)`.
3. `AbstractServer.readLootTables(ReloadableServerRegistries.Holder)` (called at world-load/reload time, not per-request) parses all block/entity/gameplay loot tables and trades into `IDataNode`s, writes the tooltip palette header (see `aci/CLAUDE.md`'s tree-model section) followed by the node data into a `FriendlyByteBuf` (both write steps go through `aci.network.NetworkUtils`, see `aci/CLAUDE.md`), gzips it, and slices it into ≤32KB chunks, cached in memory.
4. `syncLootTables` sends `StartMessage(chunks.size())`, then each `LootDataChunkMessage(index, data)`, then `DoneMessage()`.
5. `AbstractClient.onStart`/`onLootDataChunk`/`onDone` forward into `PluginManager.getInstance().clientRegistry` (`startReceivingData`, `addChunkData`, `doneReceivingData`), which reassembles the chunks (`aci.compatibility.DataReceiver`, used inside `CoreClientRegistry`) and completes the data future `registerData` waits on with the compressed bytes. The viewer's `GenericUtils.processData` then decompresses and decodes them through `network.LootDataReader`, which references no client-only class, so the same decode runs on a dedicated server.

The two top-level maps are written differently: trades go through `aci.network.NetworkUtils.writeMapData`, while loot tables go through `AbstractServer.writeLootData`, which writes each entry's node ID next to its table id. A top-level node is otherwise not self-describing — `CoreListNode.encode` writes IDs for children only — so without it `LootDataReader` could not tell an `EntityLootTableNode` from a plain `LootTableNode`.

### The item pipeline: nothing item-shaped is sent

The payload carries the node tree and nothing else — the flat item lists a recipe viewer needs (a recipe's outputs, a trade's costs and results, the reverse ingredient index) are derived **client-side** from that same tree, by `compatibility/common/GenericUtils.collectItems`/`collectTradeItems`. This is the same arrangement as AWI's block-tag pipeline (`awi/CLAUDE.md`), for the same two reasons: the lists cannot drift from what is rendered, and a tag is resolved against the *client's* current registry, so it re-resolves on every datapack/tag reload instead of being frozen at scan time.

- `IItemNode.getItem()` is what the slot stands for (`Either<ItemStack, TagKey<? extends ItemLike>>`), `getItems()` the stacks it resolves to (tag members expanded, a block tag's blocks as their items, empty stacks and repeated items dropped, list mutable), `retainItems(Predicate)` drops the members the viewer hides. Resolution goes through `NodeUtils.resolveItems`, used by both sides. A tag travels with its registry, item or block; the viewers show an item tag as their own tag ingredient and any other tag through `getItems()`, since none of them reads a block tag's items.
- `GenericUtils.pruneHiddenItems`/`pruneHiddenTrades` must run before anything asks for the lists — pruning narrows `getItems()` in place, which is what keeps tree, outputs and index in agreement. A node standing for an empty stack is kept: it is the placeholder second input of a single-input trade, and `requiresAllChildren` would drop the whole trade with it.
- In loot tables an empty stack is never an item: `NodeUtils.replaceEmptyItems`, run by `removeEmptyLootTable` after all operations, turns every `IItemNode` standing for one into an `EmptyNode` with the same chance and tooltip. Trades are not passed through it.
- **Inputs vs outputs live on `ITradeNode`, not on the leaf.** A leaf is one stack and cannot know which side of a trade it sat on; `ItemsToItemsNode` adds its children cost-first and encodes how many of the leading ones are costs, so the split survives the wire without relying on child count. The order survives because the node is `isOrdered()`, so `CoreListNode`'s decode does not sort its children by chance.
- The server still walks the tree (`AbstractServer.collectItems`) for two things only: telling an empty loot table from a real one in `removeEmptyLootTable`, and collecting a page's candidate items to match global loot modifiers against (see `plugin/glm`). Neither list is sent.
- There is **no item collector registration at all**, on either side: a table's items come from walking its parsed nodes and a trade's two sides from `ITradeNode`, so nothing in the API answers "what items does this entry/function/`ItemListing` produce". `registerItemListing` (the node factory) is the only trade-side registration.

`AbstractServer`/`AbstractClient` are template-method base classes: they hold all the shared logic above and declare `protected abstract send*` methods that each loader's `Server`/`Client` subclass implements over its native networking API (Fabric's `ServerPlayNetworking`/`ClientPlayNetworking`, Forge's `SimpleChannel`).

## Gametests

The integration test is one server-side GameTest per loader, in a `gametest` source set of `ali/fabric`, `ali/forge` and `ali/neoforge` that never reaches the release jar. It boots a headless dedicated server with the real loader, vanilla data and a test datapack, waits for the startup scan, reassembles `AbstractServer.getChunks()`, decodes them through `LootDataReader` with the client registry (`registerClientEvent` on the dedicated server) and renders every loot table and trade page to text, which it compares against the golden files in `ali/<loader>/src/gametest/golden/`. What the run produced is written to `ali/<loader>/build/gametest/golden/`, so `diff -r` between the two shows a failure line by line. `runGametest` deletes the run's `config` directory first, so every run scans with the default configuration, and carries a 10-minute Gradle timeout.

- **Layout.** The logic is `ali/common/src/gametest/java/.../LootDataGolden` (variants, reload) over `LootDataCapture` (decode and render every page — what ALICompat's gametest reuses) and the shared datapack is `ali/common/src/gametest/resources/data/ali_gametest/`, in this Minecraft version's data folder names (`loot_table`, `predicate`, `item_modifier`, `structure`); `ali:common` has no gametest source set of its own, every loader compiles these directories into its own, together with ACI's shared `GoldenFiles`/`GoldenRenderer`/`GoldenLanguage` (see `aci/CLAUDE.md`'s tests section). `ali/common`'s gametest code references no KubeJS class, since LootJS is not built on every loader. Each loader adds only a wrapper that registers the test (Fabric API's `@GameTest`, a `TEST_FUNCTION` registration plus a `test_instance` JSON on NeoForge), plus its own fixtures (see `ali/fabric/CLAUDE.md`, `ali/forge/CLAUDE.md`, `ali/neoforge/CLAUDE.md`).
- **Language.** `LootDataGolden` injects ALI's and ACI's `en_us` through `GoldenLanguage` before rendering, so the text does not depend on whether a loader loads mod languages on a GameTest server (Forge does not).
- **Views.** Every page is rendered twice: `normal`, and `advanced` with advanced tooltips and number formulas both on, as F3+H switches them together on the client. Charts are written out as their data, items with their component patch encoded as SNBT (`toString` carries identity hashes and changes every run) and the count their slot shows (`TooltipUtils.getSlotCount`).
- **Variants.** `default` holds every page. A variant changes one configuration field, reloads the datapacks and stores only the pages that differ from `default`, plus `removed.txt` listing the ones that disappeared; a variant that changes nothing fails. Reloading is required because a scan releases the `fake_loot` tables when it ends, so a second scan without a reload would run without them. After the variants a reload with the defaults has to reproduce the startup output. A loader adds its own variants through the wrapper.
- **Golden files are per loader.** Forge patches vanilla data (shears conditions become `can_tool_perform_action`, suspicious stew carries `forge:effect_id`), so the two sets differ even on vanilla pages.
- **Regenerating.** `-Pali_golden_regenerate=true` rewrites the golden files of every variant. A missing golden directory fails rather than regenerating.
- **LootJS.** Only the loaders that build `ali/common-lootjs` run it (none on this branch): LootJS, KubeJS and Rhino are on that gametest run's classpath only (`modGametestRuntimeOnly`, the same files as the loader's `modCompileOnly` pins). `runGametest` copies `ali/common/src/gametest/kubejs/` into the run directory on every loader, whose `server_scripts/lootjs.js`, written against LootJS 3, modifies the `ali_gametest:lootjs/*` tables and a few vanilla pages. Every case is its own `LootJS.modifiers` call: KubeJS runs the callbacks in one loop, so a script error in one drops every callback after it. The loader wrapper hands `LootDataGolden.run` the KubeJS server-script errors, which fail the test; a loader without LootJS hands it none.
- **Datapack fixtures.** Each table is named after the case it covers. A table referenced by another one and declaring no `type` is a sub-table and gets no page of its own (`AliServerRegistry.isSubTable`), so a case that lives in referenced tables needs an unreferenced table that reaches them (`references/cycle_entry`).
